# XZ Cases - 生成测试用例（xlsx）

参数: `$ARGUMENTS`

### 参数校验

如果 `$ARGUMENTS` 为空，**立即停止**，提示：

> 缺少版本号。用法: `/xz-cases N-M`（区间）或 `/xz-cases N1,N2,...`（离散）
> 示例: `/xz-cases 1-1.2`、`/xz-cases 1,1.2`、`/xz-cases 1`

---

## 辅助脚本

**脚本**：`xz-tools.py`

插件启用时 `bin/` 目录自动加入 PATH，直接作为命令调用即可（不需要 `python3` 前缀，也不需要绝对路径）。脚本在**当前工作目录**下操作 `.xz_planning/`。

---

## 执行流程

### 第一步：解析版本选择表达式

把 `$ARGUMENTS` 先按逗号 `,` 拆成若干 token，每个 token 是「单个版本」或「区间」：

- **区间** `A-B`（token 中含 `-`）：纳入**所有现存版本号 v 满足 A ≤ v ≤ B**。例如 `1-1.2` 命中现存的 `1`、`1.1`、`1.2` 三个版本（含中间版本）
- **单个** `A`（无 `-`）：只精确命中版本 `A`，**不**纳入相邻的中间版本。例如 `1,1.2` 只命中 `1` 和 `1.2`，即使存在 `1.1` 也跳过

把所有 token 的命中结果**取并集、去重、按版本号升序排序**，得到目标版本列表。

**版本号按数值比较**，不是字符串比较：`1 < 1.1 < 1.2 < 1.5 < 2 < 10`

### 第二步：列出现存版本并过滤

```bash
xz-tools.py status
```

从返回 JSON 的 `active` 和 `archived` 里拿到所有现存版本号，套用第一步的表达式过滤，得到最终目标版本列表。

- 区间表达式命中 0 个版本 → 停止，提示该区间内没有任何版本
- 离散表达式里某个版本不存在 → 记录「跳过」，继续处理其余版本
- 全部都不存在 → 停止，提示先用 `/xz-plan` 创建计划

### 第三步：逐个加载 PLAN 与代码

对每个目标版本 N（活跃 + 归档都要查）：

```bash
xz-tools.py parse N --include-archive
```

1. 用返回 JSON 的 `phase.plan_file` 读取 `N-PLAN.md` 完整内容，理解需求、技术方案、todolist
2. 如果同目录存在 `N-DISCUSS.md`、`N-UAT.md`，一并读取作为上下文
3. 读取 todolist 中**已完成 `[x]` 条目**涉及的**实际代码文件**，了解真实实现，作为用例的依据（不要凭空编造）

**按版本号升序读**，后读到的版本覆盖先读到的。

### 第四步：消解版本冲突，以最新实现为准

多版本汇总时，**后面的版本经常推翻前面版本的方案**（换实现、改字段、调整取值、废弃功能）。用例必须描述**当前代码里的最终形态**，绝不能拿老版本 PLAN 里已作废的方案当测试依据。

1. **后版本覆盖前版本** — 同一个功能点在多个版本里都被改过时，以**版本号最大**的那份方案为准，中间态一律不算
2. **识别覆盖信号** — 后版本 PLAN 里出现「改为」「替换」「废弃」「回滚」「不再」「调整为」「重构」，或者两个版本的 todolist 动了**同一个文件 / 函数 / 字段 / 接口**，就说明前面那份方案可能已经作废，必须去代码里核实
3. **代码是唯一裁判** — 只要拿不准某个行为的最终形态（字段名、取值范围、默认值、排序规则、条数上限、错误提示文案、兜底返回），就用 Grep/Read 打开对应代码文件确认当前实现，**以读到的代码为准，不以任何 PLAN 文字为准**。PLAN 写的是当时的打算，代码才是现在的事实
4. **被推翻的旧方案不生成用例** — 作废的中间方案一条用例都不写；同一个功能点跨版本被改过多次，最终只留**一行**，描述最终形态
5. **前后对比的基准是「改动前用户实际看到的样子」** — 详细说明里「以前是 X，现在改成 Y」的 X，指这批版本**上线前线上的真实形态**，不是同批版本里那个从未上线的作废草案；否则测试会去核对一个根本不存在过的状态
6. **对不上就标注，不编造** — 如果代码里找不到 PLAN 描述的功能（可能没实现、可能后来删了），不要凭 PLAN 编用例；要么这一行不生成，要么在详细说明里明确标注「计划与代码不一致，需与开发确认」

### 第五步：生成 xlsx

**用一个 Python 源文件**输出 xlsx，落盘到 `.xz_planning/cases/xlsx/`（脚本自动创建目录）。

1. 把整理好的用例填进脚本里的 `CASES` 列表（结构见下方「脚本骨架」）
2. 脚本写到 `/tmp/xz_cases_gen.py`
3. 运行（本机大概率没装 openpyxl，用 uv 一键带依赖跑）：

```bash
uv run --with openpyxl python3 /tmp/xz_cases_gen.py
```

**文件命名**（功能名由你根据这些版本的整体功能用一句话概括）：

- 多个版本：`cases/xlsx/v{首}-v{尾}-功能名测试用例.xlsx`，如 `v1-v1.2-用户模块测试用例.xlsx`
- 单个版本：`cases/xlsx/v{N}-功能名测试用例.xlsx`，如 `v1-用户登录测试用例.xlsx`

**只生成这一个 xlsx 产物。不生成 md，不更新 STATE.md，不更新 PLAN.md，不生成任何测试代码文件。**

## 列结构

这不是一张通用测试用例表，而是一份**版本改动验收清单**：**一行 = 一个核心功能点**（一处新增或一处改动），测试人员看完「详细说明」自己就知道该怎么测。

**内容列（4 列）：**

1. 用例编号（`TC-001`，三位补零，全文件连续）
2. 功能模块（业务模块名，用测试听得懂的叫法，如「战绩查询」而非 `game_log`；同一模块可以有多行）
3. 测试新增改动详细说明（**核心列，不限字数**，用 `1. 2. 3.` 序号逐条展开业务改动，用 `\n` 换行，写法见下方「详细说明写作规则」）
4. 预期结果（测试能观察到的现象，带具体数值，含「不应出现什么」，用 `\n` 换行）

**xlsx 额外两列**（留空给测试人员填）：

5. 测试结果
6. 备注/Bug

**不要生成这些列**：所属版本、用例标题、改动说明、优先级、类型、前置条件、操作步骤。改动内容全部并进「测试新增改动详细说明」，不再单独出列。

**xlsx 样式要求：**

- 冻结首行（`A2`）
- 自动筛选（覆盖到最后一列最后一行）
- 表头深蓝底白字加粗、自动换行
- 数据行按**功能模块**分块底色（不同模块不同淡色，同模块连续几行同色）；行数少，不加斑马纹
- 列宽预设（详细说明列最宽，预期结果次之，编号 / 模块较窄）

## 详细说明写作规则（本 skill 的质量核心）

「测试新增改动详细说明」这一列决定了测试人员看不看得懂，按下面三组硬约束写。

### 结构：逐条编号，顺序固定

必须用 `1. `、`2. `、`3. ` 逐条编号，**一条一个要点、一条一句话**，条数按改动复杂度给（一般 3～8 条），顺序固定：

1. **第 1 条 = 功能点 + 场景入口** — 以 `新增 xxx` 或 `改动 xxx` 起头（这里承担了标题的作用，一眼能看出这行讲哪个功能点），紧接着说这功能在哪、谁会用到、从哪进去能看到
2. **中间若干条 = 改动前后对比 + 各种情况分支** — 以前是什么样 → 现在变成什么样；正常情况怎样、传错怎样、没数据怎样、服务出问题怎样
3. **最后 1 条 = 测试重点** — 以「测试重点：」起头，说最容易出问题的地方、要盯着看的点

### 语言：三条禁令

- **禁止代码标识符与技术缩写** — `act_type`、`DAO`、`JWT`、`int8`、`round_id`、`GameLogUserRespStr`、SQL 片段、驼峰函数名一律翻成业务话：「记录类型开关」「登录身份」「整数上限」「轮次编号」「金额展示格式」
- **禁止规约腔** — 不写「必须」「应在……之前被拒绝」「避免……压力」这种设计评审语气；改成现象描述：「传错了会直接提示参数错误，不会去查数据库」
- **禁止只写抽象描述** — 数值要带单位和含义：「最多取最近 20 轮」「金额 30000 会显示成 3万」，不写裸值不写抽象词

### 正反例对照

（下表右列的 `<br>` 只是本文档表格内的排版换行，写进脚本时用 `\n`）

| ✗ 不要这样写（开发评审腔 + 术语裸露） | ✓ 改成这样 |
|---|---|
| 非法模式必须在访问数据库之前被拒绝，避免无效请求增加数据库压力或意外落入个人分支 | 1. 改动 战绩页的「看谁的记录」开关，只认「看自己」和「看全服」两个值<br>2. 填别的值（负数、没定义过的数字、超大数字）一律直接提示参数错误<br>3. 提示后不会去查数据库，也不会默认给你看自己的记录<br>4. 测试重点：正常玩家碰不到，主要防有人改包乱试 |
| 数据库短暂异常时接口沿用旧版兼容策略，前端仍收到成功的空列表，同时服务端必须留下错误日志方便排查 | 1. 改动 战绩查询查不到数据时的兜底表现<br>2. 数据库临时连不上时，页面不会报错崩掉<br>3. 页面显示「暂无记录」的空列表，跟真的没数据长得一样<br>4. 后台会记一条错误日志，出问题时找开发查日志能对上<br>5. 测试重点：这时候空列表不代表功能正常，要配合开发看日志确认 |
| 参数类型是int8，传128已经超出范围，应在JSON解析阶段报参数错误而不是发生数值绕回 | 合并进上面第一行的第 2 条，**不单独开一行** |

## 脚本骨架

```python
#!/usr/bin/env python3
# -*- coding: utf-8 -*-
"""xz-cases 生成脚本：输出 xlsx 到当前工作目录的 .xz_planning/cases/xlsx/。"""

from pathlib import Path
from openpyxl import Workbook
from openpyxl.styles import Alignment, Font, PatternFill, Border, Side
from openpyxl.utils import get_column_letter

# ↓↓↓ AI 按读到的 PLAN / 代码填充
BASENAME = "v1-v1.2-用户模块测试用例"      # 不带扩展名
CASES = [
    {
        "no": "TC-001",
        "module": "战绩查询",
        "detail": "1. 新增 全服战绩查询入口，玩家在战绩页原来只有「我的战绩」，这次多了「全服战绩」标签\n2. 以前只能看自己的记录，现在切到全服标签能看全服玩家最近的对局\n3. 两个标签共用一个入口，靠一个开关区分看谁的\n4. 全服最多只给最近 20 轮，按轮次从新到旧排\n5. 测试重点：切标签时两边数据不能串，金额格式两边要一样",
        "expect": "切到「全服战绩」能看到 20 条记录，最上面一条是最新一轮\n切回「我的战绩」只有自己的记录，不应混进别人的",
    },
    # ... 更多功能点
]
# ↑↑↑

HEADERS = ["用例编号", "功能模块", "测试新增改动详细说明", "预期结果"]
EXTRA_HEADERS = ["测试结果", "备注/Bug"]
XLSX_WIDTHS = [12, 16, 80, 48, 12, 24]
# 功能模块分块底色（按出现顺序循环取色；行数少，不用斑马纹，避免盖掉分块）
PALETTE = ["FFF7EC", "EAF6FF", "F5EEFF", "ECFBF0", "FFF0F3"]


def _module_fill_map():
    modules = []
    for c in CASES:
        if c["module"] not in modules:
            modules.append(c["module"])
    return {m: PALETTE[i % len(PALETTE)] for i, m in enumerate(modules)}


def write_xlsx(path):
    wb = Workbook()
    ws = wb.active
    ws.title = "测试用例"
    full_headers = HEADERS + EXTRA_HEADERS
    module_fill = _module_fill_map()

    header_fill = PatternFill(fill_type="solid", start_color="305496", end_color="305496")
    header_font = Font(bold=True, color="FFFFFF", size=11)
    header_align = Alignment(horizontal="center", vertical="center", wrap_text=True)
    thin = Side(style="thin", color="C0C0C0")
    border = Border(left=thin, right=thin, top=thin, bottom=thin)

    for col_idx, h in enumerate(full_headers, start=1):
        cell = ws.cell(row=1, column=col_idx, value=h)
        cell.fill = header_fill
        cell.font = header_font
        cell.alignment = header_align
        cell.border = border
    ws.row_dimensions[1].height = 32

    cell_align = Alignment(vertical="top", wrap_text=True)
    for row_idx, c in enumerate(CASES, start=2):
        fill_color = module_fill.get(c["module"], "FFFFFF")
        fill = PatternFill(fill_type="solid", start_color=fill_color, end_color=fill_color)
        values = [c["no"], c["module"], c["detail"], c["expect"], "", ""]
        for col_idx, v in enumerate(values, start=1):
            cell = ws.cell(row=row_idx, column=col_idx, value=v)
            cell.fill = fill
            cell.alignment = cell_align
            cell.border = border

    for i, w in enumerate(XLSX_WIDTHS, start=1):
        ws.column_dimensions[get_column_letter(i)].width = w

    ws.freeze_panes = "A2"
    last_col = get_column_letter(len(full_headers))
    ws.auto_filter.ref = f"A1:{last_col}{len(CASES) + 1}"
    wb.save(str(path))


def main():
    xlsx_dir = Path.cwd() / ".xz_planning" / "cases" / "xlsx"
    xlsx_dir.mkdir(parents=True, exist_ok=True)
    xlsx_path = xlsx_dir / f"{BASENAME}.xlsx"
    write_xlsx(xlsx_path)
    print(f"wrote: {xlsx_path}\ntotal cases: {len(CASES)}")


if __name__ == "__main__":
    main()
```

## 生成规则

### 粒度（这条最重要，宁少勿滥）

1. **一行 = 一个核心功能点** — 行的单位是「一处新增功能」或「一处改动」，**不是单个输入值、不是单个分支**
2. **同类必须收敛** — 同一个校验点的多个非法输入、同一个兜底策略的多种触发原因，全部写进那一行详细说明的子序号里，**不单独开行**。反例：`记录类型传 -1`、`传 2`、`传 128` 拆成三行 → 应合并成一行「记录类型开关的取值校验」，三个值写进同一条子序号
3. **内部实现不单独成行** — 函数调用次数、序列化路径、日志埋点这类测试观察不到的东西不开行；确实要提醒时，作为详细说明里的一条「排查提示」
4. **条数上限** — 单个版本 5～12 行，多版本汇总一般不超过 20 行；超了说明粒度还是太细，回去合并
5. **合并不等于漏测** — 合并后仍要保证每个核心功能点都有一行；宁可一行写长，不要拆成多行

### 内容

6. **跨版本汇总到一份** — 多个版本的功能点放进同一个 xlsx，按功能模块排在一起，不按版本分开
7. **用例编号全局连续** — `TC-001`、`TC-002`… 在整个文件内连续
8. **不写版本号和需求编号** — 用例正文里**不要**出现 `v36.2`、`#1`、`#2` 这类版本号或 todolist 条目编号，测试人员不关心需求是从哪条来的；要追溯用文件名里的版本号就够了
9. **基于已完成 `[x]` 条目生成** — 未完成的 `[ ]` 条目对应功能点在详细说明第 1 条标注「待实现后测试」
10. **依据真实代码，代码优先于计划** — 详细说明和预期结果来自读过的代码；PLAN 与代码冲突时**一律以代码为准**（见第四步），拿不准就 Grep/Read 去查，不凭空编造行为或字段
11. **预期结果写正反面** — 既写「应该出现什么」，也写「不应出现什么」，带具体数值（「能看到 20 条记录，最上面一条是最新一轮」「不应混进别人的记录」）
12. **数值要具体且前后一致** — 涉及数据都填具体示例值并说明含义，如「最多取最近 20 轮」「金额 30000 会显示成 3万」；数值要符合代码里的真实约束，同一行内详细说明与预期结果的数值必须对得上
13. **行尾不带标点** — 每一行结尾**不要**带句号 `。`/`.`、分号 `;`/`；` 或任何其他收尾符号，写到末尾字符就结束
14. **详细说明必须过「三条禁令」检查** — 见上方「详细说明写作规则」：无代码标识符、无规约腔、无抽象描述。写完自查一遍，有残留就重写
15. **xlsx 必须可用** — 冻结首行、自动筛选、表头配色、功能模块分块底色、列宽合理；「测试结果」「备注/Bug」两列留空给测试人员填

## 校验

运行脚本后抽查：

- `.xz_planning/cases/xlsx/` 下生成了 `.xlsx`，没有生成任何 md
- 内容列 4 列 + 测试列 2 列 = 6 列
- 行数落在 5～12（单版本）或 20 以内（多版本汇总）；明显超出说明粒度太细，回去合并
- 「测试新增改动详细说明」每格是否 `1. 2. 3.` 逐条编号、条数 3～8、第 1 条以「新增」或「改动」起头、最后一条以「测试重点：」起头
- 全表扫一遍是否残留代码标识符（`act_type`、`DAO`、`JWT`、`int8`、驼峰函数名、SQL 关键字）或规约腔（「必须」「应」「避免」）
- 多版本汇总时，同一功能点是否只剩一行、描述的是**最新版本的最终形态**；有没有把老版本已作废的中间方案当成待测行为（拿不准的行去代码里再核一遍）
- 若 `uv` 不可用，回退 `pip3 install openpyxl && python3 /tmp/xz_cases_gen.py`
