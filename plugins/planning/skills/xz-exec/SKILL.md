# XZ Exec - 执行版本计划

执行版本号: `$ARGUMENTS`。为空或不是合法版本号（正整数，或小数如 1.5）→ **立即停止**，提示 `用法: /xz-exec N`（示例 `/xz-exec 1`）。

**脚本**：`xz-tools.py`（`bin/` 已在 PATH，直接调用，在当前目录操作 `.xz_planning/`）。

---

## 执行流程

### 第一步：读取项目上下文

读取 `.xz_planning/PROJECT.md`（如果存在），了解项目技术栈和目录结构。

### 第二步：解析并读取计划

```bash
xz-tools.py parse $ARGUMENTS
```

- 从返回 JSON 中取 `phase.plan_file` 路径，读取 N-PLAN.md 完整内容
- 读取时不要只看 todolist，必须同时提取并理解这些章节（存在即读）：`目标` / `上下文` / `约束` / `完成标准` / `技术方案` / `任务清单` / `测试方案`
- 版本不存在 → 提示用户先运行 `/xz-plan N`

**执行原则：**
- `N-PLAN.md` 是本次执行的主上下文来源
- 如果计划中记录了用户外部资料（如接口约束、字段含义、业务规则、固定文案），执行时必须遵守
- 禁止依赖"当前聊天里可能提过但计划里没写"的信息继续执行

#### 模式判断（读到 PLAN 后立即判断）

| PLAN 头部 `> 状态:` | 走向 |
|---|---|
| **`待手动执行`** | 手动路径，**本 skill 不处理** → 提示去跑 `/xz-manual N`（贴完码它会把状态转成 `待闭环测试`，那时再回来跑本 skill）；**禁止替用户实现他明确要自己动手的条目** |
| **`待闭环测试`** | 手动路径（`/xz-manual` 校验通过）**或并行路径（`/xz-worktree` 全部组已合并）** —— 条目已勾完、代码已落地 → **跳过第四到第六步，但必须先走 3.5 步生成测试方案**，然后进第七步闭环测试。<br>**3.5 不能跳**——它是唯一生成用例表的地方，跳了第七步就没有可执行的方案。<br>**别被"没有未完成条目"骗过去建议 `/xz-done`**——这个状态的存在就是为了保证人工贴的码也要跑一遍闭环。跑完第七步再按第八步给建议。<br>**读到这个状态但任务清单里仍有 `[ ]` → 不许跳过第四到第六步**，改按 `进行中` 处理（先把剩下的条目做完再进第七步），并在对话里说明状态与勾选不一致。 |
| 其他（`待执行` / `进行中`） | 常规执行模式，进入第三步 |

**并行现场未收尾的检查**：`phases/N.xxx/worktree/` 下存在 `integration` 非 `applied` 的 handoff → 先告知用户有并行现场没收（跑 `xz-tools.py wt list N` 看详情），问清是要自己用那份 patch 还是丢弃（`xz-tools.py wt clean N`）。**别直接在主工作区把同一批 todo 再实现一遍** —— 会跟用户手上那份 patch 撞车。

### 第三步：评估当前状态

检查 todolist 中已完成（`[x]`）和未完成（`[ ]`）的条目，找到第一个未完成条目。

- **没有未完成条目** → 提示全部完成，建议运行 `/xz-done N`
- **有已完成条目 + 有未完成条目（中途接手）** → 进入接续评估（见下方）
- **全部未完成（从头开始）** → 直接进入第四步执行

#### 接续评估（中途接手时必须执行）

上一个 AI 可能已经执行了部分任务，当前代码状态未必和计划完全吻合。**先读最近已完成条目的 改动详情 → 用 Read 查涉及文件确认改动是否真落地 → 判断偏差程度**：

| 情况 | 操作 |
|------|------|
| 改动已正确落地，代码与 改动详情 一致 | 正常继续，进入第四步 |
| 小幅偏差但不影响后续（变量名略不同、多了注释） | 记录偏差，适配后续执行，进入第四步 |
| 改动未落地（标了完成但代码没改） | **停下来报告用户**，列出未执行条目并提问：「以下条目标记完成但实际未执行: {列表}。回复 1) 重新执行这些条目 2) 跳过继续后续」 |
| 与 改动详情 偏差较大（换了方案、改了别的文件、结构重组） | **停下来报告用户**，列出偏差点并提问：「已完成改动与计划偏差较大: {偏差点摘要}。回复 1) 回退重做—按原计划执行 2) 基于现状调整—/xz-update-plan N」 |

### 3.5 现场生成测试方案（动手改代码之前必做）

`N-PLAN.md` 的 `## 测试方案` **只有地基三段**（测试环境与命令 / 测试前置信息 / 通过标准），**没有用例表**——具体测哪几个点、什么命令什么断言由本步现场生成。之所以放执行阶段：计划写完到真正执行往往隔着若干轮改动（接口签名变了、todo 拆合了、依赖换了），拿当下的真实代码现场推比照抄一份过期方案准。**本步生成的方案是第四步「先跑」和第七步「闭环测试」的共同依据，不落 PLAN。**

**生成依据（三样都要，缺一不可）**：① PLAN 的计划内容（`目标` / `约束` / `完成标准` / `技术方案` / `任务清单`，第二步已读）② PLAN 的 `## 测试方案` 三段（环境命令、测试前置信息、通过标准）③ **当下代码的实际状态**——已有测试文件、测试框架、能跑什么命令、服务怎么起。**PLAN 的环境命令跟当下代码对不上时以代码为准**，并在对话里说明哪里对不上（如「PLAN 写的是 `npm test`，但 `package.json` 里已改成 `pnpm test`，按后者跑」）。

#### 三类判据（缺一类就会卡住闭环）

| 类别 | 判据 | 处理 |
|------|------|------|
| **自动化用例** | AI 能用一条命令跑出**机器可判定结果**：单测/集成测试、接口 curl + 断言、CLI 输出比对、脚本、数据库查询校验、浏览器操作（**用 `/claude-in-chrome` skill 驱动 Chrome**，唤起后走 `mcp__claude-in-chrome__*` 工具） | 直接跑 |
| **测试前置信息** | AI **能跑，只是缺参数**：数据库/Redis/MQ 连接串、外部 API base URL + token、测试账号、环境变量、seed 数据来源、本地依赖实例 | 对上 PLAN 的「测试前置信息」段；标「待定」的走 7.2.1 索取 |
| **人工介入项** | AI **客观做不到**，仅限：真实凭证/密钥/第三方账号、线上或预发环境、破坏性操作（删生产数据、发真实短信/支付）、业务方主观确认的视觉与体验判断 | 7.5 停下请人做或确认 |

**判定铁律**：能用 `/claude-in-chrome` 驱动浏览器完成的 UI 操作 **不算**人工项；**多端多人同时操作也不算**（该插件能开多个标签页/多份会话，双端互通、并发抢单这类场景 AI 自己模拟，「要两个账号同时在线」不是找人的理由）；「麻烦」「要起服务」「要造测试数据」**不算**（AI 自己起服务、自己造数据）；**缺连接信息更不算**——那是「测试前置信息」，措辞是「给我参数我自己跑」而不是「这事你来做」。**把能自动化的写成人工项 = 违规，必须重写。**

#### 自动化用例表

| 编号 | 对应 todo | 类型 | 执行命令 | 预期判定 | 先跑 |
|------|-----------|------|----------|----------|------|
| T1 | #1,#2 | 接口 | `curl -s -X POST localhost:8080/login -d '{"u":"a","p":"b"}'` | HTTP 200 且 body 含 `token` 字段 | ⏭️ 跳过（要先起服务） |
| T2 | #3 | 单测 | `go test ./auth/... -run TestTimeout` | 全部 PASS，无 FAIL | ✅ 可先跑 |

**「先跑」列判据**只有一条：**这条用例现在（代码还没改）能不能几秒内跑完**。
- `✅ 可先跑` —— 单测、纯函数、不依赖外部服务的 CLI 或脚本。第四步会在改代码前跑一次确认它是失败的。
- `⏭️ 跳过（原因）` —— 要起服务、要连数据库或 Redis、要造大批数据、浏览器用例，一律标跳过并在括号里写原因。这些留到第七步统一跑。
- **只要这条用例要用 PLAN「测试前置信息」里还标着「待定」的东西，就一定是 `⏭️ 跳过`**——参数都还没注入，先跑必然报连接错误。

**每条用例硬性要求**：① 有具体可执行命令（不是「运行测试」这种泛指）② 预期判定必须机器可判（HTTP 码、退出码、输出含某字符串、DB 某行值、页面某元素），禁止「功能正常」「表现符合预期」这类无法判定的话 ③ 标明对应哪几条 todo，**每条 todo 至少被一条用例覆盖** ④ **编号即产物前缀** —— T 编号就是产物文件名前缀（`tests/T3-run.log`）和报告「复现步骤」的小节号。

#### 人工介入项

分两型：**给信息型**（用户提供参数/样本，AI 自己跑）和 **动手型**（要用户把系统操作到某个状态，AI 从那个状态续跑）。两型都写三行：为什么 AI 做不了 / 需要你提供什么或操作到哪一步（动手型注明完成后回一句「已就绪」）/ 拿到后 AI 做什么（动手型写明从哪儿续跑，**不会让你重做一遍**）。

**人工介入项不另起编号**：每项必须挂在它服务的那条 T 用例上（写「拿到后跑 T7」而不是自成一套编号）；确实不对应任何自动化用例的纯人工确认项（如主观视觉与体验判断），**也要给一个 T 编号并进用例表**（类型写「人工」，预期判定写清"怎样算通过"），保证通过标准能逐项核对、报告里每条都有复现步骤。

#### 三条硬规则

1. **T 编号跨轮次稳定** — 生成前**先读同目录已有的 `N-TEST-REPORT.md`**（存在就读）：同一个验证点**沿用原编号**，新增的验证点接着历史最大编号往后排，**不复用已删编号**。否则产物文件名 `tests/T3-*` 和历史报告里的 T3 会指向两个不同的东西
2. **宽重构要加「阶段」列** — PLAN 的 `## 技术方案` 写了「走 expand-contract 三段」时，用例表加一列「阶段」，每条标 `全程必须绿`（回归基线，任何一批迁移后都得过）还是 `contract 后才跑`（迁移中间态本来就不该通过）。不标的话 7.6 每轮全量回归会把正常的中间状态判成失败，三轮上限直接撞满
3. **只展示不落 PLAN** — 在对话里展示完整用例表（**不等用户确认，展示完直接往下走**），最终随 7.8 写进 `N-TEST-REPORT.md`。**禁止回写 PLAN 的 `## 测试方案`**——PLAN 是计划书，报告才是执行记录

**PLAN 无 `## 测试方案` 章节（老计划）** → 环境命令自己扫代码推导，前置信息缺的走 7.2.1，照常生成用例表。**不因缺章节而中断，也不要求用户补计划。**

### 第四步：执行任务

根据 改动详情 中描述的具体改动：

1. **先跑一遍** — 看 3.5 步生成的用例表里挂在这条 todo 下面的 T 用例，**「先跑」列标了 `✅ 可先跑` 的，动手改代码之前先跑一次，确认它现在是跑不过的**。

   > 为什么多跑这一次：一条从来没失败过的用例最后通过了，你分不清是代码真做对了，还是这条用例压根没断到点子上。先看着它失败一次，后面它变绿才算数。

   **跑不跑以 3.5 标的为准，别自己重判**——`⏭️ 跳过` 的直接进第 2 小步，留到第七步统一跑。

   跑完看结果，三种情况：

   | 结果 | 怎么办 |
   |------|--------|
   | **跑不过**（断言失败、期望值对不上） | 正常往下写。第 3 小步改完再跑一遍看它通过，报告「测试结果」那条写上 `改之前先跑过，当时是失败的` |
   | **居然通过了** | 这条用例的断言没断到点子上（恒真断言，说白了就是改不改代码它都能过、等于没测）→ **当场把用例改对，再动手写代码**，报告「修复记录」写清原来的断言错在哪。归 7.4 的「用例/环境问题」，**不动源码** |
   | **报的是环境错误**（连不上库、服务没起、端口不通、命令找不到、依赖缺失） | **这不算验证成功，也不算用例有问题** —— 环境自检在 7.2，那时候还没跑。**别改用例、别改源码**，跳过这次先跑，直接进第 2 小步，这条留给第七步。顺手在 3.5 那份方案里把该行的「先跑」列改成 `⏭️ 跳过（环境依赖：xxx）`，后面的 todo 就不白跑了 |

   两条限制：这次先跑**不算进** 7.5.1 的「同一用例最多修 3 次」；先跑的命令一样受 2 分钟挂起限制，超时就跳过、留给第七步。
2. 读取需要修改的现有文件
3. 按描述执行代码编写/修改
4. 确保改动符合 改动详情 的描述
5. **语法检查** — 改动完成后用项目对应的方式做语法级检查（Python `python3 -c "import ast; ast.parse(open('路径').read())"`、JS/TS 走项目 lint、其他语言用对应编译器/解释器）。不通过 → **立即修复**，修复后再标记完成

### 第五步：标记完成

**每完成一条只勾 `[x]`**（勾选是进度的唯一来源），改 N-PLAN.md（用 `phase.plan_file` 路径），不动时间与变更记录。

**全部条目做完后统一做一次**：`date "+%Y-%m-%d %H:%M:%S"` 取时间 → 更新 `> 最后更新:` → 在变更记录追加**一行**（如 `- YYYY-MM-DD HH:mm:ss 完成 #1-#5`）→ 跑一次 `xz-tools.py update-state`。

### 第六步：循环或结束

检查是否还有下一个 `[ ]` 条目：

- **有** → 回到第四步继续执行
- **无** → 全部完成，**不要在这里收尾**，直接进入第七步闭环测试。代码写完 ≠ 做完，条目全 `[x]` 只代表改动落地，必须跑完闭环测试才允许输出下一步建议。

### 第七步：闭环测试与修复循环（全部条目完成后强制执行）

**目标**：AI 自己把本次改动完整跑一遍，出问题自己修、自己全量回归，直到全绿或触到上限停下报告。**只有客观做不到的事才停下来找人。**

#### 7.1 取测试方案

**用 3.5 步生成的那份用例表**，逐条执行。方案已经在 3.5 展示过，这里不重新生成、不重新展示。

第四步执行过程中如果动过 3.5 那份方案（如把某条的「先跑」列改成了 `⏭️ 跳过（环境依赖）`、发现某条 todo 的实现方式变了要调断言），**以改过的为准**，并在报告「修复记录」里留一行说明改了什么、为什么改。

#### 7.2 环境与前置信息自检

**先自己想办法，别急着问人。** 顺序：

1. **读 PLAN 的「测试前置信息」段** —— 已经记了来源的直接用（去那个来源里读），**禁止把用户在计划阶段已经给过的再问一遍**；只有标「待定」的才可能要问。用例要用的前置项 PLAN 里压根没写 → 说明 3.5 漏了一项，补进本步索取清单
2. **仍缺则自查代码**：`.env` / `.env.example` / `config/*` / `docker-compose.yml` / `Makefile` / `conftest.py` 及测试 fixture / `README` 本地开发章节 / 项目已有测试的连接配置
3. **检查命令与服务**：测试框架装没装、端口通不通、依赖服务起没起。**纯启动本项目的服务**（如 `npm run dev`、`go run main.go`）自己起；**要起外部依赖容器**（数据库/Redis/MQ）→ 不自作主张，转 7.2.1 让用户选
4. 自查后仍缺 → **转 7.2.1 一次性索取**；属于人工项范畴的（真实凭证/线上环境）→ 转 7.5

用户给的凭据就地用；确实要落盘只放 `.xz_planning/phases/N.xxx/tests/.env.local`（文件头标注勿提交、先确认项目 `.gitignore` 覆盖），**明文不进 PLAN 与报告**。

#### 7.2.1 前置信息缺失 → 停下索取（一次性）

与 7.5 的区别：这里是**"给我参数我自己跑"**，不是"这事你来做"。

缺参数就**一次性**纯文本问清（只问真缺的，PLAN 里已经给过来源的不许再问），每项写：要什么 / 为什么要 / 我找过哪些文件（**必须真查过，禁编**）/ 给选项（直接贴、指到文件字段、我起本地实例（注明占端口与是否清理）、跳过）。选「我起本地实例」要先说清起什么占哪个端口、用户点头才动手。

#### 7.3 执行全部自动化用例

逐条真实执行，记录每条：通过 / 失败 / 阻塞 + 关键输出摘要（错误栈、状态码、断言差异）。

> **禁止伪造结果**：没有真实执行过的用例不许标记通过，禁止靠"代码看起来是对的"推断结论、禁止编造命令输出。

**边跑边落，不攒到最后补**：每条用例跑完**立即**在报告里补上该条的「测试结果」一行和「复现步骤」`###` 小节，**把刚才真跑的那条命令原样贴进去**，再跑下一条。事后统一补写等于凭记忆编现场，与 7.4.1 的即时可见性同理——**禁止**。

测试产物（脚本/截图/样本/日志）放 `.xz_planning/phases/N.xxx/tests/`，名字带 T 编号好认就行；报告不进 `tests/`；产物里的 token/密钥/手机号落盘前替换成 `***`。浏览器用例用 `/claude-in-chrome` 在关键节点截图存进去，这是 UI 结果唯一的可回看证据。

#### 7.4 失败分诊（三类，判错类别比修得快更重要）

| 类别 | 判断依据 | 处理 |
|------|----------|------|
| **实现 bug（计划内）** | 本次 todo 改的代码写错了：漏判空、逻辑反、参数传错、边界没处理 | **直接修源码**，修完进 7.6 全量回归 |
| **用例/环境问题** | 代码没问题，是测试命令写错、端口/路径不对、测试数据缺失、fixture 没准备 | 修用例或环境，**不动源码**，然后重跑 |
| **越界** | 修复需要新增功能/新建文件/改架构/动计划外模块，或根因在本次改动之外 | **不修**，记入待确认清单，进 7.7 |
| **触碰用户指定差异** | 修复方案会推翻 PLAN `## 约束` 里「已确认保留手动实现」的写法 | **不自行改**，停下来单独问：「这是你特意保留的写法，但 T3 失败根因在此，是否允许改？a. 允许改（推荐）b. 保留写法，我自己想办法 c. 忽略该用例」 |

> 最后一类是第七步里唯一**为了征求许可**而打断的情况——`## 约束` 里那行留痕是用户在 `/xz-manual` 校验闸门上明确拍过板的，AI 不能替他推翻自己刚做的决定。另一种打断是**走不下去了**（7.5 卡壳），性质不同：那不是征求许可，是真的没法往下走。

#### 7.4.1 改动可见性（每修一处即时打印，不等最后汇总）

修复源码时**每改完一处就在终端打印一次**（文件:行号 / 原因 / 改前 / 改后），然后才改下一处；禁止批量改完再统一说。手动 / 并行路径（`待闭环测试`）跑闭环时一样适用——代码不是本轮 exec 写的，更得看得见 AI 动了哪儿。同一内容汇总进报告的修复记录。

**修复牵动命令就同步改**：修复让某条用例的命令/参数变了 → 同步改报告「复现步骤」里该条的代码块，**贴出来的必须是最后真正跑通的那条**；确属用例本身写错要改断言的 → 「测试结果」和「修复记录」**两处都要留痕**（原断言是什么、为什么错、改成了什么）。

#### 7.5 卡壳与人工介入 → 停下找人（防死磕的核心闸口）

**闭环 ≠ 无限自转。** 走不下去就停下来找人，禁止在原地反复试、反复改指望它自己变绿——**卡壳不喊人、在原地空转，比打扰用户严重得多。**

典型卡壳：预先声明的人工介入项 / 同一用例修 3 次仍失败 / 根因说不清 / 改法取决于用户意图 / 环境阻塞 / 要人工操作到某一步（验证码、扫码、第三方后台）/ 命令超 2 分钟无输出 / 修复反复横跳。

**先跑完能跑的，再一次性问**（不要遇到一个停一次）：把与卡壳项无关、还能独立跑的用例全部跑完，卡壳项攒成一份清单一次性纯文本提问（禁用 AskUserQuestion——其弹窗会吞掉同回复中前面的文本），每项写：现象 / 已试过什么 / 卡在哪 / 需要你做什么 / 拿到后我做什么。

**用户回复后的处理：**

| 回复 | 处理 |
|------|------|
| **给了信息/参数** | 用它继续修或继续跑；该项计入修复轮次 |
| **「N 已就绪」** | **从人工操作后的状态接着跑该用例的剩余部分**，不重头来、不重复要求用户再操作一遍；跑之前先确认一下当前状态确实到位（如查一下登录态/数据是否已存在） |
| **「跳过 N」** | 「测试结果」该行标 **`⏭️ 未验证`**，卡在哪 / 已尝试什么 / 需要用户做什么写在同一行，继续跑其余用例 |
| **用户给的信息仍不足以解决** | **不许自己接着猜**——再问一轮，明确说「按你给的 X 试过了，结果还是 Y，还差 Z」；同一项最多再问一轮，仍不通则「测试结果」标 `❌ 失败`、注明「未解决」，并进报告「遗留与下一步」 |

**卡壳项的「复现步骤」照样写全**：人工步骤用 `# ⚠️ 你手动做：` 注释标出，并写明**AI 从第几步续跑、前面哪几步不用重做**（这是用户下次自己复现时最需要的一行）；用户回「跳过」的标「未验证」，步骤也照写——他想自己跑时能直接照做。

#### 7.5.1 防死循环硬性护栏（违反即为违规）

| 护栏 | 上限 | 触到之后 |
|------|------|----------|
| 同一条用例的修复次数 | **3 次** | 判定卡壳，转 7.5 找人，禁止修第 4 次 |
| 全局修复-回归轮次 | **3 轮** | 停止修复，进 7.7 收敛报告 |
| 同一失败的重跑确认次数 | **2 次** | 确认不是偶发后立即分诊，禁止反复重跑指望它自己变绿 |
| 单条命令执行时长 | **2 分钟**（长任务按项目实际值，需在报告注明） | 判为挂起，中止该命令转 7.5，禁止干等 |
| 同一项的追问轮次 | **2 轮** | 仍不通则标「未解决」，写进报告「遗留与下一步」，不再纠缠 |

**禁止放水式通过（红线）**：不许为了让用例变绿而——改断言去迁就错误结果、删掉跑不过的用例、注释或绕过被测代码、把真实逻辑 mock 成永远成功、把失败降级成 warning。确实是用例本身写错了要改断言，**必须在报告的「修复记录」里写明：原断言是什么、为什么它是错的、改成了什么**，接受用户回头复查。

**停下就是真停**：进入 7.5 提问后，在用户回复前**不得**继续改源码、不得继续尝试该卡壳项。可以做的只有：把无关的用例跑完、整理清单。

#### 7.6 修复后全量回归（上限 3 轮）

每轮修完，**全量重跑所有自动化用例**，不能只跑失败的那几条——防止修 A 把 B 改坏。一轮 = 修复 + 全量回归。**最多 3 轮**，且每条用例最多修 3 次（见 7.5.1）。

**每轮结束打印一行进度**（如 `🔄 第 2 轮回归：T1-T6 → 通过 5 / 失败 1（T3 仍 401，已修 3 次 → 判定卡壳，本轮结束后找你确认）`），让用户看得见还在往前走、没有空转。

**回归跑完覆盖产物**：`tests/` 里的产物与报告结果更新为**最后一轮**的真实结果，不留上一轮的旧截图旧日志混淆视听。

#### 7.7 收敛判断

**结论词落在哪**：报告「测试结果」段的首行 + **第八步终端输出的首行** + **PLAN 变更记录那一行**，三处一致；逐条状态看「测试结果」里每条的 icon。

- **全绿**（自动化用例全通过，人工项已由用户确认，无阻塞项、无卡壳项）→ 进 7.8 写报告，结论词 **「全部通过」**
- **有阻塞项**（用户在 7.2.1 回了「跳过」，相关用例缺信息没跑）→ 结论词 **「部分阻塞」**（区别于「部分失败」——不是代码有问题，是没参数没跑成）；这些条目标 `⛔ 阻塞`、写清缺什么，「遗留与下一步」写「补 `tests/.env.local` 后重跑 `/xz-exec N` 即可」
- **有卡壳项未解决**（7.5 问过、用户跳过或追问 2 轮仍不通）→ 结论词 **「待人工确认」**；这些条目标 `⏳ 待确认` 或 `⏭️ 未验证`，写清卡在哪、已尝试什么，「遗留与下一步」写还缺什么、用户提供后怎么继续
- **3 轮仍未全绿，或存在越界项** → **停下报告**，纯文本列出：剩余失败项 + 每项已尝试过的修复 + 建议下一步（越界项 → `/xz-update-plan N` 补条目；根因不清 → `/xz-debug` 定位）。报告照样写（结论词「部分失败」），不要静默结束

> **任何一种未全绿的收尾都必须落到"用户下一步能做什么"**：要么给出他补什么信息/做什么操作后重跑，要么给出该走哪个 skill。禁止只说"部分失败"就结束，那等于把死循环换了个形式甩给用户。

#### 7.8 产出

1. **写 `N-TEST-REPORT.md`** — 落在 **`{phase.plan_file 所在目录}/N-TEST-REPORT.md`**，与 `N-PLAN.md` 平级，**不进 `tests/`**；已存在则**覆盖为最新一轮结果**
2. **PLAN 变更记录追加一行** — `- YYYY-MM-DD HH:mm:ss 闭环测试: 通过 X/Y，修复 K 轮，结论 全部通过`（结论词取 7.7 四选一），同时更新 `> 最后更新:`
3. **进来时状态是 `待闭环测试` 的，跑完把 PLAN 头部 `> 状态:` 改成 `已完成`** —— 不改的话下次跑 `/xz-exec N` 还会跳进第七步重跑一遍闭环，而且 `/xz-done` 会一直拦着不让归档
4. **刷新 STATE.md** — `xz-tools.py update-state`

**测试脚本落地规则**：

- **项目已有测试框架** → 测试代码**写进项目正式测试目录**（如 `tests/`、`*_test.go`），报告「复现步骤」里写明代码位置 + 运行命令
- **项目无测试框架** → 可执行脚本就是 `tests/T{编号}-run.sh`｜`.py` 并**保留**（下次可重跑），不往源码树里乱扔文件

#### N-TEST-REPORT.md 模板

**获取当前时间：** `date "+%Y-%m-%d %H:%M:%S"`

````markdown
# 版本 N: 中文需求名 - 闭环测试报告

> 生成时间: YYYY-MM-DD HH:mm:ss

## 测试结果

通过 X/Y，修复 K 轮，结论 <7.7 四选一>。

- T1 ✅ 登录返回 token
- T2 ✅ 超时生效（改之前先跑过，当时是失败的）
- T3 ⏳ 卡片排版待你确认 —— 截图 `tests/T3-排版.png`，未经你确认不标通过
- T4 ⛔ 阻塞：缺测试库 DSN（你回了「跳过」），补进 `tests/.env.local` 后重跑
- T5 ⏭️ 未验证：生产商户退款，预声明人工项

## 复现步骤（照着跑就能重来一遍，cwd = 项目根）

### T1 登录接口
```bash
go run ./cmd/api &
curl -s -X POST localhost:8080/login -d @tests/T1-req.json
```
预期：HTTP 200 且 body 含 `token`

### T5 注册验证码（含人工步骤）
```bash
curl -s -X POST localhost:8080/register -d '{"phone":"1xxxxxxxxxx"}'
# ⚠️ 你手动做：手机收验证码并提交，直到账号可登录
curl -s -X POST localhost:8080/login -d '{"u":"1xxxxxxxxxx","p":"***"}'   # AI 从这里续跑，前两步不用重做
```
预期：登录返回 200 且拿到 token

## 修复记录

一轮一条：哪条用例失败 → 判定是什么 → 改了 `file:line` 的什么 → 回归结果。本次无修复则写「0 轮修复，全部用例首轮通过」。

## 遗留与下一步

只写**还需要用户做什么**（补什么参数重跑 / 确认什么 / 走哪个 skill）；无遗留写「无」。
````

三条底线：

1. **人工确认项在用户明确回复之前一律 `⏳`**，禁止 AI 替用户判通过、禁止靠「截图看着没问题」标 ✅；缺参数没跑成（`⛔`）或用户跳过（`⏭️`）**既不算通过也不算失败**，不许凑进通过数
2. **复现步骤里贴的必须是真跑过的那条命令**；人工步骤用 `# ⚠️ 你手动做：` 标出，并写明 AI 从第几步续跑、前面哪几步不用重做
3. 结果段一屏看完；失败/卡住的写清缺什么、下一步做什么

### 第八步：输出下一步建议

闭环测试收尾后，以纯文本输出（禁用 AskUserQuestion）：

> 版本 N 的 todolist 已全部完成，闭环测试：**全部通过**，通过 X/Y，修复 K 轮，报告见 `phases/N.xxx/N-TEST-REPORT.md`。接下来：
>   /xz-review N — 代码审查（可选）
>   /xz-update-plan N — 追加/更新计划（有新需求、遗漏项或越界失败项）
>   /xz-done N — 归档版本

**首行必须带 7.7 的结论词**（全部通过 / 部分失败 / 部分阻塞 / 待人工确认）——与报告「测试结果」段首行一致。

**测试未全绿时**，把上面第一行换成「闭环测试：**部分失败**，X/Y 通过，仍有 Z 项待处理（详见 N-TEST-REPORT.md 的『遗留与下一步』）」，并把 `/xz-update-plan N` 或 `/xz-debug` 放在建议首位；**有 `⏳ 待确认` 的人工项**，首行后补一句「T7 等你确认排版后我才标通过」，不许替用户判定。

用户回复后执行对应 skill 命令。
