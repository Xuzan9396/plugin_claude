# XZ Exec - 执行版本计划

执行版本号: `$ARGUMENTS`

### 参数校验

如果 `$ARGUMENTS` 为空或不是合法版本号（正整数，或小数如 1.5），**立即停止**，提示：

> 缺少版本号。用法: `/xz-exec N`
> 示例: `/xz-exec 1`

## 辅助脚本

**脚本**：`xz-tools.py`

插件启用时 `bin/` 目录自动加入 PATH，直接作为命令调用即可（不需要 `python3` 前缀，也不需要绝对路径）。脚本在**当前工作目录**下操作 `.xz_planning/`。

---

## 执行流程

### 第一步：读取项目上下文

读取 `.xz_planning/PROJECT.md`（如果存在），了解项目技术栈和目录结构。

### 第二步：解析并读取计划

```bash
xz-tools.py parse $ARGUMENTS
```

- 从返回 JSON 中取 `phase.plan_file` 路径，读取 N-PLAN.md 完整内容
- 读取时不要只看 todolist，必须同时提取并理解这些章节（存在即读）：
  - `目标`
  - `上下文`
  - `约束`
  - `完成标准`
  - `技术方案`
  - `任务清单`
  - `测试方案`
- 版本不存在 → 提示用户先运行 `/xz-plan N`

**执行原则：**
- `N-PLAN.md` 是本次执行的主上下文来源
- 如果计划中记录了用户外部资料（如接口约束、字段含义、业务规则、固定文案），执行时必须遵守
- 禁止依赖"当前聊天里可能提过但计划里没写"的信息继续执行

#### 模式判断（读到 PLAN 后立即判断）

| PLAN 头部 `> 状态:` | 走向 |
|---|---|
| **`待手动执行`** | 手动路径，**本 skill 不处理** → 提示去跑 `/xz-manual N`（见下） |
| **`待闭环测试`** | 手动路径已过 `/xz-manual` 校验闸门，代码是人工贴的、条目已勾完 → **跳过第四到第六步，但必须先走 3.5 步生成测试方案**，然后进第七步闭环测试。<br>**3.5 不能跳**——它是唯一生成用例表的地方，跳了第七步就没有可执行的方案。<br>**别被"没有未完成条目"骗过去建议 `/xz-done`**——这个状态的存在就是为了保证人工贴的码也要跑一遍闭环。跑完第七步再按第八步给建议。 |
| 其他（`待执行` / `进行中`） | 常规执行模式，进入第三步 |

### 手动路径归 `/xz-manual`

PLAN 头部 `> 状态: 待手动执行` → **本 skill 不处理**，停下提示：

```
版本 N 走的是手动执行路径（状态：待手动执行）。
请运行 /xz-manual N —— 没有 N-MANUAL.md 时它生成手动清单，
你贴完码再跑一次 /xz-manual N 做校验，通过后状态转「待闭环测试」，
那时再回来跑 /xz-exec N，我直接做闭环验证。
```

**禁止在本 skill 内替用户实现「待手动执行」版本的条目**——那正是用户明确要自己动手的部分。


### 第三步：评估当前状态

检查 todolist 中已完成（`[x]`）和未完成（`[ ]`）的条目，找到第一个未完成条目。

- **没有未完成条目** → 提示全部完成，建议运行 `/xz-done N`
- **有已完成条目 + 有未完成条目（中途接手）** → 进入接续评估（见下方）
- **全部未完成（从头开始）** → 直接进入第四步执行

#### 接续评估（中途接手时必须执行）

上一个 AI 可能已经执行了部分任务，当前代码状态未必和计划完全吻合。必须先评估再继续：

1. **读取最近已完成条目的 改动详情** — 了解上一步应该做了什么
2. **检查实际代码** — 用 Read 工具查看这些条目涉及的文件，确认改动是否真的落地
3. **判断偏差程度：**

| 情况 | 操作 |
|------|------|
| 已完成条目的改动已正确落地，代码与 改动详情 一致 | 正常继续，进入第四步 |
| 有小幅偏差但不影响后续任务（如变量名略不同、多了注释） | 记录偏差，适配后续执行，进入第四步 |
| 已完成条目的改动未落地（标了完成但代码没改） | **停下来报告用户**，文本列出未执行条目并提问：「以下条目标记完成但实际未执行: {列表}。回复 1) 重新执行这些条目 2) 跳过继续后续」 |
| 已完成的改动与 改动详情 偏差较大（用了不同方案、改了不同文件、结构重组） | **停下来报告用户**，文本列出具体偏差点并提问：「已完成改动与计划偏差较大: {偏差点摘要}。回复 1) 回退重做—按原计划执行 2) 基于现状调整—/xz-update-plan N」 |

### 3.5 现场生成测试方案（动手改代码之前必做）

`N-PLAN.md` 的 `## 测试方案` **只有地基三段**（测试环境与命令 / 测试前置信息 / 通过标准），**没有用例表**——具体测哪几个点、什么命令什么断言，由本步现场生成。

**为什么放在执行阶段而不是计划阶段**：计划写完到真正执行往往隔着若干轮澄清和改动（接口签名变了、todo 拆合了、依赖换了）。拿当下的真实代码现场推，比照抄一份过期方案准。

**本步生成的方案是第四步「先跑」和第七步「闭环测试」的共同依据，不落 PLAN。**

#### 生成依据（三样都要，缺一不可）

1. **PLAN 的计划内容** — `目标` / `约束` / `完成标准` / `技术方案` / `任务清单`（第二步已读）
2. **PLAN 的 `## 测试方案` 三段** — 环境命令、前置信息 P 表、通过标准
3. **当下代码的实际状态** — 已有测试文件、测试框架、能跑什么命令、服务怎么起。**PLAN 的环境命令跟当下代码对不上时以代码为准**，并在对话里说明哪里对不上（如「PLAN 写的是 `npm test`，但 `package.json` 里已改成 `pnpm test`，按后者跑」）

#### 三类判据（缺一类就会卡住闭环）

| 类别 | 判据 | 处理 |
|------|------|------|
| **自动化用例** | AI 能用一条命令跑出**机器可判定结果**：单测/集成测试、接口 curl + 断言、CLI 输出比对、脚本、数据库查询校验、浏览器操作（**用 `/claude-in-chrome` skill 驱动 Chrome**，唤起后走 `mcp__claude-in-chrome__*` 工具） | 直接跑 |
| **测试前置信息** | AI **能跑，只是缺参数**：数据库/Redis/MQ 连接串、外部 API base URL + token、测试账号、环境变量、seed 数据来源、本地依赖实例 | 对上 PLAN 的 P 表；标「⏳ 待定」的走 7.2.1 索取 |
| **人工介入项** | AI **客观做不到**，仅限：真实凭证/密钥/第三方账号、线上或预发环境、破坏性操作（删生产数据、发真实短信/支付）、业务方主观确认的视觉与体验判断 | 7.5 停下请人做或确认 |

**判定铁律**：
- 能用 `/claude-in-chrome` 驱动浏览器完成的 UI 操作 **不算**人工项；
- **多端多人同时操作也不算**——该插件能开多个标签页/多份会话上下文，双端互通、并发抢单这类场景 AI 自己模拟，「要两个账号同时在线」不是找人的理由；
- 「麻烦」「要起服务」「要造测试数据」**不算**人工项——AI 自己起服务、自己造数据；
- **缺连接信息 ≠ 人工介入项**——那是「测试前置信息」：给了参数 AI 自己就能跑完，别写成"这事你来做"；
- 把能自动化的写成人工项 = 违规，必须重写。

#### 自动化用例表

| 编号 | 对应 todo | 类型 | 执行命令 | 预期判定 | 先跑 |
|------|-----------|------|----------|----------|------|
| T1 | #1,#2 | 接口 | `curl -s -X POST localhost:8080/login -d '{"u":"a","p":"b"}'` | HTTP 200 且 body 含 `token` 字段 | ⏭️ 跳过（要先起服务） |
| T2 | #3 | 单测 | `go test ./auth/... -run TestTimeout` | 全部 PASS，无 FAIL | ✅ 可先跑 |
| T3 | #4 | 浏览器 | 用 `/claude-in-chrome` 打开 `localhost:3000/login` 提交表单 | 页面出现「登录成功」文案且 URL 跳到 `/home` | ⏭️ 跳过（浏览器用例） |

**「先跑」列判据**只有一条：**这条用例现在（代码还没改）能不能几秒内跑完**。
- `✅ 可先跑` —— 单测、纯函数、不依赖外部服务的 CLI 或脚本。第四步会在改代码前跑一次确认它是失败的。
- `⏭️ 跳过（原因）` —— 要起服务、要连数据库或 Redis、要造大批数据、浏览器用例，一律标跳过并在括号里写原因。这些留到第七步统一跑。
- **只要这条用例挂了 PLAN「测试前置信息」里的 P 编号，就一定是 `⏭️ 跳过`**——参数都还没注入，先跑必然报连接错误。

**每条用例硬性要求**：① 有具体可执行命令（不是「运行测试」这种泛指）② 预期判定必须机器可判（HTTP 码、退出码、输出含某字符串、DB 某行值、页面某元素），禁止「功能正常」「表现符合预期」这类无法判定的话 ③ 标明对应哪几条 todo，**每条 todo 至少被一条用例覆盖** ④ **编号即产物前缀** —— T 编号就是产物文件名前缀（`tests/T3-run.log`）和报告「复现步骤」的小节号。

#### 人工介入项

分两型：**给信息型**（用户提供参数/样本，AI 自己跑）和 **动手型**（要用户把系统操作到某个状态，AI 从那个状态续跑）。两型都写三行：

1. [给信息型] 支付回调验签需要生产商户密钥
   - 为什么 AI 做不了：密钥只在你的密钥管理里，本地无法获取（真实凭证）
   - 需要你提供：测试商户号 + 密钥，或一条已签名的回调报文样本
   - 拿到后 AI 做什么：注入本地环境跑 T7 验签用例并断言返回 `SUCCESS`
2. [动手型] 注册流程的短信验证码
   - 为什么 AI 做不了：验证码只发到你的手机，本地收不到（真实短信通道）
   - 需要你操作到哪一步：手动注册到「已提交验证码、账号可登录」，完成后回一句「已就绪」
   - 你就绪后 AI 做什么：从该登录态继续跑 T5 剩余断言和 T6，**不会让你重做一遍**

**人工介入项不另起编号**：每项必须挂在它服务的那条 T 用例上（写「拿到后跑 T7」而不是自成一套编号）；确实不对应任何自动化用例的纯人工确认项（如主观视觉与体验判断），**也要给一个 T 编号并进用例表**（类型写「人工」，预期判定写清"怎样算通过"），保证通过标准能逐项核对、报告里每条都有复现步骤。

#### 三条硬规则

1. **T 编号跨轮次稳定** — 生成前**先读同目录已有的 `N-TEST-REPORT.md`**（存在就读）：同一个验证点**沿用原编号**，新增的验证点接着历史最大编号往后排，**不复用已删编号**。否则产物文件名 `tests/T3-*` 和历史报告里的 T3 会指向两个不同的东西
2. **宽重构要加「阶段」列** — PLAN 的 `## 技术方案` 写了「走 expand-contract 三段」时，用例表加一列「阶段」，每条标 `全程必须绿`（回归基线，任何一批迁移后都得过）还是 `contract 后才跑`（迁移中间态本来就不该通过）。不标的话 7.6 每轮全量回归会把正常的中间状态判成失败，三轮上限直接撞满
3. **只展示不落 PLAN** — 在对话里展示完整用例表（**不等用户确认，展示完直接往下走**），最终随 7.8 写进 `N-TEST-REPORT.md`。**禁止回写 PLAN 的 `## 测试方案`**——PLAN 是计划书，报告才是执行记录

**PLAN 无 `## 测试方案` 章节（老计划）** → 环境命令自己扫代码推导，前置信息缺的走 7.2.1，照常生成用例表。**不因缺章节而中断，也不要求用户补计划。**

### 第四步：执行任务

根据 改动详情 中描述的具体改动：

1. **先跑一遍** — 看 3.5 步生成的用例表里挂在这条 todo 下面的 T 用例，**「先跑」列标了 `✅ 可先跑` 的，动手改代码之前先跑一次，确认它现在是跑不过的**。

   > 为什么多跑这一次：一条从来没失败过的用例最后通过了，你分不清是代码真做对了，还是这条用例压根没断到点子上。先看着它失败一次，后面它变绿才算数。

   **跑不跑以 3.5 标的为准，别自己重判**——`⏭️ 跳过` 的直接进第 2 小步，留到第七步统一跑。

   跑完看结果，三种情况：

   | 结果 | 怎么办 |
   |------|--------|
   | **跑不过**（断言失败、期望值对不上） | 正常往下写。第 3 小步改完再跑一遍看它通过，报告明细表那行「备注」写上 `改之前先跑过，当时是失败的` |
   | **居然通过了** | 这条用例的断言没断到点子上（恒真断言，说白了就是改不改代码它都能过、等于没测）→ **当场把用例改对，再动手写代码**，报告「修复记录」写清原来的断言错在哪。归 7.4 的「用例/环境问题」，**不动源码** |
   | **报的是环境错误**（连不上库、服务没起、端口不通、命令找不到、依赖缺失） | **这不算验证成功，也不算用例有问题** —— 环境自检在 7.2，那时候还没跑。**别改用例、别改源码**，跳过这次先跑，直接进第 2 小步，这条留给第七步。顺手在 3.5 那份方案里把该行的「先跑」列改成 `⏭️ 跳过（环境依赖：xxx）`，后面的 todo 就不白跑了 |

   两条限制：这次先跑**不算进** 7.5.1 的「同一用例最多修 3 次」；先跑的命令一样受 2 分钟挂起限制，超时就跳过、留给第七步。
2. 读取需要修改的现有文件
3. 按描述执行代码编写/修改
4. 确保改动符合 改动详情 的描述
5. **语法检查** — 改动完成后，用项目对应的方式快速验证语法：
   - Python: `python3 -c "import ast; ast.parse(open('文件路径').read())"`
   - JS/TS: 项目有 lint 命令则运行，否则检查文件是否有明显语法错误
   - 其他语言: 用对应编译器/解释器做语法级检查
   - 语法不通过 → **立即修复**，修复后再标记完成

### 第五步：标记完成

**获取当前时间：**

```bash
date "+%Y-%m-%d %H:%M:%S"
```

1. 将该条目的 `[ ]` 改为 `[x]`
2. 更新 N-PLAN.md 文件（使用 `phase.plan_file` 路径）：
   - 更新 `> 最后更新:` 为当前精确时间 `YYYY-MM-DD HH:mm:ss`
   - 在变更记录追加 `- YYYY-MM-DD HH:mm:ss 完成 #N 任务标题`
3. 刷新 STATE.md：

```bash
xz-tools.py update-state
```

### 第六步：循环或结束

检查是否还有下一个 `[ ]` 条目：

- **有** → 回到第四步继续执行
- **无** → 全部完成，**不要在这里收尾**，直接进入第七步闭环测试。代码写完 ≠ 做完，条目全 `[x]` 只代表改动落地，必须跑完闭环测试才允许输出下一步建议。

### 第七步：闭环测试与修复循环（全部条目完成后强制执行）

**目标**：AI 自己把本次改动完整跑一遍，出问题自己修、自己全量回归，直到全绿或触到上限停下报告。**只有客观做不到的事才停下来找人。**

#### 三类判据（完整定义在 3.5，这里只复述判定口径）

- **自动化用例** — 一条命令能跑出机器可判定的结果（单测、curl + 断言、CLI 比对、脚本、查库校验、`/claude-in-chrome` 驱动浏览器）→ **直接跑**
- **测试前置信息** — 能跑，只是缺参数（连接串、token、测试账号、环境变量、seed、本地依赖实例）→ **7.2 自检，缺就 7.2.1 一次性要，拿到就自动跑完**
- **人工介入项** — 客观做不到，只有四类：真实凭证密钥、线上或预发环境、破坏性操作、主观视觉确认 → **7.5 停下请人做**

**铁律**：`/claude-in-chrome` 能驱动的 UI 操作不算人工项；多端多人同时操作也不算（自己开多个标签页模拟）；「麻烦」「要起服务」「要造数据」都不算；**缺连接信息更不算**——那是前置信息，措辞是「给我参数我自己跑」而不是「这事你来做」。把能自动化的推给用户 = 违规。

#### 7.1 取测试方案

**用 3.5 步生成的那份用例表**，逐条执行。方案已经在 3.5 展示过，这里不重新生成、不重新展示。

第四步执行过程中如果动过 3.5 那份方案（如把某条的「先跑」列改成了 `⏭️ 跳过（环境依赖）`、发现某条 todo 的实现方式变了要调断言），**以改过的为准**，并在报告「修复记录」里留一行说明改了什么、为什么改。

#### 7.2 环境与前置信息自检

**先自己想办法，别急着问人。** 顺序：

1. **读 PLAN 的「测试前置信息」段**，列出本次要用到的连接与凭据 —— 标了 **✅ 已提供** 的直接用（值在 `tests/.env.local`），**禁止把用户在计划阶段已经给过的再问一遍**；只有标「⏳ 待定」的才可能要问。**3.5 生成的用例挂的 P 编号要跟这张表对得上**——用例挂了 P 表里没有的项，说明 3.5 漏了一项前置信息，补进本步的索取清单
2. **查 `.xz_planning/phases/N.xxx/tests/.env.local`** —— 已有对应项 → 注入环境变量，继续
3. **仍缺则自查代码**：`.env` / `.env.example` / `config/*` / `docker-compose.yml` / `Makefile` / `conftest.py` 及测试 fixture / `README` 本地开发章节 / 项目已有测试的连接配置
4. **检查命令与服务**：测试框架装没装、端口通不通、依赖服务起没起。**纯启动本项目的服务**（如 `npm run dev`、`go run main.go`）自己起；**要起外部依赖容器**（数据库/Redis/MQ）→ 不自作主张，转 7.2.1 让用户选
5. 自查后仍缺 → **转 7.2.1 一次性索取**；属于人工项范畴的（真实凭证/线上环境）→ 转 7.5

#### 7.2.1 前置信息缺失 → 停下索取（一次性）

**只问真缺的**：PLAN 里标「✅ 已提供」的项不许再问，本步只覆盖标「⏳ 待定」的和执行中新发现缺的。

与 7.5 的区别：这里是**"给我参数我自己跑"**，不是"这事你来做"。纯文本一次性问清，每项写四行 + 带选项：

```
以下 N 项信息缺了，测试跑不起来。给我之后我会全自动跑完，中途不再打扰你：

1. [P1] T4/T5 需要测试库连接
   要什么：MySQL DSN（host:port/库名 + 账号密码）
   为什么：这两条用例要写入 orders 表再查回来断言
   我找过：`.env` 无 DB_* 项、`docker-compose.yml` 只有 app 服务、`conftest.py` 无 fixture
   a. 直接贴 DSN 给我
   b. 告诉我在哪个文件哪个字段，我自己读
   c. 我用项目 docker-compose 起一个本地 MySQL（占 3307，跑完我清理）
   d. 跳过 → T4/T5 标「阻塞·缺信息」，不算通过也不算失败

回复如 `1a: mysql://...` 或 `1c`。
```

**「我找过」必须是真查过的文件，禁止编造。** 选 c（起本地依赖）时**先说清起什么、占哪个端口、跑完是否清理，用户点头才动手**。

#### 7.2.2 凭据落盘与隔离（强制四条）

1. 用户给的连接串/密码写进 `.xz_planning/phases/N.xxx/tests/.env.local`，文件头加 `# 本文件含明文凭据，勿提交`
2. **写之前先查项目 `.gitignore`**：未覆盖该路径 → 追加 `.xz_planning/**/tests/.env.local` 并在终端告知「已追加 .gitignore 规则」
3. **只有这一个文件能存明文**：`N-PLAN.md` / `N-TEST-REPORT.md` / 测试脚本一律只写引用（`DB_DSN：见 tests/.env.local`）、命令列脱敏（`mysql://root:***@localhost:3307/test`）、脚本读环境变量（`os.environ["DB_DSN"]`）**禁止硬编码**
4. 选 c 起的本地实例，连接信息同样写进 `.env.local`，并在报告「遗留与下一步」记一行：起了什么、占哪个端口、跑完是否已清理

#### 7.2.3 产物落地约定（跑之前先立规矩）

**先划清边界：`N-TEST-REPORT.md` 不是测试产物**，它和 `N-PLAN.md` 平级放在 phase 目录，**不进 `tests/`**。下面这条"平铺 tests/"的规矩只管脚本、截图、样本、日志：

```
.xz_planning/phases/N.中文名/
├── N-PLAN.md
├── N-TEST-REPORT.md          # ← 报告在这一层，与 PLAN 平级（详见 7.8）
└── tests/                    # ← 只放产物，报告不进来
    ├── .env.local            # 唯一存明文凭据的文件（规则见 7.2.2）
    ├── T1-req.json           # T1 的请求体
    ├── T1-resp.json          # T1 的实际响应（已脱敏）
    ├── T1-run.log            # T1 的运行输出
    ├── T3-run.sh             # T3 的可执行脚本（无测试框架时）
    ├── T3-01-登录页.png       # T3 第 1 张截图
```

本次测试的脚本、截图、样本、日志**一律平铺放 `tests/`，不建子目录**，靠文件名前缀区分归属：

1. **命名（硬要求）** —— `T{编号}-<用途>.<扩展名>`；**截图必须带两位序号**：`T8-01-活号列表.png` ✅ / `T8-active-list.png` ❌（缺序号看不出是第几步）
2. **禁止丢 `/tmp`** —— 临时目录会被清、重启即失，产物必须落在 `tests/` 里
3. **重跑覆盖，只留最新一轮** —— 历史失败现场以文字留在报告「修复记录」，不靠堆文件
4. **节制** —— 单条用例截图 ≤ 5 张；`run.log` 超 500 行只留头尾 + 关键片段并注明「已截断」
5. **脱敏（红线）** —— 产物里 token/密钥/手机号落盘前替换成 `***`，含凭据区域不截图，连接串写 `mysql://root:***@localhost:3307/test`；明文只允许在 `tests/.env.local`

**怎么手动重跑不另开文件**，统一写进 `N-TEST-REPORT.md` 的 `## 复现步骤` 段——每条用例一个代码块，见 7.8 模板。

#### 7.3 执行全部自动化用例

逐条真实执行，记录每条：通过 / 失败 / 阻塞 + 关键输出摘要（错误栈、状态码、断言差异）。

> **禁止伪造结果**：没有真实执行过的用例不许标记通过，禁止靠"代码看起来是对的"推断结论、禁止编造命令输出。

**边跑边落，不攒到最后补**：每条用例跑完**立即**做两件事，再跑下一条——

1. 产物按 `T{编号}-` 前缀写进 `tests/`（浏览器用例用 `/claude-in-chrome` 在关键节点**必须**截图存进去，这是 UI 结果唯一的可回看证据）

   **截图怎么落盘**：`computer` 的 `screenshot` / `zoom` 带上 **`save_to_disk: true`**，从返回结果里拿到磁盘路径，再把文件复制进 `tests/` 并重命名为 `T{编号}-NN-中文描述.png`。**只截图不落盘 = 没有证据**——报告产物列会指向不存在的文件
2. 在报告里补上该条的「用例执行明细」**表格行**和「复现步骤」`###` 小节，**把刚才真跑的那条命令原样贴进去**

**明细必须是表格的一行**：一条用例一行、七列齐全、结果列填 7.8 那五个 icon 之一。**禁止**写成 `## T1` 二级标题 + 无序列表的流水账——那样一眼看不出通过几条、失败几条，等于把总账拆散了。

事后统一补写等于凭记忆编现场，与 7.4.1 的即时可见性同理——**禁止**。

#### 7.4 失败分诊（三类，判错类别比修得快更重要）

| 类别 | 判断依据 | 处理 |
|------|----------|------|
| **实现 bug（计划内）** | 本次 todo 改的代码写错了：漏判空、逻辑反、参数传错、边界没处理 | **直接修源码**，修完进 7.6 全量回归 |
| **用例/环境问题** | 代码没问题，是测试命令写错、端口/路径不对、测试数据缺失、fixture 没准备 | 修用例或环境，**不动源码**，然后重跑 |
| **越界** | 修复需要新增功能/新建文件/改架构/动计划外模块，或根因在本次改动之外 | **不修**，记入待确认清单，进 7.7 |
| **触碰用户指定差异** | 修复方案会推翻 PLAN `## 约束` 里「已确认保留手动实现」的写法 | **不自行改**，停下来单独问：「这是你特意保留的写法，但 T3 失败根因在此，是否允许改？a. 允许改（推荐）b. 保留写法，我自己想办法 c. 忽略该用例」 |

> 最后一类是第七步里唯一**为了征求许可**而打断的情况——`## 约束` 里那行留痕是用户在 `/xz-manual` 校验闸门上明确拍过板的，AI 不能替他推翻自己刚做的决定。另一种打断是**走不下去了**（7.5 卡壳），性质不同：那不是征求许可，是真的没法往下走。

#### 7.4.1 改动可见性（每修一处即时打印，不等最后汇总）

修复源码时，**每改完一处就在终端打印一次**，然后才改下一处；禁止批量改完再统一说。格式：

```
🔧 修复 #1 ← T3 失败
   文件：src/auth/login.go:42-46
   原因：Timeout 赋值写在 Do() 之后，不生效
   改前：resp, err := client.Do(req)
   改后：client.Timeout = 5 * time.Second
         resp, err := client.Do(req)
```

同一内容汇总进 `N-TEST-REPORT.md` 的「修复记录」。**手动路径（`待闭环测试` 状态）跑闭环时一样适用**：用户不必盯着，但回头一定能看清 AI 动了哪儿、为什么动——尤其代码是他自己贴的，更得看得见。

**修复牵动命令就同步改**：修复让某条用例的命令/参数变了 → 同步改报告「复现步骤」里该条的代码块，**贴出来的必须是最后真正跑通的那条**；确属用例本身写错要改断言的 → 「用例执行明细」和「修复记录」**两处都要留痕**（原断言是什么、为什么错、改成了什么）。

#### 7.5 卡壳与人工介入 → 停下找人（防死磕的核心闸口）

**闭环 ≠ 无限自转。** 只要 AI 走不下去了，就必须停下来找人，禁止在原地反复试、反复改、反复跑指望它自己变绿——**卡壳不喊人、在原地空转，比打扰用户严重得多。**

**卡壳触发清单（任一命中即判定卡壳，立刻停止对该项的尝试）：**

| # | 触发情形 | 典型表现 |
|---|----------|----------|
| 1 | **预先声明的人工介入项** | PLAN 测试方案里已列出的（真实凭证/线上环境/破坏性操作/主观视觉确认） |
| 2 | **同一用例修 3 次仍失败** | 改了三次，同样的错误还在，或修完引出新的失败 |
| 3 | **根因说不清** | 代码和日志都读完了，仍解释不了为什么失败 |
| 4 | **信息不足，改法取决于用户意图** | 不知道正确预期值/业务规则/接口约定/数据该长什么样，怎么改都是猜 |
| 5 | **环境阻塞** | 依赖装不上、服务起不来、端口被占、权限不足、网络不通、外部服务不可达 |
| 6 | **需要人工手动操作到某一步** | 短信/邮箱验证码、扫码授权、第三方后台点某个按钮、人工造一批数据 |
| 7 | **命令挂起** | 单条用例执行**超过 2 分钟**无输出，或命令要求交互输入——判为卡壳，禁止干等 |
| 8 | **修复反复横跳** | 改 A 修好了但坏了 B，改回来又坏 A，来回抵消 |

**先跑完能跑的，再一次性问（不要遇到一个停一次）**：某项卡壳后，**先把与它无关、还能独立跑的用例全部跑完**，把所有卡壳项攒成一份清单，**一次性**纯文本提问（禁用 AskUserQuestion——其弹窗会吞掉同回复中前面的文本）。

**求助块格式（每项五行，缺一不可）：**

```
闭环测试卡住了，需要你介入。在你回复之前我不会继续改代码、不会继续跑这几项：

1. [卡壳·同一用例修 3 次仍失败] T3 登录接口返回 401
   现象：`curl -s -X POST localhost:8080/login -d '...'` 返回 401 {"err":"invalid_sign"}
   已尝试：① 按计划补了 sign 字段（第 1 次）② 核对密钥读取路径并改用 base64 编码（第 2 次）③ 改按参数名字典序拼接后再签（第 3 次），仍 401
   卡在哪：签名算法到底是 HMAC-SHA256 还是 MD5，代码里没写、文档里也没有，再改就是猜
   需要你：告诉我签名算法 + 一个示例签名串；或直接给我一条能通过的完整请求样本
   拿到后我做什么：改签名实现 → 重跑 T3 → 全量回归 T1-T6

2. [卡壳·需要人工操作到某一步] T5 注册流程要短信验证码
   现象：POST /register 后卡在待验证态，T5 后续断言跑不了
   已尝试：查过有无测试通道/万能码，`config/sms.yaml` 里只有生产通道
   卡在哪：验证码只会发到你的手机，我收不到
   需要你：手动把流程操作到「已提交验证码、注册完成」这一步，完成后回复「2 已就绪」
   拿到后我做什么：从注册完成后的登录态继续跑 T5 剩余断言和 T6，不重头开始

回复方式（可混着回）：
  · 直接给信息 —— 如 `1: HMAC-SHA256，示例 sign=abc123`
  · 回「N 已就绪」—— 你已手动操作到位，我从那个状态接着跑
  · 回「跳过 N」—— 该项本次不验证，报告标「未验证」，不算通过也不算失败
```

**用户回复后的处理：**

| 回复 | 处理 |
|------|------|
| **给了信息/参数** | 用它继续修或继续跑；该项计入修复轮次 |
| **「N 已就绪」** | **从人工操作后的状态接着跑该用例的剩余部分**，不重头来、不重复要求用户再操作一遍；跑之前先确认一下当前状态确实到位（如查一下登录态/数据是否已存在） |
| **「跳过 N」** | 明细表该行标 **`⏭️ 未验证`**，卡在哪 / 已尝试什么 / 需要用户做什么写进该行「备注」列，继续跑其余用例 |
| **用户给的信息仍不足以解决** | **不许自己接着猜**——再问一轮，明确说「按你给的 X 试过了，结果还是 Y，还差 Z」；同一项最多再问一轮，仍不通则明细表标 `❌ 失败`、备注写「未解决」，并进报告「遗留与下一步」 |

**卡壳项的「复现步骤」照样写全**：人工步骤用 `# ⚠️ 你手动做：` 注释标出，并写明**AI 从第几步续跑、前面哪几步不用重做**（这是用户下次自己复现时最需要的一行）；用户回「跳过」的标「未验证」，步骤也照写——他想自己跑时能直接照做。

#### 7.5.1 防死循环硬性护栏（违反即为违规）

| 护栏 | 上限 | 触到之后 |
|------|------|----------|
| 同一条用例的修复次数 | **3 次** | 判定卡壳，转 7.5 找人，禁止修第 4 次 |
| 全局修复-回归轮次 | **3 轮** | 停止修复，进 7.7 收敛报告 |
| 同一失败的重跑确认次数 | **2 次** | 确认不是偶发后立即分诊，禁止反复重跑指望它自己变绿 |
| 单条命令执行时长 | **2 分钟**（长任务按项目实际值，需在报告注明） | 判为挂起，中止该命令转 7.5，禁止干等 |
| 同一项的追问轮次 | **2 轮** | 仍不通则标「未解决」，写进报告「遗留与下一步」，不再纠缠 |

**禁止放水式通过（红线）**：不许为了让用例变绿而——改断言去迁就错误结果、删掉跑不过的用例、注释或绕过被测代码、把真实逻辑 mock 成永远成功、把失败降级成 warning。确实是用例本身写错了要改断言，**必须在报告的「修复记录」里写明：原断言是什么、为什么它是错的、改成了什么**，接受用户回头复查。

**停下就是真停**：进入 7.5 提问后，在用户回复前**不得**继续改源码、不得继续尝试该卡壳项。可以做的只有：把无关的用例跑完、整理清单。

#### 7.6 修复后全量回归（上限 3 轮）

每轮修完，**全量重跑所有自动化用例**，不能只跑失败的那几条——防止修 A 把 B 改坏。一轮 = 修复 + 全量回归。**最多 3 轮**，且每条用例最多修 3 次（见 7.5.1）。

**每轮结束打印一行进度**，让用户看得见还在往前走、没有空转：

```
🔄 第 2 轮回归：T1-T6 → 通过 5 / 失败 1（T3 仍 401，已修 3 次 → 判定卡壳，本轮结束后找你确认）
```

**回归跑完覆盖产物**：`tests/` 里的产物与报告结果更新为**最后一轮**的真实结果，不留上一轮的旧截图旧日志混淆视听。

#### 7.7 收敛判断

**结论词落在哪**：报告正文不再写整体结论（头部没有 `> 结论:` 行了），四种结论只落两处 —— **第八步终端输出的首行** + **PLAN 变更记录那一行**；报告里的逐条状态一律看「用例执行明细」的结果列 icon。

- **全绿**（自动化用例全通过，人工项已由用户确认，无阻塞项、无卡壳项）→ 进 7.8 写报告，结论词 **「全部通过」**
- **有阻塞项**（用户在 7.2.1 回了「跳过」，相关用例缺信息没跑）→ 结论词 **「部分阻塞」**（区别于「部分失败」——不是代码有问题，是没参数没跑成）；明细表这些行标 `⛔ 阻塞`、备注写缺什么，「遗留与下一步」写「补 `tests/.env.local` 后重跑 `/xz-exec N` 即可」
- **有卡壳项未解决**（7.5 问过、用户跳过或追问 2 轮仍不通）→ 结论词 **「待人工确认」**；明细表这些行标 `⏳ 待确认` 或 `⏭️ 未验证`，备注写清卡在哪、已尝试什么，「遗留与下一步」写还缺什么、用户提供后怎么继续
- **3 轮仍未全绿，或存在越界项** → **停下报告**，纯文本列出：剩余失败项 + 每项已尝试过的修复 + 建议下一步（越界项 → `/xz-update-plan N` 补条目；根因不清 → `/xz-debug` 定位）。报告照样写（结论词「部分失败」），不要静默结束

> **任何一种未全绿的收尾都必须落到"用户下一步能做什么"**：要么给出他补什么信息/做什么操作后重跑，要么给出该走哪个 skill。禁止只说"部分失败"就结束，那等于把死循环换了个形式甩给用户。

#### 7.8.1 报告结构硬约束（是契约不是参考，违反即为违规）

下面的模板**不是示例，是必须逐段照抄的结构**：

1. **四个 `##` 标题逐字固定、顺序固定**，一个不许少、不许改名、不许合并、不许自创：
   `## 用例执行明细` → `## 复现步骤` → `## 修复记录` → `## 遗留与下一步`
2. **必需段（缺任一 = 第七步未完成，不许进第八步）：**
   - `## 用例执行明细` —— **必须是 markdown 表格**，八列固定不许增删：`编号｜对应 todo｜类型｜命令｜预期判定｜结果｜产物｜备注`；**一条用例一行**，本次处理过的用例（含跳过、阻塞、人工确认项）**全部进表**，这是唯一总账。**禁止降级成 `## T1` + 列表**
     > **「预期判定」列不许省**：PLAN 里已经不存用例表了，这份报告是「当时到底期望什么」的唯一记录。少了这列，事后没法复核断言是否合理，也看不出某条用例是不是恒真断言。内容照抄 3.5 生成的用例表那一列
   - `## 复现步骤` —— 每条用例一个 `### T{编号} 标题` 小节 + 一个可执行代码块，贴真跑过的命令
3. **按需段无内容也保留标题**：`## 修复记录` 写「本次 0 轮修复」、`## 遗留与下一步` 写「无」。结构恒定才好逐项核对
4. **结果列固定五枚举，禁止自创写法**：`✅ 通过`｜`❌ 失败`｜`⏳ 待确认`｜`⛔ 阻塞`｜`⏭️ 未验证`
5. **判定红线 —— 禁止自作主张判通过**：
   - `✅ 通过` 只给**真跑过、且断言机器可判为真**的用例
   - **人工介入项（主观视觉、体验确认、需用户拍板的）在用户明确回复之前一律 `⏳ 待确认`**，禁止 AI 替用户判通过、禁止靠"截图看着没问题"标 ✅
   - 用户回「跳过 N」→ `⏭️ 未验证`；7.2.1 缺参数没跑成 → `⛔ 阻塞`。这两种**既不算通过也不算失败**，不许凑进通过数
6. **已废除的章节不许再写**：`> 结论:` 行、`## 结论摘要`、`## 卡壳与人工介入`、`## 阻塞项`、`## 测试产物` —— 这些信息已并入明细表的「结果 / 产物 / 备注」列和「遗留与下一步」，写了就是重复
