# XZ Exec - 执行版本计划

执行版本号: `$ARGUMENTS`

### 参数校验

如果 `$ARGUMENTS` 为空或不是合法版本号（正整数，或小数如 1.5），**立即停止**，提示：

> 缺少版本号。用法: `/xz-exec N`
> 示例: `/xz-exec 1`

## 辅助脚本

**脚本**：`xz-tools.py`

插件启用时 `bin/` 目录自动加入 PATH，直接作为命令调用即可（不需要 `python3` 前缀，也不需要绝对路径）。脚本在**当前工作目录**下操作 `.xz_planning/`。

---

## 执行流程

### 第一步：读取项目上下文

读取 `.xz_planning/PROJECT.md`（如果存在），了解项目技术栈和目录结构。

### 第二步：解析并读取计划

```bash
xz-tools.py parse $ARGUMENTS
```

- 从返回 JSON 中取 `phase.plan_file` 路径，读取 N-PLAN.md 完整内容
- 读取时不要只看 todolist，必须同时提取并理解这些章节（存在即读）：
  - `目标`
  - `上下文`
  - `约束`
  - `完成标准`
  - `技术方案`
  - `任务清单`
  - `测试方案`
- 版本不存在 → 提示用户先运行 `/xz-plan N`

**执行原则：**
- `N-PLAN.md` 是本次执行的主上下文来源
- 如果计划中记录了用户外部资料（如接口约束、字段含义、业务规则、固定文案），执行时必须遵守
- 禁止依赖"当前聊天里可能提过但计划里没写"的信息继续执行

#### 模式判断（读到 PLAN 后立即判断）

- **PLAN 头部 `> 状态: 待手动执行`** → 进入下方 **校验模式**（人工已手改源码，AI 先只读校验、确认后放行自动闭环）
- **其他状态**（`待执行` / `进行中` 等）→ 走 **常规执行模式**，进入第三步

### 校验模式（仅当状态为「待手动执行」）

该版本由 `/xz-plan` 的「手动执行」路径生成：用户已照 `N-MANUAL.md` 手动改完源码。当前 `N-MANUAL.md` 的默认格式是“修改已有文件统一使用 `========= v计划号 真实改动标题 before|start|end ===========`，新建文件给整文件，删除贴完整原文”；修改文件默认不再给整文件。

**手动执行路径的目的是让用户自己掌握代码写到哪儿了**——用户照 `N-MANUAL.md` 逐块贴码、心里有数，**不是"AI 永远不许碰代码"**。因此本模式分三段，闸门前后行为完全不同：

- **闸门前（校验比对）** — AI **只读不写**：一致/等价自动勾选不打扰，问题**只记录不动手**，保护手动成果不被静默覆盖
- **闸门（一次性确认）** — 汇总全部差异**一次问清**，同时拿到后续自动修复的授权
- **闸门后（闭环验证）** — 等同常规模式：全自动跑用例、修 bug、全量回归，不再逐处询问；每改一处即时打印，用户看得见

对齐方向是**文档跟代码走**：手动实现等价但风格不同时，改 PLAN/MANUAL 去贴合手动代码，而不是反过来。

逐条读 任务清单 的 改动详情，用 Read 检查对应文件的实际改动，按一致程度分级：

| 审核结论 | 处理方式 |
|------|------|
| **完全一致** — 代码已按 改动详情 改好 | 勾选 `[x]`，变更记录标「校验通过 #N」 |
| **轻微差异** — 语义达成、功能等价（变量名/注释/格式/等价写法不同，常见为用户自己的代码风格） | **保持手动现状不变**，照常勾选 `[x]`；**同步对齐文档**：把 N-PLAN.md 该条 改动详情 和 N-MANUAL.md 对应改动块改写为手动实际实现；变更记录标「#N 手动实现，与计划等价，已对齐 PLAN/MANUAL（差异: …）」 |
| **严重错误 / 未落地** — 漏改、改错文件或位置、复制粘贴出错导致功能不符 | **不修改、不勾选**，记入「待确认清单」：问题描述 + 现状代码摘要 + 计划预期 |
| **无法判断** — 改动详情 与代码模糊到无法对照 | 同样记入「待确认清单」，注明判断不了的点 |

**待确认清单 → 闸门：一次性确认（核心约束）：**

全部条目审完后，待确认清单**非空**则编号列出所有问题点，**一次性**找用户确认。**默认一律对齐原计划**——每项 `a` 固定为「按计划修正」，用户只需要挑出自己想保留的差异：

```markdown
以下 N 处与计划不一致，确认后我会按你的选择处理，然后直接进入全自动闭环验证：

1. #3 `src/auth/login.go` 超时未生效 — 手动只加了 Timeout 但写在 Do() 之后
   a. 按计划修正（推荐，与原计划对齐）  b. 保持现状并勾选（记为你指定的差异）  c. 跳过，我自己再改
2. #5 `src/util/retry.go` 未创建 — 文件不存在
   a. 按计划补建（推荐，与原计划对齐）  b. 跳过，我自己补

回复如 `1a 2b`，或 `全部默认`（= 全部按计划修正）。
确认后我会：补齐差异 → 跑测试用例 → 发现 bug 自行修复并全量回归，每改一处会在终端打印 文件:行号 + 改前/改后，最后出 N-TEST-REPORT.md。
```

**纯文本提问（禁用 AskUserQuestion——其弹窗会吞掉同回复中前面的清单文本）**：清单末尾必须带上上面那两行（`全部默认` 的含义 + 确认后会自动做什么），让用户知道这是**唯一一次打断**。

用户选定后才执行：

- 选「按计划修正」→ AI 改完做语法检查再勾选，变更记录标「#N 经用户确认按计划修正」
- 选「保持现状」→ 不动代码直接勾选，**并把 N-PLAN.md 改动详情 与 N-MANUAL.md 对应块改写为手动实际实现**，标「#N 经用户确认保留手动实现，已对齐 PLAN/MANUAL」；**同时记入 PLAN 的 `## 约束`**（见下方「用户指定差异」）
- 选「跳过」→ 不动不勾，标「#N 待用户手动处理」

**用户指定差异（必须落地，防止闭环验证把它改回去）：**

凡最终结论为「等价保留」或用户明确选了「保持现状」的条目，除了文档对齐外，还要在 N-PLAN.md 的 `## 约束` 追加一行留痕：

```
已确认保留手动实现：#3 `src/auth/login.go` 用早退代替嵌套 if（与计划写法不同，功能等价）。后续修复不得改回计划写法。
```

**校验模式其他规则：**
- 问题点**禁止边审边改**，必须汇总到闸门一次性确认
- **文档对齐代码**：「等价保留」「确认保留手动实现」的条目，按实际代码改写 N-PLAN.md 的 改动详情（行号/现状摘要/改动点）和 N-MANUAL.md 对应块（格式沿用 `/xz-plan` 的 MANUAL 规则，只回写实际改动块，不把未改方法整段带回），做到 **源码 = PLAN = MANUAL 三者一致，且源码一行不动**
- 每条处理后更新 `> 最后更新:` 与变更记录
- 全部处理完成后，把 PLAN 头部 `> 状态:` 从 `待手动执行` 回写为 `进行中`（仍有未完成）或交由 update-state 反映完成度，刷新 STATE.md（`xz-tools.py update-state`），并输出汇总：**校验通过 X 条 / 等价保留 Y 条 / 经确认修正 Z 条 / 跳过待手动 W 条**，列出每条结论。

**闸门后的走向（校验模式专用，不走第六步的循环判断）：**

| 状态 | 走向 |
|------|------|
| **条目全部勾选** | **直接进第七步闭环验证**——人工手改的代码一样要跑通，不能只对照文本就算完；此时已拿到闸门授权，全自动跑用例、修 bug、全量回归，不再逐处询问 |
| **有「跳过，我自己改」的条目** | **停在这里出报告**，列出待用户处理的条目清单，提示「处理完重新跑 `/xz-exec N`」；不进第七步 |

**硬规则**：校验模式下**严禁回第四步**替用户自动实现未勾选的条目——那正是用户明确要自己动手的部分，抢着做等于毁掉手动路径的意义。

### 第三步：评估当前状态

检查 todolist 中已完成（`[x]`）和未完成（`[ ]`）的条目，找到第一个未完成条目。

- **没有未完成条目** → 提示全部完成，建议运行 `/xz-done N`
- **有已完成条目 + 有未完成条目（中途接手）** → 进入接续评估（见下方）
- **全部未完成（从头开始）** → 直接进入第四步执行

#### 接续评估（中途接手时必须执行）

上一个 AI 可能已经执行了部分任务，当前代码状态未必和计划完全吻合。必须先评估再继续：

1. **读取最近已完成条目的 改动详情** — 了解上一步应该做了什么
2. **检查实际代码** — 用 Read 工具查看这些条目涉及的文件，确认改动是否真的落地
3. **判断偏差程度：**

| 情况 | 操作 |
|------|------|
| 已完成条目的改动已正确落地，代码与 改动详情 一致 | 正常继续，进入第四步 |
| 有小幅偏差但不影响后续任务（如变量名略不同、多了注释） | 记录偏差，适配后续执行，进入第四步 |
| 已完成条目的改动未落地（标了完成但代码没改） | **停下来报告用户**，文本列出未执行条目并提问：「以下条目标记完成但实际未执行: {列表}。回复 1) 重新执行这些条目 2) 跳过继续后续」 |
| 已完成的改动与 改动详情 偏差较大（用了不同方案、改了不同文件、结构重组） | **停下来报告用户**，文本列出具体偏差点并提问：「已完成改动与计划偏差较大: {偏差点摘要}。回复 1) 回退重做—按原计划执行 2) 基于现状调整—/xz-update-plan N」 |

### 第四步：执行任务

根据 改动详情 中描述的具体改动：

1. 读取需要修改的现有文件
2. 按描述执行代码编写/修改
3. 确保改动符合 改动详情 的描述
4. **语法检查** — 改动完成后，用项目对应的方式快速验证语法：
   - Python: `python3 -c "import ast; ast.parse(open('文件路径').read())"`
   - JS/TS: 项目有 lint 命令则运行，否则检查文件是否有明显语法错误
   - 其他语言: 用对应编译器/解释器做语法级检查
   - 语法不通过 → **立即修复**，修复后再标记完成

### 第五步：标记完成

**获取当前时间：**

```bash
date "+%Y-%m-%d %H:%M:%S"
```

1. 将该条目的 `[ ]` 改为 `[x]`
2. 更新 N-PLAN.md 文件（使用 `phase.plan_file` 路径）：
   - 更新 `> 最后更新:` 为当前精确时间 `YYYY-MM-DD HH:mm:ss`
   - 在变更记录追加 `- YYYY-MM-DD HH:mm:ss 完成 #N 任务标题`
3. 刷新 STATE.md：

```bash
xz-tools.py update-state
```

### 第六步：循环或结束

检查是否还有下一个 `[ ]` 条目：

- **有** → 回到第四步继续执行
- **无** → 全部完成，**不要在这里收尾**，直接进入第七步闭环测试。代码写完 ≠ 做完，条目全 `[x]` 只代表改动落地，必须跑完闭环测试才允许输出下一步建议。

### 第七步：闭环测试与修复循环（全部条目完成后强制执行）

**目标**：AI 自己把本次改动完整跑一遍，出问题自己修、自己全量回归，直到全绿或触到上限停下报告。**只有客观做不到的事才停下来找人。**

#### 三类判据（什么自己跑、什么要参数、什么必须找人）

| 类别 | 判据 | 处理 |
|------|------|------|
| **自动化用例** | 一条命令跑出**机器可判定结果**：单测/集成测试、接口 curl + 断言、CLI 输出比对、脚本、数据库查询校验、浏览器操作（**用 `xz-cdp-cli` skill 驱动 Chrome**） | 直接跑 |
| **测试前置信息** | AI **能跑，只是缺参数**：DB/Redis/MQ 连接串、API base URL + token、测试账号、环境变量、seed 来源、本地依赖实例 | 7.2 自检 → 缺则 7.2.1 一次性索取，拿到即自动跑完 |
| **人工介入项** | AI **客观做不到**，仅限：真实凭证/密钥/第三方账号、线上或预发环境、真机硬件、多端多人同时操作、破坏性操作、业务方主观视觉确认 | 7.5 停下请人做 |

**判定铁律**：`xz-cdp-cli` 能驱动完成的 UI 操作**不算**人工项；「麻烦」「要起服务」「要造测试数据」**不算**——AI 自己起、自己造；**缺连接信息 ≠ 人工介入项**，那是前置信息，措辞是「给我参数我自己跑」而不是「这事你来做」；把能自动化的推给用户 = 违规。

#### 7.1 取测试方案

读 PLAN 的 `## 测试方案`：

- **有该章节** → 按其中的「自动化用例」表逐条执行
- **无该章节**（老计划）→ 按 `/xz-plan` 4.5 的五段模板（测试环境与命令 / 测试前置信息 / 自动化用例 / 人工介入项 / 通过标准）现场推导一份，先在对话中展示，然后照跑。**不因缺章节而中断，也不要求用户补计划**

#### 7.2 环境与前置信息自检

**先自己想办法，别急着问人。** 顺序：

1. **读 PLAN 的「测试前置信息」段**，列出本次要用到的连接与凭据
2. **查 `.xz_planning/phases/N.xxx/tests/.env.local`** —— 已有对应项 → 注入环境变量，继续
3. **仍缺则自查代码**：`.env` / `.env.example` / `config/*` / `docker-compose.yml` / `Makefile` / `conftest.py` 及测试 fixture / `README` 本地开发章节 / 项目已有测试的连接配置
4. **检查命令与服务**：测试框架装没装、端口通不通、依赖服务起没起。**纯启动本项目的服务**（如 `npm run dev`、`go run main.go`）自己起；**要起外部依赖容器**（数据库/Redis/MQ）→ 不自作主张，转 7.2.1 让用户选
5. 自查后仍缺 → **转 7.2.1 一次性索取**；属于人工项范畴的（真实凭证/线上/真机）→ 转 7.5

#### 7.2.1 前置信息缺失 → 停下索取（一次性）

与 7.5 的区别：这里是**"给我参数我自己跑"**，不是"这事你来做"。纯文本一次性问清，每项写四行 + 带选项：

```
以下 N 项信息缺了，测试跑不起来。给我之后我会全自动跑完，中途不再打扰你：

1. [P1] T4/T5 需要测试库连接
   要什么：MySQL DSN（host:port/库名 + 账号密码）
   为什么：这两条用例要写入 orders 表再查回来断言
   我找过：`.env` 无 DB_* 项、`docker-compose.yml` 只有 app 服务、`conftest.py` 无 fixture
   a. 直接贴 DSN 给我
   b. 告诉我在哪个文件哪个字段，我自己读
   c. 我用项目 docker-compose 起一个本地 MySQL（占 3307，跑完我清理）
   d. 跳过 → T4/T5 标「阻塞·缺信息」，不算通过也不算失败

回复如 `1a: mysql://...` 或 `1c`。
```

**「我找过」必须是真查过的文件，禁止编造。** 选 c（起本地依赖）时**先说清起什么、占哪个端口、跑完是否清理，用户点头才动手**。

#### 7.2.2 凭据落盘与隔离（强制四条）

1. 用户给的连接串/密码写进 `.xz_planning/phases/N.xxx/tests/.env.local`，文件头加 `# 本文件含明文凭据，勿提交`
2. **写之前先查项目 `.gitignore`**：未覆盖该路径 → 追加 `.xz_planning/**/tests/.env.local` 并在终端告知「已追加 .gitignore 规则」
3. **只有这一个文件能存明文**：`N-PLAN.md` / `N-TEST-REPORT.md` / 测试脚本一律只写引用（`DB_DSN：见 tests/.env.local`）、命令列脱敏（`mysql://root:***@localhost:3307/test`）、脚本读环境变量（`os.environ["DB_DSN"]`）**禁止硬编码**
4. 选 c 起的本地实例，连接信息同样写进 `.env.local`，并在报告「测试产物」记一行：起了什么、占哪个端口、跑完是否已清理

#### 7.2.3 产物落地约定（跑之前先立规矩）

本次测试的脚本、截图、样本、日志**一律平铺放 `.xz_planning/phases/N.中文名/tests/`，不建子目录**，靠文件名前缀区分归属：

```
tests/
├── .env.local            # 唯一存明文凭据的文件（规则见 7.2.2）
├── T1-req.json           # T1 的请求体
├── T1-resp.json          # T1 的实际响应（已脱敏）
├── T1-run.log            # T1 的运行输出
├── T3-run.sh             # T3 的可执行脚本（无测试框架时）
├── T3-01-登录页.png       # T3 第 1 张截图
└── T3-02-登录成功.png
```

1. **命名** —— `T{编号}-<用途>.<扩展名>`，截图再带两位序号，一眼看出属于哪条用例、第几步
2. **禁止丢 `/tmp`** —— 临时目录会被清、重启即失，产物必须落在 `tests/` 里
3. **重跑覆盖，只留最新一轮** —— 历史失败现场以文字留在报告「修复记录」，不靠堆文件
4. **节制** —— 单条用例截图 ≤ 5 张；`run.log` 超 500 行只留头尾 + 关键片段并注明「已截断」
5. **脱敏（红线）** —— 产物里 token/密钥/手机号落盘前替换成 `***`，含凭据区域不截图，连接串写 `mysql://root:***@localhost:3307/test`；明文只允许在 `tests/.env.local`

**怎么手动重跑不另开文件**，统一写进 `N-TEST-REPORT.md` 的 `## 复现步骤` 段——每条用例一个代码块，见 7.8 模板。

#### 7.3 执行全部自动化用例

逐条真实执行，记录每条：通过 / 失败 / 阻塞 + 关键输出摘要（错误栈、状态码、断言差异）。

> **禁止伪造结果**：没有真实执行过的用例不许标记通过，禁止靠"代码看起来是对的"推断结论、禁止编造命令输出。

**边跑边落，不攒到最后补**：每条用例跑完**立即**做两件事，再跑下一条——

1. 产物按 `T{编号}-` 前缀写进 `tests/`（浏览器用例用 `xz-cdp-cli` 在关键节点**必须**截图存进去，这是 UI 结果唯一的可回看证据）
2. 在报告里补上该条的「用例执行明细」行和「复现步骤」小节，**把刚才真跑的那条命令原样贴进去**

事后统一补写等于凭记忆编现场，与 7.4.1 的即时可见性同理——**禁止**。

#### 7.4 失败分诊（三类，判错类别比修得快更重要）

| 类别 | 判断依据 | 处理 |
|------|----------|------|
| **实现 bug（计划内）** | 本次 todo 改的代码写错了：漏判空、逻辑反、参数传错、边界没处理 | **直接修源码**，修完进 7.6 全量回归 |
| **用例/环境问题** | 代码没问题，是测试命令写错、端口/路径不对、测试数据缺失、fixture 没准备 | 修用例或环境，**不动源码**，然后重跑 |
| **越界** | 修复需要新增功能/新建文件/改架构/动计划外模块，或根因在本次改动之外 | **不修**，记入待确认清单，进 7.7 |
| **触碰用户指定差异** | 修复方案会推翻 PLAN `## 约束` 里「已确认保留手动实现」的写法 | **不自行改**，停下来单独问：「这是你特意保留的写法，但 T3 失败根因在此，是否允许改？a. 允许改（推荐）b. 保留写法，我自己想办法 c. 忽略该用例」 |

> 最后一类是闸门后唯一**为了征求许可**而打断的情况——它与用户先前的明确决定冲突，AI 不能替用户推翻自己刚做的决定。另一种打断是**走不下去了**（7.5 卡壳），**不受闸门影响**：闸门授权的是"可以自主改代码"，不是"必须一个人硬扛到底"。

#### 7.4.1 改动可见性（每修一处即时打印，不等最后汇总）

修复源码时，**每改完一处就在终端打印一次**，然后才改下一处；禁止批量改完再统一说。格式：

```
🔧 修复 #1 ← T3 失败
   文件：src/auth/login.go:42-46
   原因：Timeout 赋值写在 Do() 之后，不生效
   改前：resp, err := client.Do(req)
   改后：client.Timeout = 5 * time.Second
         resp, err := client.Do(req)
```

同一内容汇总进 `N-TEST-REPORT.md` 的「修复记录」。这条对**常规模式和校验模式同样适用**：用户不必盯着，但回头一定能看清 AI 动了哪儿、为什么动。

**修复牵动命令就同步改**：修复让某条用例的命令/参数变了 → 同步改报告「复现步骤」里该条的代码块，**贴出来的必须是最后真正跑通的那条**；确属用例本身写错要改断言的 → 「用例执行明细」和「修复记录」**两处都要留痕**（原断言是什么、为什么错、改成了什么）。

#### 7.5 卡壳与人工介入 → 停下找人（防死磕的核心闸口）

**闭环 ≠ 无限自转。** 只要 AI 走不下去了，就必须停下来找人，禁止在原地反复试、反复改、反复跑指望它自己变绿——**卡壳不喊人、在原地空转，比打扰用户严重得多。**

**卡壳触发清单（任一命中即判定卡壳，立刻停止对该项的尝试）：**

| # | 触发情形 | 典型表现 |
|---|----------|----------|
| 1 | **预先声明的人工介入项** | PLAN 测试方案里已列出的（真实凭证/线上环境/真机硬件/多端多人/破坏性操作/主观视觉确认） |
| 2 | **同一用例修 3 次仍失败** | 改了三次，同样的错误还在，或修完引出新的失败 |
| 3 | **根因说不清** | 代码和日志都读完了，仍解释不了为什么失败 |
| 4 | **信息不足，改法取决于用户意图** | 不知道正确预期值/业务规则/接口约定/数据该长什么样，怎么改都是猜 |
| 5 | **环境阻塞** | 依赖装不上、服务起不来、端口被占、权限不足、网络不通、外部服务不可达 |
| 6 | **需要人工手动操作到某一步** | 短信/邮箱验证码、扫码授权、真机连接、后台点某个按钮、人工造一批数据 |
| 7 | **命令挂起** | 单条用例执行**超过 2 分钟**无输出，或命令要求交互输入——判为卡壳，禁止干等 |
| 8 | **修复反复横跳** | 改 A 修好了但坏了 B，改回来又坏 A，来回抵消 |

**先跑完能跑的，再一次性问（不要遇到一个停一次）**：某项卡壳后，**先把与它无关、还能独立跑的用例全部跑完**，把所有卡壳项攒成一份清单，**一次性**纯文本提问（禁用 AskUserQuestion——其弹窗会吞掉同回复中前面的文本）。

**求助块格式（每项五行，缺一不可）：**

```
闭环测试卡住了，需要你介入。在你回复之前我不会继续改代码、不会继续跑这几项：

1. [卡壳·同一用例修 3 次仍失败] T3 登录接口返回 401
   现象：`curl -s -X POST localhost:8080/login -d '...'` 返回 401 {"err":"invalid_sign"}
   已尝试：① 按计划补了 sign 字段（第 1 次）② 核对密钥读取路径并改用 base64 编码（第 2 次）③ 改按参数名字典序拼接后再签（第 3 次），仍 401
   卡在哪：签名算法到底是 HMAC-SHA256 还是 MD5，代码里没写、文档里也没有，再改就是猜
   需要你：告诉我签名算法 + 一个示例签名串；或直接给我一条能通过的完整请求样本
   拿到后我做什么：改签名实现 → 重跑 T3 → 全量回归 T1-T6

2. [卡壳·需要人工操作到某一步] T5 注册流程要短信验证码
   现象：POST /register 后卡在待验证态，T5 后续断言跑不了
   已尝试：查过有无测试通道/万能码，`config/sms.yaml` 里只有生产通道
   卡在哪：验证码只会发到你的手机，我收不到
   需要你：手动把流程操作到「已提交验证码、注册完成」这一步，完成后回复「2 已就绪」
   拿到后我做什么：从注册完成后的登录态继续跑 T5 剩余断言和 T6，不重头开始

回复方式（可混着回）：
  · 直接给信息 —— 如 `1: HMAC-SHA256，示例 sign=abc123`
  · 回「N 已就绪」—— 你已手动操作到位，我从那个状态接着跑
  · 回「跳过 N」—— 该项本次不验证，报告标「未验证」，不算通过也不算失败
```

**用户回复后的处理：**

| 回复 | 处理 |
|------|------|
| **给了信息/参数** | 用它继续修或继续跑；该项计入修复轮次 |
| **「N 已就绪」** | **从人工操作后的状态接着跑该用例的剩余部分**，不重头来、不重复要求用户再操作一遍；跑之前先确认一下当前状态确实到位（如查一下登录态/数据是否已存在） |
| **「跳过 N」** | 标记为**未验证**，写进报告的「卡壳与人工介入」段，继续跑其余用例 |
| **用户给的信息仍不足以解决** | **不许自己接着猜**——再问一轮，明确说「按你给的 X 试过了，结果还是 Y，还差 Z」；同一项最多再问一轮，仍不通则标「未解决」写进报告遗留问题 |

**卡壳项的「复现步骤」照样写全**：人工步骤用 `# ⚠️ 你手动做：` 注释标出，并写明**AI 从第几步续跑、前面哪几步不用重做**（这是用户下次自己复现时最需要的一行）；用户回「跳过」的标「未验证」，步骤也照写——他想自己跑时能直接照做。

#### 7.5.1 防死循环硬性护栏（违反即为违规）

| 护栏 | 上限 | 触到之后 |
|------|------|----------|
| 同一条用例的修复次数 | **3 次** | 判定卡壳，转 7.5 找人，禁止修第 4 次 |
| 全局修复-回归轮次 | **3 轮** | 停止修复，进 7.7 收敛报告 |
| 同一失败的重跑确认次数 | **2 次** | 确认不是偶发后立即分诊，禁止反复重跑指望它自己变绿 |
| 单条命令执行时长 | **2 分钟**（长任务按项目实际值，需在报告注明） | 判为挂起，中止该命令转 7.5，禁止干等 |
| 同一项的追问轮次 | **2 轮** | 仍不通则标「未解决」，写进报告遗留问题，不再纠缠 |

**禁止放水式通过（红线）**：不许为了让用例变绿而——改断言去迁就错误结果、删掉跑不过的用例、注释或绕过被测代码、把真实逻辑 mock 成永远成功、把失败降级成 warning。确实是用例本身写错了要改断言，**必须在报告的「修复记录」里写明：原断言是什么、为什么它是错的、改成了什么**，接受用户回头复查。

**停下就是真停**：进入 7.5 提问后，在用户回复前**不得**继续改源码、不得继续尝试该卡壳项。可以做的只有：把无关的用例跑完、整理清单。

#### 7.6 修复后全量回归（上限 3 轮）

每轮修完，**全量重跑所有自动化用例**，不能只跑失败的那几条——防止修 A 把 B 改坏。一轮 = 修复 + 全量回归。**最多 3 轮**，且每条用例最多修 3 次（见 7.5.1）。

**每轮结束打印一行进度**，让用户看得见还在往前走、没有空转：

```
🔄 第 2 轮回归：T1-T6 → 通过 5 / 失败 1（T3 仍 401，已修 3 次 → 判定卡壳，本轮结束后找你确认）
```

**回归跑完覆盖产物**：`tests/` 里的产物与报告结果更新为**最后一轮**的真实结果，不留上一轮的旧截图旧日志混淆视听。

#### 7.7 收敛判断

- **全绿**（自动化用例全通过，人工项已确认或用户明确跳过，无阻塞项、无卡壳项）→ 进 7.8 写报告
- **有阻塞项**（用户在 7.2.1 回了「跳过」，相关用例缺信息没跑）→ 结论标 **「部分阻塞」**（区别于「部分失败」——不是代码有问题，是没参数没跑成），报告列出缺什么、影响哪几条用例，并提示「补 `tests/.env.local` 后重跑 `/xz-exec N` 即可」
- **有卡壳项未解决**（7.5 问过、用户跳过或追问 2 轮仍不通）→ 结论标 **「待人工确认」**，报告的「卡壳与人工介入」段逐项写清：卡在哪、已尝试什么、还缺什么、用户提供后怎么继续
- **3 轮仍未全绿，或存在越界项** → **停下报告**，纯文本列出：剩余失败项 + 每项已尝试过的修复 + 建议下一步（越界项 → `/xz-update-plan N` 补条目；根因不清 → `/xz-debug` 定位）。报告照样写（结论标「部分失败」），不要静默结束

> **任何一种未全绿的收尾都必须落到"用户下一步能做什么"**：要么给出他补什么信息/做什么操作后重跑，要么给出该走哪个 skill。禁止只说"部分失败"就结束，那等于把死循环换了个形式甩给用户。

#### 7.8 产出

1. **写 `N-TEST-REPORT.md`** — 放在 PLAN 同目录（`phase.plan_file` 的所在目录），格式见下方模板；已存在则**覆盖为最新一轮结果**，并在文件内保留历史轮次记录
2. **PLAN 变更记录追加一行** — `- YYYY-MM-DD HH:mm:ss 闭环测试: 通过 X/Y，修复 K 轮`，同时更新 `> 最后更新:`
3. **刷新 STATE.md** — `xz-tools.py update-state`

**测试脚本落地规则**：

- **项目已有测试框架** → 测试代码**写进项目正式测试目录**（如 `tests/`、`*_test.go`），走项目自己的 fixture 与 CI，`.xz_planning/.../tests/` 只留跑不进框架的东西（截图、样本、日志）；报告「复现步骤」里写明代码位置 + 运行命令

4. **更新进度** — 每完成一条都更新 PLAN.md 和 STATE.md；全部完成后输出本次改动点汇总
5. **只做计划内的事** — 严禁做 改动详情 之外的改动，即使觉得"顺手改了更好"也不行；发现计划有遗漏，停下来告知用户，由用户决定是否通过 `/xz-update-plan` 补充。**唯一例外**：第七步修复「计划内实现 bug」（本次 todo 改的代码写错了）不算越界，可直接修；但只要修复需要新增功能/新建文件/改架构/动计划外模块，仍必须停下报告
6. **遇阻与卡壳一律停下找人，禁止死磕** — 执行期：改动详情与实际文件不符、依赖缺失、指令含糊到无法确定改什么 → 先回读 PLAN 的 `## 目标`/`## 上下文` 消歧义，仍不清楚立即停下报告，**禁止猜测或自行创造解法**。测试期：判据与求助格式见 7.5（八条触发情形、每项五行）——**先把无关用例跑完再攒成一份清单一次性问**，提问后到用户回复前**真停**（不改源码、不再试该项）；用户回「已就绪」→ **从人工操作后的状态接着跑，不重头、不让人重做一遍**；信息仍不够最多再问一轮，仍不通标「未解决」写进遗留问题。浏览器 UI 一律用 `xz-cdp-cli` 自跑，「麻烦」「要起服务」「要造数据」不是找人的理由
7. **语法必须通过** — 每条任务执行后做语法检查，不通过不标完成
8. **中途接手先评估** — 有已完成条目时，先检查实际代码与 改动详情 的一致性，偏差大则报告用户等决定
9. **闭环测试不通过不算完成，未全绿也要给出口** — todolist 全 `[x]` 只代表代码写完，必须走完第七步才允许输出 `/xz-done` 等建议（常规模式和校验模式都要跑）；任何非全绿收尾（部分失败 / 部分阻塞 / 待人工确认）都必须落到"用户下一步能做什么"——补哪个信息、做哪步操作后重跑 `/xz-exec N`，或该走 `/xz-update-plan`、`/xz-debug`，**禁止只丢一句"部分失败"就结束**
10. **测试结果必须真实，禁止伪造与放水** — 每条用例真跑过才能标结果，禁止靠读代码推断通过、禁止编造命令输出；跑不了的如实标「阻塞」或转人工介入项。**更禁止为了变绿而**改断言迁就错误结果、删跑不过的用例、注释或绕过被测代码、把真实逻辑 mock 成永远成功、把失败降级成 warning；确属用例写错要改断言的，必须在报告「修复记录」写明原断言是什么、为什么错、改成了什么
11. **回归必须全量、护栏硬性** — 每轮修完重跑**全部**用例而不是只跑失败项（防修 A 坏 B）；护栏是硬的：同一用例最多修 **3 次**、全局最多 **3 轮**、同一失败最多重跑确认 **2 次**、单条命令超 **2 分钟**判挂起、同一项最多追问 **2 轮**。触到任一上限立刻转 7.5 找人或进 7.7 收敛，**禁止无限循环硬磕**
12. **缺信息先自查再索取、凭据只存一处** — 跑用例缺的连接/凭据属于「测试前置信息」而非人工介入项——给了参数 AI 自己跑完。按 7.2 先查 `tests/.env.local` 和 `.env`/`config`/`docker-compose.yml`/fixture/README，**找得到的不问**；仍缺才按 7.2.1 一次性索取（「我找过」禁编造）。**起外部依赖容器必须先告知端口与清理方式、用户点头才起**；本项目自身的服务自己起。凭据只写 `tests/.env.local`（头部标注勿提交 + 先确保 `.gitignore` 覆盖），**PLAN/报告/脚本一律只写引用、命令脱敏、脚本读环境变量禁硬编码**；用户跳过的项标「阻塞·缺信息」，结论用「部分阻塞」而非「部分失败」
13. **改动可见性** — 每修一处源码就在终端即时打印「文件:行号 + 原因 + 改前/改后」（格式见 7.4.1），改完一处再改下一处，禁止批量改完才统一汇报；同一内容进报告「修复记录」。常规模式与校验模式一致
14. **产物平铺 `tests/`、报告必须可复现** — 脚本/截图/样本/日志一律平铺放 `.xz_planning/phases/N.xxx/tests/`，**不建子目录**，文件名带 `T{编号}-` 前缀区分归属，**禁止丢 `/tmp`**；重跑覆盖只留最新一轮，截图 ≤ 5 张/条、日志超 500 行截断；**每条用例（含跳过项、未验证项）在报告 `## 复现步骤` 里都有一个代码块**，贴真实跑过的命令（cwd = 项目根、复制即可执行），人工步骤用 `# ⚠️ 你手动做：` 标出并写明 AI 从第几步续跑。**红线：产物与报告禁止出现明文凭据**，token/密钥/手机号落盘前替换成 `***`、含凭据区域不截图、连接串脱敏，明文只存 `tests/.env.local`
15. **校验模式 = 闸门制，不是禁区** — PLAN 头部 `状态: 待手动执行` 时进入校验模式，目的是让用户掌握代码写到哪儿了，**不是 AI 永不碰代码**：**闸门前**只读比对（一致/等价直接勾选，问题只记录不动手）→ **闸门**是唯一一次打断（编号清单，每项 `a` 固定为「按计划修正」，`全部默认` = 全部对齐原计划）→ **闸门后**等同常规模式全自动跑闭环，不再逐处询问。等价/确认保留的条目**文档对齐代码**：同步改 N-PLAN.md 与 N-MANUAL.md 贴合手动实现，MANUAL 只回写实际改动块、不带回未改方法整段
16. **用户的手动成果受保护** — 闸门处选「保持现状」的写法必须写进 PLAN `## 约束` 留痕，闭环修 bug 时**不得推翻**，若失败根因正是该差异，停下来单独问（闸门后唯一的征求许可）；选「跳过，我自己改」的条目保持 `[ ]` 不动，AI 停在报告并提示处理完重跑 `/xz-exec N`，**绝不替用户自动实现**——抢着做等于毁掉手动路径的意义
