# XZ Update Plan - 修改版本计划的 todolist

你收到的参数: `$ARGUMENTS`

其中 `$0` 是版本号 N，`$0` 之后的内容是操作描述（修改/新增/删除要求）。

### 参数校验

如果 `$ARGUMENTS` 为空或 `$0` 不是合法版本号（正整数，或小数如 1.5），**立即停止**，提示：

> 缺少版本号。用法: `/xz-update-plan N 操作描述`
> 示例: `/xz-update-plan 1 修改 #3 增加 refresh token 逻辑`

**示例调用：**
- `/xz-update-plan 1 修改 #3 增加 refresh token 逻辑`
- `/xz-update-plan 1 新增一条: 添加日志中间件`
- `/xz-update-plan 1 删除 #4`
- `/xz-update-plan 1 在 #2 后面插入一条缓存优化`

---

## 辅助脚本

**脚本**：`xz-tools.py`

插件启用时 `bin/` 目录自动加入 PATH，直接作为命令调用即可（不需要 `python3` 前缀，也不需要绝对路径）。脚本在**当前工作目录**下操作 `.xz_planning/`。

## 执行流程

### 第一步：读取项目上下文

读取 `.xz_planning/PROJECT.md`（如果存在），快速了解项目技术栈、目录结构和关键入口，为后续新增/修改条目的 change details 提供准确的文件路径参考。

### 第二步：解析当前计划

```bash
xz-tools.py parse $0
```

- 如果返回 `"ok": false` → 版本不存在，提示用户先运行 `/xz-plan N 需求描述` 创建计划
- 如果返回 `"ok": true` → 读取 N-PLAN.md 完整内容，继续
- 同时检查同目录是否存在 `N-MANUAL.md`，并读取 PLAN 头部 `> 状态:`：
  - `N-MANUAL.md` 存在，或 PLAN 状态为 `待手动执行` → 本次变更必须同步手动清单
  - `N-MANUAL.md` 不存在且 PLAN 不是 `待手动执行` → 本次只更新 PLAN，不生成 MANUAL
  - PLAN 状态为 `待手动执行` 但 `N-MANUAL.md` 不存在 → 确认写入时按本次变更草案创建 `N-MANUAL.md`

### 第三步：读取并展示当前 todolist

读取 N-PLAN.md 文件，展示当前所有条目及状态：

```
当前 todolist (版本 N):
  [x] #1 创建 User model           ← 已完成，锁定
  [x] #2 实现注册接口               ← 已完成，锁定
  [ ] #3 实现登录接口               ← 可修改
  [ ] #4 JWT 中间件鉴权             ← 可修改
	  [ ] #5 添加单元测试               ← 可修改
```

同时展示手动清单同步状态：

```
手动清单:
  N-MANUAL.md: 存在 / 不存在
  同步策略: 本次会同步 MANUAL / 本次只更新 PLAN
```

### 第四步：锁定检查

**铁律：已完成的 `[x]` 条目不可修改、不可删除。**

如果用户的操作描述涉及 `[x]` 条目，**立即拒绝**并说明：

> #N 已完成，无法修改/删除。已完成的条目受锁定保护。

### 第五步：解析用户操作意图

根据操作描述，判断属于以下哪种操作（可以组合）：

#### 操作 A：修改已有条目

- 用户指定编号（如 "修改 #3"）
- 检查该编号是否为 `[ ]` 状态
- 生成修改后的条目内容（标题 + change details）
- 若需要同步手动清单：同步重写 `N-MANUAL.md` 中对应 `改动 N` 块；修改已有文件统一使用 `========= v计划号 真实改动标题 before|start|end ===========`，新建文件给整文件，删除贴完整原文

#### 操作 B：新增条目

- 在末尾追加，或在指定位置插入（如 "在 #2 后插入"）
- 插入后，后续条目编号自动递增
- 新条目必须包含完整的 change details
- 若需要同步手动清单：在 `N-MANUAL.md` 末尾追加或在对应位置插入新的 `改动 N` 块，并随最终 todolist 重编号

#### 操作 C：删除条目

- 用户指定编号（如 "删除 #4"）
- 检查该编号是否为 `[ ]` 状态
- 删除后，后续条目编号自动递减
- 若需要同步手动清单：删除 `N-MANUAL.md` 中对应 `改动 N` 块，并随最终 todolist 重编号

### 第六步：理解 + 澄清（有歧义/选择空间才做，无则跳过）

与 `/xz-plan` 第 3 步同构。**简单无歧义的增删改**（删 #4、改一句描述文字、纯位置调整）→ **跳过本步**直接进第七步草案。只要本次操作命中下列任一，就先在**同一条回复**里输出「①我的理解 + ②未澄清清单」、末尾一次**纯文本**提问（禁用 AskUserQuestion——其弹窗会吞掉前面文本），等用户回复后再出草案：

1. 改动涉及技术方向选择（换库/换协议/换数据结构/实现路径不止一种）；
2. 操作描述里的字段/状态/枚举/key 含义、取值范围、边界、验收没说清；
3. 需求内部矛盾、或与现有条目/代码/已确认约束冲突；
4. 改动会连带影响其他已有条目。

**① 我的理解**：一句话复述本次要改哪些条目、怎么改（与第七步变更草案要点对齐）。

**② 未澄清清单（技术方向选择 + 需求约束；按高/中/低排序；无则整段省略）**：把两类「需要用户在 a/b 里定夺」的点合到一张清单、**整段从 1 连续编号**，单项选项 ≤4——技术方向选择（多个可行改法、会左右改动范围/连带条目，`a` = 推荐，括号说理由）+ 需求约束（歧义的约束/边界/验收/字段定义、需求冲突，`a` = 最可能/推荐，括号说依据）。每项格式：`编号. [高/中/低] 一句话问题` → 换行 `现状：当前代码/条目/需求的实际情况` → 换行 `a. xxx（推荐…）  b. xxx`；打 `高/中/低` 标签并**从高到低排序**（技术方向多属高、自然靠前 = 先定大方向）。判级：高=选错大幅改变改动范围/返工成本高；中=只影响局部条目或某分支；低=边角细节。

**技术方向选择若需展开对比**（尤其连带影响多个已有条目）：在该项现状下补一张小对比表，但选择仍走 a/b。对比表模板：

```markdown
当前修改存在多种实现方式：

### 方案 A (推荐): 方案名称

**核心思路:** 一句话说清楚

**涉及改动:**
- 修改 #3: xxx → xxx
- 新增 #6: xxx

**优点:** ...
**缺点:** ...

---

### 方案 B (备选): 方案名称

**涉及改动:**
- 修改 #3: xxx → xxx
- 修改 #4: xxx → xxx（连带影响）
- 新增 #6: xxx

**优点:** ...
**缺点:** ...

---

| 维度 | 方案 A | 方案 B |
|------|--------|--------|
| 改动条目数 | 2 | 3 |
| 复杂度 | 低 | 中 |
| 对已有条目影响 | 无 | #4 需连带修改 |

👉 推荐方案 A: [理由]
```

（对比表仅在技术方向项需要展开时附；最终选择仍并入未澄清清单的 a/b，不再单独问「方案A/B」。）

**末尾一次提问（纯文本）**：
> 请一次回复：1) 理解准确？（`理解OK` / `理解需修正：xxx`）2) 未澄清各项（含技术方向与需求约束，`全部默认`用推荐 a，或按编号 `1a 2b 3a` 逐项覆盖）。示例：`理解OK 1a 2b`。

用户回复后，把理解 + 未澄清选择作为本次变更的既定前提，进第七步。**无歧义/无选择空间 → 整步跳过**，直接进第七步草案。

### 第七步：生成变更草案

基于第六步已确认的「理解 + 未澄清选择」（无澄清则按操作描述）生成。**先输出到对话中，不写文件！**

展示变更对比，格式：

```
变更对比 (版本 N):

  [锁定] #1 创建 User model         ✅ 已完成，不可变更
  [锁定] #2 实现注册接口             ✅ 已完成，不可变更
  [修改] #3 实现登录接口
    旧: JWT 签发，过期 24h
    新: JWT 签发 + Refresh Token，access 过期 1h，refresh 过期 7d
  [保留] #4 JWT 中间件鉴权           （无变化）
  [删除] #5 添加单元测试             ← 将被删除
  [新增] #5 添加 token 刷新接口      ← 新增条目

重编号后最终 todolist:
  [x] #1 创建 User model
  [x] #2 实现注册接口
  [ ] #3 实现登录接口 (已修改)
  [ ] #4 JWT 中间件鉴权
  [ ] #5 添加 token 刷新接口 (新增)
```

**同时输出改动前后对比草案**：基于本次变更后的 todolist，对照 N-PLAN.md 现有的 `## 改动前后对比`，输出新版「改动前/改动后」内容（基于实际代码、数据优先、不重复 todolist）。若本次变更不影响宏观效果（例如纯文字描述微调），可声明「改动前后对比无变化」。

```markdown
## 改动前后对比（草案）

改动前:
（原始现状）

改动后:
（变化后样子）
```

**如需要同步手动清单，同时输出 MANUAL 变更草案**：对照现有 `N-MANUAL.md`（若存在），展示本次将新增、修改、删除哪些手动块，并标出**本次改版号**（= 现有 MANUAL 里最大 `改版K` + 1；无任何改版标识则为 `改版1`）、以及头部「改版记录」将追加的那一行。

```markdown
## MANUAL 变更草案

- [修改] 改动 3 ｜ `src/auth/login.go`
  - 原手动块: 摘要说明
  - 新手动块: 摘要说明
  - 修改块标识: `========= vN 修改登录超时逻辑 before|start|end ===========`
- [新增] 改动 5 ｜ `src/token/refresh.go`
  - 新增手动块位置: 追加到改动 4 后
- [删除] 改动 6 ｜ `src/old/legacy.go`
  - 删除对应手动块，并重编号后续改动
```

MANUAL 草案规则：
- 只有 `N-MANUAL.md` 存在，或 PLAN 状态为 `待手动执行` 时才输出
- 修改文件默认只给最小必要上下文，不输出整文件；新建文件可以给整文件
- 修改已有文件统一使用 `========= v计划号 真实改动标题 before|start|end ===========`
- 注释、小插入、小替换也按修改已有文件处理，使用 `before|start|end` 标识最小必要上下文
- 片段中出现函数/方法时，上方必须带用途注释和案例
- **改版标识（本次新增/修改的块必加，给人工筛选用）**：本次 update 新增或修改的改动块，大分隔线标题加 `｜【改版K·新增｜需重新手动】` 或 `｜【改版K·修改｜需重新手动】`（K = 本次改版号），如 `═══ 改动 7 ｜【改版2·新增｜需重新手动】═══`；未触及的块保持原样（保留其历史标识）。**标识只加在大分隔线标题与头部改版记录，绝不改 `before|start|end` 代码锚点里的 `v计划号 真实改动标题`**——xz-exec 校验靠该锚点，改了会失配
- **头部改版记录**：N-MANUAL.md 顶部引导注释区维护「改版记录」，每次 update 追加一行 `- 改版K YYYY-MM-DD：新增 改动 a、修改 改动 b、删除 改动 c`，并保留一句说明「带【改版N】标识的块为该轮新增/修改、需重新手动；未标识的块不变」；原本无该区块（初版由 /xz-plan 生成）则本次初始化它

### 第八步：等待确认

在变更草案同一条回复末尾以纯文本提问确认（禁用 AskUserQuestion——其弹窗会吞掉同回复中前面的草案文本）：

> 以上变更是否确认？回复：
>   1) 确认更新 — 先做开发风险确认（第八·五步），再写入 N-PLAN.md、按需同步 N-MANUAL.md、刷新 STATE.md，等手动调 /xz-exec
>   2) 确认更新并直接执行 — 先做开发风险确认，再写入并立即进入 /xz-exec N 流程
>   3) 修改意见 — 调整后重新输出变更草案

**禁止自动写入文件。必须等待明确确认。** 用户选 `1` / `2` → 进第八·五步开发风险确认；选「修改意见」或给其他反馈 → 按反馈调整后重新输出草案（回第七步）。

### 第八·五步：开发风险确认（确认变更草案后、写文件前，强制独立一轮）

**触发**：用户在第八步选了 `1) 确认更新` 或 `2) 确认更新并直接执行` 后，**先做这一轮再写文件**（与 `/xz-plan` 3.5 同构）；选「修改意见」则回第七步、不进本步。

**怎么做**：基于本次**已确认的变更 change details**（含 MANUAL 改动块）对照风险清单逐项排查。**命中** = 本次改动真实触及该点 + 处理方式未定 + 不同处理有实质差异；命中即列、未命中维度不展示；即使能推断安全默认，也作为推荐 a 摆出让用户确认。

**风险清单**：安全（硬编码密钥、输入未校验、敏感信息泄露、鉴权缺失/绕过、弱加密）/ 性能（循环冗余、资源未释放、N+1、缺索引大表查询/缺分页、goroutine 泄漏）/ 数据与兼容（改字段历史数据、接口向后兼容、迁移与回滚）/ 并发时序（无锁共享、重试幂等、竞态）/ 错误处理（吞异常、错误丢上下文、失败回滚清理）/ 边界（空值/零值/负数/超大输入）/ 语言专项（Go 未检查 error return、缺超时、竞态；JS/TS XSS、eval、监听器/定时器未清理；SQL 拼接注入、过宽 GRANT、动态表名未白名单；Python async 夹同步阻塞、ORM N+1）。

**每条命中项**：打 `严重/高/中/低` 标签、**从严重到低排序**，每条末尾固定一个 `不处理/忽略` 逃生项。格式：

```
开发风险确认（按严重度排序，逐项回复怎么处理，如 `1a 2b 3c`，全用推荐回 `全部默认`）：
1. [严重] 新增 token 刷新接口入参未校验 → a. 入口统一校验非空+格式（推荐，防脏数据）  b. 仅依赖下游兜底  c. 不处理/忽略（明确接受该风险）
2. [中] 改 #3 后历史 token 字段为空 → a. 迁移补默认值（推荐）  b. 运行时兼容 null  c. 不处理/忽略（明确接受该风险）
```

**无命中**：输出「已逐项排查安全/性能/数据兼容/并发/错误处理/边界等维度，本次变更无需额外确认的开发风险」并直接进第九步。

**用户回复后**：把每项选定处理落地到第九步要写的 N-PLAN.md（Constraints / 技术方案 / 对应条目 change details）与 N-MANUAL.md；选「不处理/忽略」的不落地为改动，但在 Constraints 记一句「已确认接受 X 风险，本次不处理」留痕。然后进第九步写文件。

### 第九步：确认后更新文件

**先落地第八·五步确认的开发风险处理**（写进下面对应的 N-PLAN.md Constraints/技术方案/change details 与 N-MANUAL.md），再按下列步骤写文件。

**获取当前时间：**

```bash
date "+%Y-%m-%d %H:%M:%S"
```

1. **更新 N-PLAN.md**：
   - 修改/新增/删除对应的 todolist 条目和 change details
   - 重新编号所有条目，保证连续（1, 2, 3, ...）
   - **同步更新「任务总结」章节** — 根据变更后的 todolist 重新生成自然语言总结，保持与条目一一对应
   - **同步刷新 `## 改动前后对比`** — 按第七步草案中确认过的「改动前/改动后」覆盖原有章节；若声明无变化则保留原内容
   - 更新「最后更新」时间
   - 在「变更记录」中追加一行：`- YYYY-MM-DD HH:mm:ss 操作描述`

2. **按需更新 N-MANUAL.md**：
   - 仅当 `N-MANUAL.md` 存在，或 PLAN 状态为 `待手动执行` 时执行
   - 按第七步确认过的 MANUAL 变更草案，新增/修改/删除对应 `改动 N` 块
   - 删除 todolist 条目时，同步删除对应手动块
   - 插入/删除后，重编号后续 `改动 N` 和小节编号，保持与 N-PLAN.md 的 todolist 一一对应
   - 若原本没有 `N-MANUAL.md` 但 PLAN 状态为 `待手动执行`，创建 `N-MANUAL.md`
   - 手动块格式必须满足 `xz-exec` 校验模式：修改已有文件统一使用 `v计划号` 标识，修改文件不输出整文件
   - **写改版标识**：按第七步确认的本次改版号 K，给本次新增/修改的块大分隔线标题加 `｜【改版K·新增｜需重新手动】` / `｜【改版K·修改｜需重新手动】`；未触及块不动其标题；**不改 `before|start|end` 代码锚点**
   - **更新头部改版记录**：在 N-MANUAL.md 顶部「改版记录」追加本轮一行（新增/修改/删除了哪些改动 + 日期）；首次需要时初始化该区块

3. **刷新 STATE.md**：

```bash
xz-tools.py update-state
```

**若用户选「确认更新并直接执行」**：STATE.md 刷新完成后，直接按 `/xz-exec N` 的完整流程接着执行 todolist，跳过下面第十步（由 xz-exec 自己的流程接管后续询问）。

### 第十步：输出改动结果（仅「确认更新」路径）

整理并输出：
- 修改了哪些条目
- 新增了哪些条目
- 删除了哪些条目
- MANUAL 同步了哪些手动块（新增/修改/删除/未启用同步）
- 当前 todolist 总数和完成进度

然后以纯文本输出下一步选项：

> 计划已更新。下一步: /xz-exec N（继续执行）/ /xz-update-plan N（继续修改）/ /xz-ref N（加载为上下文）

用户回复后执行对应的 skill 命令。

## 关键规则

1. **已完成锁定** — `[x]` 条目绝不可修改或删除，这是铁律
2. **先输出后写文件** — 变更草案必须先展示，用户确认后才写入
3. **编号自动维护** — 插入/删除后重新编号，保持 1, 2, 3... 连续
4. **change details 必填** — 新增/修改的条目必须包含完整的 change details
5. **变更记录追加** — 每次修改都在变更记录中留痕
6. **STATE.md 同步** — 更新文件后必须刷新 STATE.md 反映最新进度
7. **澄清同 /xz-plan** — 涉及技术方向选择（换库/协议/数据结构/多实现路径）、字段/边界/验收歧义、需求冲突、或连带影响其他条目时，第六步先出「①我的理解 + ②未澄清清单」：技术方向选择 + 需求约束合一张清单，每项 `[高/中/低]` + 现状 + a/b、整段连号、从高到低排序，纯文本确认（禁用 AskUserQuestion），禁自行替用户选定；简单无歧义增删改跳过。技术方向需展开对比时在该项附小对比表，选择仍走 a/b
8. **Bug/问题排查类变更** — 如果操作描述涉及修复 bug、排查问题、处理异常等，建议用户先用 `/xz-debug` 定位根因，再回来新增/修改 todolist 条目。纯功能调整不需要
9. **一次确认批处理** — 变更草案是唯一的确认入口，所有 AI 判定和建议全写进草案，第八步文本确认的选项覆盖所有 override 路径；禁止在草案之前单独弹问；全程禁用 AskUserQuestion（其弹窗会吞掉同回复中前面的文本）
10. **聚焦本次操作边界** — 严格按用户的操作描述范围调整，禁止顺手扩展到其他条目（例如"新增一条日志中间件"不应连带重排其他条目的细节）
11. **改动前后对比同步** — 修改/新增/删除影响宏观效果时，必须同步刷新 N-PLAN.md 的 `## 改动前后对比`；草案先在第七步对话里展示，第九步落盘时一并更新
12. **MANUAL 同步触发条件** — 只要 `N-MANUAL.md` 存在，或 N-PLAN.md 头部状态为 `待手动执行`，修改/新增/删除 todolist 时必须同步手动清单；否则只更新 PLAN
13. **MANUAL 增删改一一对应** — 修改条目重写对应手动块；新增/插入条目新增手动块；删除条目删除对应手动块；重编号后 MANUAL 的 `改动 N` 必须和 PLAN todolist 编号一致
14. **MANUAL 块格式沿用 xz-plan/xz-exec 规则** — 修改已有文件统一使用 `========= v计划号 真实改动标题 before|start|end ===========`；新建文件给整文件；删除贴完整原文；修改文件不输出整文件；片段里出现函数/方法时必须带用途注释和案例
15. **PLAN/MANUAL 草案一起确认** — 需要同步 MANUAL 时，第七步必须同时展示 PLAN 变更草案和 MANUAL 变更草案；第八步确认后才允许写入两份文件
16. **开发风险独立一轮** — 变更草案确认后、写文件前（第八·五步），基于本次 change details 排查安全/性能/数据兼容/并发/错误处理/边界，命中即列、打 `严重/高/中/低` 并从严重到低排序、每条末尾带 `不处理/忽略` 逃生项，用户 `1a 2b 3c` 确认；选定处理落地到 PLAN/MANUAL，选忽略的在 Constraints 留痕；无命中声明并直接写。与 `/xz-plan` 3.5 同构
17. **MANUAL 改版标识** — 改动 MANUAL 时，本次改版号 = 现有最大 `改版K`+1（无则 1）；本次新增/修改的 `═══ 改动 N ═══` 块标题加 `｜【改版K·新增/修改｜需重新手动】`，并在 MANUAL 头部「改版记录」追加本轮动了哪些改动，让人工一眼筛出需重新手动的块；**改版标识只加在分隔线标题与头部，绝不改 `before|start|end` 代码锚点里的 `v计划号 真实改动标题`**（xz-exec 校验靠它）
