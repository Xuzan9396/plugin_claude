# XZ Update Plan - 修改版本计划的 todolist

你收到的参数: `$ARGUMENTS`

其中 `$0` 是版本号 N，`$0` 之后的内容是操作描述（修改/新增/删除要求）。

### 参数校验

如果 `$ARGUMENTS` 为空或 `$0` 不是合法版本号（正整数，或小数如 1.5），**立即停止**，提示：

> 缺少版本号。用法: `/xz-update-plan N 操作描述`
> 示例: `/xz-update-plan 1 修改 #3 增加 refresh token 逻辑`

**示例调用：**
- `/xz-update-plan 1 修改 #3 增加 refresh token 逻辑`
- `/xz-update-plan 1 新增一条: 添加日志中间件`
- `/xz-update-plan 1 删除 #4`
- `/xz-update-plan 1 在 #2 后面插入一条缓存优化`

---

## 辅助脚本

**脚本**：`xz-tools.py`

插件启用时 `bin/` 目录自动加入 PATH，直接作为命令调用即可（不需要 `python3` 前缀，也不需要绝对路径）。脚本在**当前工作目录**下操作 `.xz_planning/`。

---

## 执行流程

### 第一步：读取项目上下文

读取 `.xz_planning/PROJECT.md`（如果存在），快速了解项目技术栈、目录结构和关键入口，为后续新增/修改条目的 改动详情 提供准确的文件路径参考。

### 第二步：解析当前计划

```bash
xz-tools.py parse $0
```

- 如果返回 `"ok": false` → 版本不存在，提示用户先运行 `/xz-plan N 需求描述` 创建计划
- 如果返回 `"ok": true` → 读取 N-PLAN.md 完整内容，继续
- 同时检查同目录是否存在 `N-MANUAL.md`，并读取 PLAN 头部 `> 状态:`：
  - `N-MANUAL.md` 存在，或 PLAN 状态为 `待手动执行` → 本次变更必须同步手动清单
  - `N-MANUAL.md` 不存在且 PLAN 不是 `待手动执行` → 本次只更新 PLAN，不生成 MANUAL
  - PLAN 状态为 `待手动执行` 但 `N-MANUAL.md` 不存在 → 确认写入时按本次变更草案创建 `N-MANUAL.md`
- **同时读取 PLAN 的 `## 测试方案` 章节**（五段：测试环境与命令 / 测试前置信息 / 自动化用例 / 人工介入项 / 通过标准），并检查同目录是否已有 `N-TEST-REPORT.md`：
  - 有 `N-TEST-REPORT.md` → 该版本已跑过闭环测试，本次变更后重新 `/xz-exec` 时会**全量重跑**（不是只跑新增用例），需在草案里提示用户
  - PLAN 无 `## 测试方案` 章节（老计划）→ 本次按 `/xz-plan` 4.5 的四段模板**补齐**该章节，作为变更草案的一部分展示

### 第三步：读取并展示当前 todolist

读取 N-PLAN.md 文件，展示当前所有条目及状态：

```
当前 todolist (版本 N):
  [x] #1 创建 User model           ← 已完成，锁定
  [x] #2 实现注册接口               ← 已完成，锁定
  [ ] #3 实现登录接口               ← 可修改
  [ ] #4 JWT 中间件鉴权             ← 可修改
	  [ ] #5 添加单元测试               ← 可修改
```

同时展示手动清单同步状态：

```
手动清单:
  N-MANUAL.md: 存在 / 不存在
  同步策略: 本次会同步 MANUAL / 本次只更新 PLAN

测试方案:
  ## 测试方案: 已有 4 条自动化用例 T1-T4 / 无该章节（本次补齐）
  N-TEST-REPORT.md: 存在（上轮 4/4 通过，本次变更后需全量重跑）/ 不存在
```

### 第四步：锁定检查

**铁律：已完成的 `[x]` 条目不可修改、不可删除。**

如果用户的操作描述涉及 `[x]` 条目，**立即拒绝**并说明：

> #N 已完成，无法修改/删除。已完成的条目受锁定保护。

### 第五步：解析用户操作意图

根据操作描述，判断属于以下哪种操作（可以组合）：

#### 操作 A：修改已有条目

- 用户指定编号（如 "修改 #3"）；检查该编号是否为 `[ ]` 状态
- 生成修改后的条目内容（标题 + 改动详情）

#### 操作 B：新增条目

- 在末尾追加，或在指定位置插入（如 "在 #2 后插入"）；插入后后续条目编号自动递增
- 新条目必须包含完整的 改动详情

#### 操作 C：删除条目

- 用户指定编号（如 "删除 #4"）；检查该编号是否为 `[ ]` 状态
- 删除后，后续条目编号自动递减

> **三种操作若需同步 MANUAL**（触发条件见第二步）：改条目 → 重写对应 `改动 N` 块；增条目 → 追加/插入新块；删条目 → 删除对应块。之后随最终 todolist 重编号，块格式沿用 `/xz-plan` 的 MANUAL 规则。

### 第六步：理解 + 澄清（有歧义/选择空间才做，无则跳过）

与 `/xz-plan` 第 3 步同构。**简单无歧义的增删改**（删 #4、改一句描述文字、纯位置调整）→ **跳过本步**直接进第七步草案。只要本次操作命中下列任一，就先在**同一条回复**里输出「①我的理解 + ②未澄清清单」、末尾一次**纯文本**提问（禁用 AskUserQuestion——其弹窗会吞掉前面文本），等用户回复后再出草案：

1. 改动涉及技术方向选择（换库/换协议/换数据结构/实现路径不止一种）；
2. 操作描述里的字段/状态/枚举/key 含义、取值范围、边界、验收没说清；
3. 需求内部矛盾、或与现有条目/代码/已确认约束冲突；
4. 改动会连带影响其他已有条目。

**① 我的理解**：一句话复述本次要改哪些条目、怎么改（与第七步变更草案要点对齐）。

**② 未澄清清单（无则整段省略）**：技术方向选择 + 需求约束合到一张清单、**整段从 1 连续编号**，单项选项 ≤4。每项格式：

```
编号. [高/中/低] 一句话问题
     现状：当前代码/条目/需求的实际情况
     a. xxx（推荐，理由/依据）  b. xxx
```

`a` 固定放推荐项（技术方向给理由、需求约束给依据）。打标签并**从高到低排序**：`高` = 选错大幅改变改动范围/返工成本高；`中` = 只影响局部条目或某分支；`低` = 边角细节。技术方向多属高、自然靠前 = 先定大方向。

**技术方向选择若需展开对比**（尤其连带影响多个已有条目）：在该项「现状：」下补一张 3 列小表即可，**不要另起「方案 A/B」大段**——选择仍走清单里的 a/b：

```markdown
| 维度 | a. 方案名(推荐) | b. 方案名 |
|------|----------------|-----------|
| 改动条目 | 改 #3、新增 #6 | 改 #3、改 #4(连带)、新增 #6 |
| 改动量 | 2 条 | 3 条 |
| 对已有条目影响 | 无 | #4 需连带修改 |
```

**末尾一次提问（纯文本）**：
> 请一次回复：1) 理解准确？（`理解OK` / `理解需修正：xxx`）2) 未澄清各项（含技术方向与需求约束，`全部默认`用推荐 a，或按编号 `1a 2b 3a` 逐项覆盖）。示例：`理解OK 1a 2b`。

#### 澄清追问循环（答复后必做，与 `/xz-plan` 第 3 步同构）

一轮问答往往问不干净——用户定了某个方向后常会暴露新的待定点。所以：

- 用户答复后，把已定夺项（含选定的技术方向）并入「我的理解」；用户修正了理解 → 更新后**重出「我的理解」**，必要时重新对齐再问。
- 若答复**引出新歧义**（如选了 b 方案后暴露新的字段/边界待定）、**答复不完整**（有编号没回）、或**与已确认内容冲突** → **继续追问**：同格式再出一轮未澄清清单，**编号重新从 1 连号**，段首说明第几轮追问及触发原因。例：`第 2 轮追问（因选定方案 b 后，新增字段的默认值未定）：`
- **禁止带着未定项进第七步草案**；无剩余未澄清项时输出「澄清完毕，进入变更草案」再进第七步。

用户回复后，把理解 + 全部轮次的未澄清选择作为本次变更的既定前提，进第七步。**无歧义/无选择空间 → 整步跳过**，直接进第七步草案。

### 第七步：生成变更草案

基于第六步已确认的「理解 + 未澄清选择」（无澄清则按操作描述）生成。**先输出到对话中，不写文件！**

展示变更对比，格式：

```
变更对比 (版本 N):

  [锁定] #1 创建 User model         ✅ 已完成，不可变更
  [锁定] #2 实现注册接口             ✅ 已完成，不可变更
  [修改] #3 实现登录接口
    旧: JWT 签发，过期 24h
    新: JWT 签发 + Refresh Token，access 过期 1h，refresh 过期 7d
  [保留] #4 JWT 中间件鉴权           （无变化）
  [删除] #5 添加单元测试             ← 将被删除
  [新增] #5 添加 token 刷新接口      ← 新增条目

重编号后最终 todolist:
  [x] #1 创建 User model
  [x] #2 实现注册接口
  [ ] #3 实现登录接口 (已修改)
  [ ] #4 JWT 中间件鉴权
  [ ] #5 添加 token 刷新接口 (新增)
```

**同时输出改动前后对比草案**：基于本次变更后的 todolist，对照 N-PLAN.md 现有的 `## 改动前后对比`，输出新版「改动前/改动后」内容（基于实际代码、数据优先、不重复 todolist）。若本次变更不影响宏观效果（例如纯文字描述微调），可声明「改动前后对比无变化」。

```markdown
## 改动前后对比（草案）

改动前:
（原始现状）

改动后:
（变化后样子）
```

**如需要同步手动清单，同时输出 MANUAL 变更草案**：对照现有 `N-MANUAL.md`（若存在），展示本次将新增、修改、删除哪些手动块，并标出**本次改版号**（= 现有 MANUAL 里最大 `改版K` + 1；无任何改版标识则为 `改版1`）、以及头部「改版记录」将追加的那一行。

```markdown
## MANUAL 变更草案

- [修改] 改动 3 ｜ `src/auth/login.go`
  - 原手动块: 摘要说明
  - 新手动块: 摘要说明
  - 修改块标识: `========= vN 修改登录超时逻辑 before|start|end ===========`
- [新增] 改动 5 ｜ `src/token/refresh.go`
  - 新增手动块位置: 追加到改动 4 后
- [删除] 改动 6 ｜ `src/old/legacy.go`
  - 删除对应手动块，并重编号后续改动
```

MANUAL 草案规则：
- 只有 `N-MANUAL.md` 存在，或 PLAN 状态为 `待手动执行` 时才输出
- 块格式沿用 `/xz-plan` 的 MANUAL 规则：修改已有文件用 `========= v计划号 真实改动标题 before|start|end ===========` 三段标识块、只给最小必要上下文不输出整文件（注释和小插入同样按此处理），新建文件给整文件，删除贴完整原文，片段里出现函数/方法必须带用途注释和案例
- **改版标识（本次新增/修改的块必加，给人工筛选用）**：大分隔线标题加 `｜【改版K·新增｜需重新手动】` 或 `｜【改版K·修改｜需重新手动】`（K = 本次改版号），如 `═══ 改动 7 ｜【改版2·新增｜需重新手动】═══`；未触及的块保持原样（保留历史标识）。**标识只加在大分隔线标题与头部改版记录，绝不改 `before|start|end` 锚点里的 `v计划号 真实改动标题`**——xz-exec 校验靠该锚点，改了会失配
- **头部改版记录**：N-MANUAL.md 顶部引导注释区维护「改版记录」，每次 update 追加一行 `- 改版K YYYY-MM-DD：新增 改动 a、修改 改动 b、删除 改动 c`，并保留一句说明「带【改版N】标识的块为该轮新增/修改、需重新手动；未标识的块不变」；原本无该区块（初版由 /xz-plan 生成）则本次初始化它

**同时输出测试方案变更草案（必做，与 PLAN 变更草案一起展示）**：本次条目增删改必然影响 `## 测试方案` 的自动化用例，草案里要说清用例怎么变。

```markdown
## 测试方案变更草案

- [新增] T5 ｜ 对应新增条目 #5 token 刷新接口
  - 类型: 接口 ｜ 命令: `curl -s -X POST localhost:8080/token/refresh -d '{"rt":"xxx"}'`
  - 预期判定: HTTP 200 且 body 含新的 `access_token`
- [修改] T3 ｜ 对应修改条目 #3 登录接口
  - 原判定: body 含 `token`
  - 新判定: body 同时含 `access_token` 和 `refresh_token`
- [删除] T4 ｜ 随条目 #5「添加单元测试」删除而移除
- [测试前置信息] 新增 P3：refresh token 走 Redis，需要 Redis 连接串（T5 要用；`.env` 无 REDIS_* 项）
- [人工介入项] 无新增 / 新增 1 项（说明为什么 AI 跑不了）
- [回归范围] 已存在 N-TEST-REPORT.md，本次 /xz-exec 后将全量重跑 T1-T5（含已完成条目的用例）
- [受影响的测试产物] 新增 → 执行时生成 `tests/T5-*`；修改 → 报告「复现步骤」里 T3 的代码块要重写；删除 → `tests/T4-*` 旧产物保留，报告里标废弃
```

测试方案草案规则：
- **新增/修改条目若引入新的外部依赖**（新表、新中间件、新第三方接口）→ 同步在「测试前置信息」加项，并在第八步确认时**一并索取**（格式与自查要求同 `/xz-plan` 4.5：先查 `.env`/`config`/`docker-compose.yml`/fixture，找得到的不问）；拿到的凭据写进 `tests/.env.local`，PLAN 里只写引用
- **新增/修改条目必须有对应自动化用例**（新增条目至少配一条新用例；修改条目要检查原用例的断言是否还成立，不成立就改断言），禁止只改条目不动用例
- **删除条目同步删除其专属用例**；若该用例还覆盖其他条目，则只删对应关系不删用例
- **T 编号只增不减** — 新用例编号接着当前最大编号往后排，**禁止复用已删编号**（否则历史 `N-TEST-REPORT.md` 里的 T4 会指向两个不同的东西）
- **测试产物跟着变** — 草案必须列出受影响的 `tests/T{编号}-*`：新增（执行时生成）、修改（报告「复现步骤」的代码块要重写）、删除（旧产物保留、报告里标废弃）
- **已完成 `[x]` 条目的用例仍参与回归** — 条目锁定不代表免测，回归范围永远是全部用例
- 用例格式沿用 `/xz-plan` 4.5：具体可执行命令 + 机器可判定断言，浏览器 UI 走 `/claude-in-chrome`，人工介入项仅限那四类（真实凭证/线上环境/破坏性操作/主观视觉）
- 本次变更确实不影响任何用例（如纯文字描述微调）→ 明确写一句「测试方案无变化」，不得省略本段

### 第八步：等待确认

在变更草案同一条回复末尾以纯文本提问确认（禁用 AskUserQuestion——其弹窗会吞掉同回复中前面的草案文本）：

> 以上变更是否确认？回复：
>   1) 确认更新 — 先做开发风险确认（第八·五步），再写入 N-PLAN.md（含更新后的测试方案）、按需同步 N-MANUAL.md、刷新 STATE.md，等手动调 /xz-exec
>   2) 确认更新并直接执行 — 先做开发风险确认，再写入并立即进入 /xz-exec N 流程（含完成后的自动闭环测试）
>   3) 修改意见 — 调整后重新输出变更草案

**禁止自动写入文件。必须等待明确确认。** 用户选 `1` / `2` → 进第八·五步开发风险确认；选「修改意见」或给其他反馈 → 按反馈调整后重新输出草案（回第七步）。

### 第八·五步：开发风险确认（确认变更草案后、写文件前，强制独立一轮）

**触发**：用户在第八步选了 `1) 确认更新` 或 `2) 确认更新并直接执行` 后，**先做这一轮再写文件**（与 `/xz-plan` 3.5 同构）；选「修改意见」则回第七步、不进本步。

**怎么做**：基于本次**已确认的变更 改动详情**（含 MANUAL 改动块）对照风险清单逐项排查。**命中** = 本次改动真实触及该点 + 处理方式未定 + 不同处理有实质差异；命中即列、未命中维度不展示；即使能推断安全默认，也作为推荐 a 摆出让用户确认。

**风险清单**：安全（硬编码密钥、输入未校验、敏感信息泄露、鉴权缺失/绕过、弱加密）/ 性能（循环冗余、资源未释放、N+1、缺索引大表查询/缺分页、goroutine 泄漏）/ 数据与兼容（改字段历史数据、接口向后兼容、迁移与回滚）/ 并发时序（无锁共享、重试幂等、竞态）/ 错误处理（吞异常、错误丢上下文、失败回滚清理）/ 边界（空值/零值/负数/超大输入）/ 语言专项（Go 未检查 error return、缺超时、竞态；JS/TS XSS、eval、监听器/定时器未清理；SQL 拼接注入、过宽 GRANT、动态表名未白名单；Python async 夹同步阻塞、ORM N+1）。

**每条命中项**：打 `严重/高/中/低` 标签、**从严重到低排序**，每条末尾固定一个 `不处理/忽略` 逃生项。格式：

```
开发风险确认（按严重度排序，逐项回复怎么处理，如 `1a 2b 3c`，全用推荐回 `全部默认`）：
1. [严重] 新增 token 刷新接口入参未校验 → a. 入口统一校验非空+格式（推荐，防脏数据）  b. 仅依赖下游兜底  c. 不处理/忽略（明确接受该风险）
2. [中] 改 #3 后历史 token 字段为空 → a. 迁移补默认值（推荐）  b. 运行时兼容 null  c. 不处理/忽略（明确接受该风险）
```

**无命中**：输出「已逐项排查安全/性能/数据兼容/并发/错误处理/边界等维度，本次变更无需额外确认的开发风险」并直接进第九步。

**用户回复后**：把每项选定处理落地到第九步要写的 N-PLAN.md（约束 / 技术方案 / 对应条目 改动详情）与 N-MANUAL.md；选「不处理/忽略」的不落地为改动，但在 约束 记一句「已确认接受 X 风险，本次不处理」留痕。然后进第九步写文件。

### 第九步：确认后更新文件

**先落地第八·五步确认的开发风险处理**（写进下面对应的 N-PLAN.md 约束/技术方案/改动详情 与 N-MANUAL.md），再按下列步骤写文件。

**获取当前时间：**


1. **更新 N-PLAN.md**：
   - 修改/新增/删除对应的 todolist 条目和 改动详情
   - 重新编号所有条目，保证连续（1, 2, 3, ...）

   - **同步刷新 `## 改动前后对比`** — 按第七步草案中确认过的「改动前/改动后」覆盖原有章节；若声明无变化则保留原内容
   - **同步刷新 `## 测试方案`** — 按第七步测试方案变更草案，把新增/修改/删除的自动化用例落到「自动化用例」表（编号保持连续），必要时同步更新「测试环境与命令」「测试前置信息」「人工介入项」「通过标准」；PLAN 原本无该章节则按 `/xz-plan` 4.5 五段模板补齐；草案声明「测试方案无变化」则保留原内容。用户在第八步给的凭据写进 `tests/.env.local`（头部标注勿提交 + 先确保 `.gitignore` 覆盖），**PLAN 里只写引用不写明文**
   - **同步测试产物口径** — 新编号接着最大编号往后排、**不复用已删编号**；被删用例的旧产物（`tests/T{编号}-*`）**不删**，在报告「复现步骤」对应小节加一行 `> ⚠️ 已于 YYYY-MM-DD 从测试方案移除（原因：xxx），保留仅供参考`——用户可能还想自己手动跑；命令有变的用例，等 `/xz-exec` 重跑时把「复现步骤」的代码块更新为真跑通的那条
   - 更新「最后更新」时间
   - 在「变更记录」中追加一行：`- YYYY-MM-DD HH:mm:ss 操作描述`

## 关键规则

1. **已完成锁定** — `[x]` 条目绝不可修改或删除，这是铁律
2. **先输出后写文件** — 变更草案必须先展示，用户确认后才写入
3. **编号自动维护** — 插入/删除后重新编号，保持 1, 2, 3... 连续
4. **改动详情 必填** — 新增/修改的条目必须包含完整的 改动详情
5. **变更记录追加** — 每次修改都在变更记录中留痕
6. **STATE.md 同步** — 更新文件后必须刷新 STATE.md 反映最新进度
7. **澄清同 /xz-plan、循环递进追问到无问题** — 涉及技术方向选择（换库/协议/数据结构/多实现路径）、字段/边界/验收歧义、需求冲突、或连带影响其他条目时，第六步先出「①我的理解 + ②未澄清清单」：技术方向选择 + 需求约束合一张清单，每项 `[高/中/低]` + 现状 + a/b、整段连号、从高到低排序，纯文本确认（禁用 AskUserQuestion），禁自行替用户选定；简单无歧义增删改跳过。技术方向需展开对比时在该项附小对比表，选择仍走 a/b。**答复后必须判断是否要再追一轮**：引出新歧义 / 答复不完整 / 与已确认内容冲突 → 同格式再出一轮（**编号重新从 1 连号**，段首标明第几轮及触发原因），直到无未澄清项；**全部定夺前禁止出变更草案**，澄清完毕先输出「澄清完毕，进入变更草案」
8. **Bug/问题排查类变更** — 如果操作描述涉及修复 bug、排查问题、处理异常等，建议用户先用 `/xz-debug` 定位根因，再回来新增/修改 todolist 条目。纯功能调整不需要
9. **一次确认批处理** — 变更草案是唯一的确认入口，所有 AI 判定和建议全写进草案，第八步文本确认的选项覆盖所有 override 路径；禁止在草案之前单独弹问；全程禁用 AskUserQuestion（其弹窗会吞掉同回复中前面的文本）
10. **聚焦本次操作边界** — 严格按用户的操作描述范围调整，禁止顺手扩展到其他条目（例如"新增一条日志中间件"不应连带重排其他条目的细节）
11. **改动前后对比同步** — 修改/新增/删除影响宏观效果时，必须同步刷新 N-PLAN.md 的 `## 改动前后对比`；草案先在第七步对话里展示，第九步落盘时一并更新
12. **MANUAL 同步触发条件** — 只要 `N-MANUAL.md` 存在，或 N-PLAN.md 头部状态为 `待手动执行`，修改/新增/删除 todolist 时必须同步手动清单；否则只更新 PLAN
13. **MANUAL 增删改一一对应** — 修改条目重写对应手动块；新增/插入条目新增手动块；删除条目删除对应手动块；重编号后 MANUAL 的 `改动 N` 必须和 PLAN todolist 编号一致
14. **MANUAL 块格式沿用 xz-plan/xz-exec 规则** — 修改已有文件统一使用 `========= v计划号 真实改动标题 before|start|end ===========`；新建文件给整文件；删除贴完整原文；修改文件不输出整文件；片段里出现函数/方法时必须带用途注释和案例
15. **PLAN/MANUAL 草案一起确认** — 需要同步 MANUAL 时，第七步必须同时展示 PLAN 变更草案和 MANUAL 变更草案；第八步确认后才允许写入两份文件
16. **开发风险独立一轮** — 变更草案确认后、写文件前（第八·五步），基于本次 改动详情 排查安全/性能/数据兼容/并发/错误处理/边界，命中即列、打 `严重/高/中/低` 并从严重到低排序、每条末尾带 `不处理/忽略` 逃生项，用户 `1a 2b 3c` 确认；选定处理落地到 PLAN/MANUAL，选忽略的在 约束 留痕；无命中声明并直接写。与 `/xz-plan` 3.5 同构
17. **测试方案同步** — todolist 增删改必须同步 N-PLAN.md 的 `## 测试方案`：新增/修改条目必须有对应自动化用例（新增配新用例、修改要复核原断言是否还成立），删除条目同步删其专属用例，已完成 `[x]` 条目的用例仍参与回归（锁定 ≠ 免测）；第七步草案必须展示「测试方案变更草案」（确实无影响则明写「测试方案无变化」，不得省略本段），第九步落盘时一并写入；用例格式沿用 `/xz-plan` 4.5——具体命令 + 机器可判定断言，浏览器 UI 走 `/claude-in-chrome`，只有真实凭证/线上环境/破坏性操作/主观视觉确认才能列入人工介入项；**新条目引入新外部依赖（新表/新中间件/新第三方接口）时同步在「测试前置信息」加项并在第八步一并索取，凭据只写 `tests/.env.local`、PLAN 里只写引用**；PLAN 无该章节则本次按五段补齐。**T 编号全版本唯一、只增不减**（删掉的编号不回收复用，它同时是产物文件名前缀 `tests/T3-*` 与报告「复现步骤」的小节号）：新增用例的产物执行时才生成，被删用例的旧产物保留并在报告里标废弃
18. **MANUAL 改版标识** — 改动 MANUAL 时，本次改版号 = 现有最大 `改版K`+1（无则 1）；本次新增/修改的 `═══ 改动 N ═══` 块标题加 `｜【改版K·新增/修改｜需重新手动】`，并在 MANUAL 头部「改版记录」追加本轮动了哪些改动，让人工一眼筛出需重新手动的块；**改版标识只加在分隔线标题与头部，绝不改 `before|start|end` 代码锚点里的 `v计划号 真实改动标题`**（xz-exec 校验靠它）
