# XZ Update Plan - 修改版本计划的 todolist

参数 `$ARGUMENTS`：第一个空格前（`$0`）为版本号 N，之后为操作描述（修改/新增/删除要求）。
`$ARGUMENTS` 为空 / `$0` 不是合法版本号（正整数，或小数如 1.5）→ **立即停止**，提示 `缺少版本号。用法: /xz-update-plan N 操作描述`。

**示例调用**：`/xz-update-plan 1 修改 #3 增加 refresh token 逻辑` / `/xz-update-plan 1 新增一条: 添加日志中间件` / `/xz-update-plan 1 删除 #4` / `/xz-update-plan 1 在 #2 后面插入一条缓存优化`

**脚本**：`xz-tools.py`（`bin/` 已在 PATH，直接调用，在当前目录操作 `.xz_planning/`）。

---

## 执行流程

### 第一步：读取项目上下文

读取 `.xz_planning/PROJECT.md`（如果存在），快速了解项目技术栈、目录结构和关键入口，为后续新增/修改条目的 改动详情 提供准确的文件路径参考。

### 第二步：解析当前计划

跑 `xz-tools.py parse $0`：

- 返回 `"ok": false` → 版本不存在，提示用户先运行 `/xz-plan N 需求描述` 创建计划
- 返回 `"ok": true` → 读取 N-PLAN.md 完整内容，继续
- 同时检查同目录有没有 `N-MANUAL.md`，并读 PLAN 头部 `> 状态:`。**只是为了判断要不要提醒用户去同步，本 skill 不碰 MANUAL 文件**：
  - `N-MANUAL.md` 存在，或状态是 `待手动执行` → 这是手动路径，本次改完 PLAN 后要提示用户跑 `/xz-manual N sync`
  - 两者都不是 → 常规路径，跟 MANUAL 无关
- 顺带读 PLAN 的 `## 测试方案` 三段、看同目录有没有 `N-TEST-REPORT.md`：有报告说明跑过闭环，本次改完重新 `/xz-exec` 会现场重新生成用例表并全量重跑，草案里提一句；PLAN 无 `## 测试方案`（老计划）按 `/xz-plan` 4.5 三段补齐；老计划里残留的「自动化用例」「人工介入项」两段顺手删掉并在草案说明一句（用例归 `/xz-exec` 3.5 现场生成）。

### 第三步：读取并展示当前 todolist

读取 N-PLAN.md 文件，展示当前所有条目及状态：

```
当前 todolist (版本 N):
  [x] #1 创建 User model           ← 已完成，锁定
  [x] #2 实现注册接口               ← 已完成，锁定
  [ ] #3 实现登录接口               ← 可修改
  [ ] #4 JWT 中间件鉴权             ← 可修改
	  [ ] #5 添加单元测试               ← 可修改
```

### 第四步：锁定检查

**铁律：已完成的 `[x]` 条目不可修改、不可删除。**

如果用户的操作描述涉及 `[x]` 条目，**立即拒绝**并说明：

> #N 已完成，无法修改/删除。已完成的条目受锁定保护。

### 第五步：解析用户操作意图

根据操作描述，判断属于以下哪种操作（可以组合）：

- **操作 A：修改已有条目** — 用户指定编号（如 "修改 #3"）；检查该编号是否为 `[ ]` 状态；生成修改后的条目内容（标题 + 改动详情）
- **操作 B：新增条目** — 在末尾追加，或在指定位置插入（如 "在 #2 后插入"），插入后后续条目编号自动递增；新条目必须包含完整的 改动详情
- **操作 C：删除条目** — 用户指定编号（如 "删除 #4"）；检查该编号是否为 `[ ]` 状态；删除后后续条目编号自动递减

### 第六步：理解 + 澄清（有歧义/选择空间才做，无则跳过）

与 `/xz-plan` 第 3 步同构。**简单无歧义的增删改**（删 #4、改一句描述文字、纯位置调整）→ **跳过本步**直接进第七步草案。只要本次操作命中下列任一，就先在**同一条回复**里输出「①我的理解 + ②未澄清清单」、末尾一次**纯文本**提问（禁用 AskUserQuestion——其弹窗会吞掉前面文本），等用户回复后再出草案：

1. 改动涉及技术方向选择（换库/换协议/换数据结构/实现路径不止一种）；
2. 操作描述里的字段/状态/枚举/key 含义、取值范围、边界、验收没说清；
3. 需求内部矛盾、或与现有条目/代码/已确认约束冲突；
4. 改动会连带影响其他已有条目。

**① 我的理解**：一句话复述本次要改哪些条目、怎么改（与第七步变更草案要点对齐）。

**② 未澄清清单（无则整段省略）**：技术方向选择 + 需求约束合到一张清单、**整段从 1 连续编号**，单项选项 ≤4。**排版与第八·五步同一套卡片式**（见那一节的五段骨架）。

**段首给总览表**（3 项以上必给，1-2 条简单项可省），回复行把推荐组合的等价展开写出来：

```
未澄清清单  →  回「全部默认」= 1a 2a

| # | 优先级  | 一句话                 | 推荐动作      |
|---|---------|-----------------------|---------------|
| 1 | 🔴 高   | 缓存换 Redis 还是留本地 | a 留本地      |
| 2 | 🟠 中   | 新字段默认值取什么      | a 空字符串    |
```

每项格式（**标签后补空格让字段值起始列对齐**）：

```
编号. 🔴 高 · 一句话问题
     现状  当前代码/条目/需求的实际情况（带 file:line）
     a. 短方案名 ✅推荐（理由/依据）  b. 短方案名
```

优先级用 `🔴 高` / `🟠 中` / `🟡 低`（emoji 与文字都要）。`a` 固定放推荐项、标记写在方案名之后（技术方向给理由、需求约束给依据）。打标签并**从高到低排序**：`🔴 高` = 选错大幅改变改动范围/返工成本高；`🟠 中` = 只影响局部条目或某分支；`🟡 低` = 边角细节。技术方向多属高、自然靠前 = 先定大方向。

**技术方向选择若需展开对比**（尤其连带影响多个已有条目）：在该项 `现状` 下补一张小表即可，**不要另起「方案 A/B」大段**——选择仍走清单里的 a/b。表按维度横向对比，比逐选项分块更适合「连带影响哪些条目」这种多维比较：

```markdown
| 维度 | a. 方案名 ✅推荐 | b. 方案名 |
|------|----------------|-----------|
| 改动条目 | 改 #3、新增 #6 | 改 #3、改 #4(连带)、新增 #6 |
| 改动量 | 2 条 | 3 条 |
| 对已有条目影响 | 无 | #4 需连带修改 |
```

表后补一行 `差异  a 得到什么/放弃什么；b 反之` 收口。**排版硬闸同第八·五步**：单条 ≤20 行、每个字段值 ≤2 行、禁连续 3 行以上散文块、量化数字不许埋在长句里。

**末尾一次提问（纯文本）**：
> 请一次回复：1) 理解准确？（`理解OK` / `理解需修正：xxx`）2) 未澄清各项（含技术方向与需求约束，`全部默认`用推荐 a，或按编号 `1a 2b 3a` 逐项覆盖）。示例：`理解OK 1a 2b`。

#### 澄清追问循环（答复后必做，与 `/xz-plan` 第 3 步同构）

一轮问答往往问不干净——用户定了某个方向后常会暴露新的待定点。所以：

- 用户答复后，把已定夺项（含选定的技术方向）并入「我的理解」；用户修正了理解 → 更新后**重出「我的理解」**，必要时重新对齐再问。
- 若答复**引出新歧义**（如选了 b 方案后暴露新的字段/边界待定）、**答复不完整**（有编号没回）、或**与已确认内容冲突** → **继续追问**：同格式再出一轮未澄清清单，**编号重新从 1 连号**，段首说明第几轮追问及触发原因。例：`第 2 轮追问（因选定方案 b 后，新增字段的默认值未定）：`
- **禁止带着未定项进第七步草案**；无剩余未澄清项时输出「澄清完毕，进入变更草案」再进第七步。

用户回复后，把理解 + 全部轮次的未澄清选择作为本次变更的既定前提，进第七步。**无歧义/无选择空间 → 整步跳过**，直接进第七步草案。

### 第七步：生成变更草案

基于第六步已确认的「理解 + 未澄清选择」（无澄清则按操作描述）生成。**先输出到对话中，不写文件！**

展示变更对比，格式：

```
变更对比 (版本 N):

  [锁定] #1 创建 User model         ✅ 已完成，不可变更
  [锁定] #2 实现注册接口             ✅ 已完成，不可变更
  [修改] #3 实现登录接口
    旧: JWT 签发，过期 24h
    新: JWT 签发 + Refresh Token，access 过期 1h，refresh 过期 7d
  [保留] #4 JWT 中间件鉴权           （无变化）
  [删除] #5 添加单元测试             ← 将被删除
  [新增] #5 添加 token 刷新接口      ← 新增条目

重编号后最终 todolist:
  [x] #1 创建 User model
  [x] #2 实现注册接口
  [ ] #3 实现登录接口 (已修改)
  [ ] #4 JWT 中间件鉴权
  [ ] #5 添加 token 刷新接口 (新增)
```

**同时输出改动前后对比草案**：基于本次变更后的 todolist，对照 N-PLAN.md 现有的 `## 改动前后对比`，输出新版「改动前/改动后」内容（基于实际代码、数据优先、不重复 todolist）。若本次变更不影响宏观效果（例如纯文字描述微调），可声明「改动前后对比无变化」。

```markdown
## 改动前后对比（草案）

改动前:
（原始现状）

改动后:
（变化后样子）
```

**手动路径的额外提示（只提示，不生成草案）**：若第二步判定这是手动路径，在变更草案末尾加一行 `⚠️ 本次改了 todolist，N-MANUAL.md 会跟着过时。写入 PLAN 后请跑 /xz-manual N sync 同步手动清单。`

**同时输出测试方案变更草案（必做，与 PLAN 变更草案一起展示）**：只说清**测试地基**要不要跟着变——

- 新增/修改条目引入新外部依赖（新表 / 新中间件 / 新第三方接口）→ 在「测试前置信息」加一项，并在第八步确认时**一并索取**（先自查 `.env` / `config/*` / `docker-compose.yml` / fixture，**找得到的不问**）；拿到的凭据只写进 `tests/.env.local`，PLAN 里只写引用
- 换技术栈或新增服务 → 同步更新「测试环境与命令」
- **不要在这里动用例** —— 用例的增删改、T 编号分配、产物归属全归 `/xz-exec` 3.5 按当下代码现场判定，在这里手工同步只会得到一份很快过期的清单
- 确实不影响测试地基 → 明写一句「测试方案无变化」，**不得省略本段**

**新增条目的粒度沿用 `/xz-plan` 第 4 步：竖着切一刀、别横着片一层** —— 一条 todo 是一条从入口打通到出口的完整链路，做完能被一条机器可判的用例盖住。

### 第八步：等待确认

在变更草案同一条回复末尾以纯文本提问确认（禁用 AskUserQuestion——其弹窗会吞掉同回复中前面的草案文本）：

> 以上变更是否确认？回复：
>   1) 确认更新 — 先做开发风险确认（第八·五步），再写入 N-PLAN.md（含更新后的测试方案）、刷新 STATE.md；执行方式你之后自己挑：/xz-exec N（串行）或 /xz-worktree N（多 agent 并行）
>   2) 确认更新并串行执行 — 先做开发风险确认，再写入并立即进入 /xz-exec N 流程（含完成后的自动闭环测试）
>   3) 确认更新并并行执行 — 先做开发风险确认，再写入并立即进入 /xz-worktree N 流程（多 agent 分组同时做，合并完再由 /xz-exec N 跑全量闭环）
>   4) 修改意见 — 调整后重新输出变更草案

**禁止自动写入文件。必须等待明确确认。** 用户选 `1` / `2` / `3` → 进第八·五步开发风险确认；选「修改意见」或给其他反馈 → 按反馈调整后重新输出草案（回第七步）。

### 第八·五步：开发风险确认（确认变更草案后、写文件前，强制独立一轮）

**触发**：用户在第八步选了 `1) 确认更新` / `2) 确认更新并串行执行` / `3) 确认更新并并行执行` 后，**先做这一轮再写文件**（与 `/xz-plan` 3.5 同构）；选「修改意见」则回第七步、不进本步。

**怎么做**：基于本次**已确认的变更 改动详情**对照风险清单逐项排查。**命中** = 本次改动真实触及该点 + 处理方式未定 + 不同处理有实质差异；命中即列、未命中维度不展示；即使能推断安全默认，也作为推荐 a 摆出让用户确认。

**风险清单**：安全（硬编码密钥、输入未校验、敏感信息泄露、鉴权缺失/绕过、弱加密）/ 性能（循环冗余、资源未释放、N+1、缺索引大表查询/缺分页、goroutine 泄漏）/ 数据与兼容（改字段历史数据、接口向后兼容、迁移与回滚）/ 并发时序（无锁共享、重试幂等、竞态）/ 错误处理（吞异常、错误丢上下文、失败回滚清理）/ 边界（空值/零值/负数/超大输入）/ 语言专项（Go 未检查 error return、缺超时、竞态；JS/TS XSS、eval、监听器/定时器未清理；SQL 拼接注入、过宽 GRANT、动态表名未白名单；Python async 夹同步阻塞、ORM N+1）。

**每条命中项**：打 `🔴 严重` / `🟠 高` / `🟡 中` / `⚪ 低` 标签（emoji 与文字都要，emoji 是终端里的扫读锚点）、**从严重到低排序**，每条末尾固定一个 `不处理/忽略` 逃生项。

> **排版：与第六步同一套卡片式** —— 段首回复行 + 总览表（3 项以上必给）、卡片标题行 `N. 🔴 严重 · 一句话问题`、定长字段区（`现在` / `改后` / `出事` / `但现在`，标签后补空格让字段值起始列对齐）、选项块（`做法` / `代价` / `结果`，推荐项固定 `a` 位、逃生项单行写完）、收口行 `取舍  …`；排版硬闸同样适用（单条 ≤20 行、每个字段值 ≤2 行、关键数字必须独占 `代价` 字段）。

**无命中**：输出「已逐项排查安全/性能/数据兼容/并发/错误处理/边界等维度，本次变更无需额外确认的开发风险」并直接进第九步。

**用户回复后**：把每项选定处理落地到第九步要写的 N-PLAN.md（约束 / 技术方案 / 对应条目 改动详情）；选「不处理/忽略」的不落地为改动，但在 约束 记一句「已确认接受 X 风险，本次不处理」留痕。然后进第九步写文件。

### 第九步：确认后更新文件

**先落地第八·五步确认的开发风险处理**（写进下面对应的 N-PLAN.md 约束/技术方案/改动详情），再按下列步骤写文件。

时间：`date "+%Y-%m-%d %H:%M:%S"`（写文件前调用）。

1. **更新 N-PLAN.md**：
   - 修改/新增/删除对应的 todolist 条目和 改动详情
   - 重新编号所有条目，保证连续（1, 2, 3, ...）
   - **同步更新「任务总结」章节** — 根据变更后的 todolist 重新生成自然语言总结，保持与条目一一对应
   - **同步刷新 `## 改动前后对比`** — 按第七步草案中确认过的「改动前/改动后」覆盖原有章节；若声明无变化则保留原内容
   - 按第七步草案更新 `## 测试方案` 三段（PLAN 原本没有则按 `/xz-plan` 4.5 三段补齐、老计划残留的用例段一并删掉；草案声明无变化则保留原内容）。用户给的凭据不写进 PLAN（只写来源），要落盘只放 `tests/.env.local` 并先确认 `.gitignore` 覆盖
   - **不写用例、不碰测试产物** —— 全归 `/xz-exec` 执行时管
   - **若 PLAN 原状态是 `待闭环测试` 且本次新增或修改了未完成条目 → 把 `> 状态:` 回置 `进行中`**（新条目还没实现，不能让 `/xz-exec` 跳过第四到第六步），并在第十步输出里说明状态已回置
   - 更新「最后更新」时间
   - 在「变更记录」中追加一行：`- YYYY-MM-DD HH:mm:ss 操作描述`

2. **刷新 STATE.md**：跑 `xz-tools.py update-state`。

**若用户选了带执行的路径**：STATE.md 刷新完成后直接接着执行，跳过下面第十步（由那个 skill 自己的流程接管后续询问）。

- 选 `2) 串行` → 按 `/xz-exec N` 完整流程走。它会按改动后的 todolist 现场生成用例表并跑闭环测试；已有 `N-TEST-REPORT.md` 时 T 编号沿用历史、本轮**全量重跑**全部用例。
- 选 `3) 并行` → 按 `/xz-worktree N` 完整流程走（分组、并行开发、边完成边合并），合并完它会把状态置 `待闭环测试` 并提示跑 `/xz-exec N` 收尾闭环。**切不出互不重叠的分组时它会自己退回串行。**

### 第十步：输出改动结果（仅「确认更新」路径）

整理并输出：
- 修改了哪些条目
- 新增了哪些条目
- 删除了哪些条目
- 手动清单要不要同步（手动路径 → 提示跑 `/xz-manual N sync`；常规路径 → 不涉及）
- 测试方案有没有跟着变（或「无变化」）
- 当前 todolist 总数和完成进度

然后以纯文本输出下一步选项：

## 关键规则

1. **已完成锁定** — `[x]` 条目绝不可修改或删除，这是铁律
2. **先输出后写文件** — 变更草案必须先展示、用户确认后才写入，**禁止自动写入**；草案是唯一的确认入口，所有 AI 判定和建议全写进草案，禁止在草案之前单独弹问；全程禁用 AskUserQuestion（其弹窗会吞掉同回复中前面的文本）
3. **落盘四件事** — 插入/删除后重新编号保持 1, 2, 3... 连续；新增/修改的条目必须包含完整的 改动详情；每次修改在变更记录中追加留痕；写完刷新 STATE.md
4. **澄清同 /xz-plan、循环递进追问到无问题** — 涉及技术方向选择（换库/协议/数据结构/多实现路径）、字段/边界/验收歧义、需求冲突、或连带影响其他条目时，第六步先出「①我的理解 + ②未澄清清单」：技术方向选择 + 需求约束合一张清单，每项 `🔴 高/🟠 中/🟡 低` + `现状` + a/b、整段连号、从高到低排序、**3 项以上给段首总览表**，纯文本确认，禁自行替用户选定；简单无歧义增删改跳过。技术方向需展开对比时在该项附小对比表 + `差异` 收口行，选择仍走 a/b。**答复后必须判断是否要再追一轮**：引出新歧义 / 答复不完整 / 与已确认内容冲突 → 同格式再出一轮（**编号重新从 1 连号**，段首标明第几轮及触发原因），直到无未澄清项；**全部定夺前禁止出变更草案**，澄清完毕先输出「澄清完毕，进入变更草案」。第六步与第八·五步的清单一律按**卡片式**排版：字段定长排布（`现在/改后/出事`、`做法/代价/结果`），**不许写成散文段落**，单条 ≤20 行、每个字段值 ≤2 行，**关键数字必须独占 `代价` 字段**——那是用户做选择的唯一依据
5. **开发风险独立一轮** — 变更草案确认后、写文件前（第八·五步），基于本次 改动详情 排查安全/性能/数据兼容/并发/错误处理/边界，命中即列、打 `🔴 严重/🟠 高/🟡 中/⚪ 低` 并从严重到低排序、每条末尾带 `不处理/忽略` 逃生项，用户 `1a 2b 3c` 确认；选定处理落地到 PLAN，选忽略的在 约束 留痕；无命中声明并直接写。与 `/xz-plan` 3.5 同构
6. **改动前后对比同步** — 修改/新增/删除影响宏观效果时，必须同步刷新 N-PLAN.md 的 `## 改动前后对比`；草案先在第七步对话里展示，第九步落盘时一并更新
7. **测试地基同步（只管地基，不管用例）** — 第七步必须展示「测试方案变更草案」（确实无影响则明写「测试方案无变化」，不得省略本段），第九步落盘时一并更新 `## 测试方案` 三段：新条目引入新外部依赖时在「测试前置信息」加项并在第八步一并索取，凭据只写 `tests/.env.local`、PLAN 里只写引用。**违规项：在本 skill 里增删改具体 T 用例、分配 T 编号、或动 `tests/T{编号}-*` 产物** —— 那全是 `/xz-exec` 3.5 执行时按当下代码现场判定的事
8. **守住边界与分工** — 严格按用户的操作描述范围调整，禁止顺手扩展到其他条目；手动路径（`N-MANUAL.md` 存在，或 PLAN 状态 `待手动执行`）只提示两句（草案末尾 + 第十步跑 `/xz-manual N sync`），**绝不生成、修改、重编号 `N-MANUAL.md`**；操作描述涉及修 bug / 排查异常时先建议用 `/xz-debug` 定位根因，再回来改条目
