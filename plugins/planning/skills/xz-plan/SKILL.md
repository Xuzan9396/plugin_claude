# XZ Plan - 创建新版本计划

参数 `$ARGUMENTS`：第一个空格前为版本号 N，之后为需求描述（`2 支持多语言` → N=2）。
任一不满足 → 停止并提示 `用法: /xz-plan N 需求描述`：`$ARGUMENTS` 为空 / N 非合法版本号（正整数，或小数如 1.5） / 需求为空。

**脚本**：`xz-tools.py`（`bin/` 已在 PATH，直接调用，在当前目录操作 `.xz_planning/`）。

## 前置检查

1. 无 `.xz_planning/` → 停止，提示 `请先执行 /xz-init`。
2. `xz-tools.py parse N`：`ok:true` → 停止，提示用 `/xz-update-plan N`；否则新建（`phase` 存在则复用目录）。

---

## 1. 调研（必做，不可跳过）

用 Glob/Read 深入需求模块，识别新建/修改文件与依赖。扫描排除 `.xz_planning/` 和 `.gitignore` 项。

**风险逐项排查（必做，结果暂存喂给第 3.5 步，本步不输出）**：读完代码后，对照第 3.5 步的风险清单（安全 / 性能 / 数据兼容 / 并发时序 / 错误处理 / 边界 / 语言专项）逐项过一遍本次改动，记下命中的点，留到方案确认后的 3.5 步逐项与用户确认处理方式。本步只排查、不提问、不输出。

## 2. 范围检查

- **多个独立子系统（无依赖）** → 停止，输出拆分建议，各走独立 `/xz-plan`。
- **Bug/排查类**（报错、异常、贴了堆栈/截图）→ 停止，提示先用 `xz-debug` 定位根因，**禁止凭猜测规划修复**。（性能/UX/重构/新增功能不算排查类。）

> ⚠️ **全程禁用 AskUserQuestion 等提问工具**：Claude Code 已知 bug——同一轮回复中提问弹窗之前的文本会被终端吞掉，用户会看不到理解/方案/草案。所有确认一律用纯文本提问，等用户回复。

## 3. 理解 + 澄清 + 方案（同一条回复批量输出，末尾一次提问）

调研后在**同一条回复**里依次输出 一、我的理解 → 二、技术选型 → 三、未澄清清单 → 四、方案，中间不插工具调用，末尾只问一次。**技术选型先于需求澄清**（先把技术大方向定下来，再澄清需求约束细节、给方案）；未澄清和理解一起出（不再分轮、不再后置），让用户一眼看清「AI 怎么选型 + 哪里不敢替用户定」。**已确认/能从代码稳定推断的关键点不单列**——直接并入「我的理解」的 Constraints/Done when，不再单设「已澄清清单」段。

> 技术选型与未澄清**共用一套连续编号**（选型占 1..k，未澄清接着 k+1..），用户末尾一次按全局编号回 `5a 6b` 即可，无需指明属于哪段。**开发风险不在本轮**——风险依附于具体实现方案，必须等方案确认后，在 **3.5 步单独一轮**逐项确认（3.5 是另一轮，编号自己从 1 重新连号）。

### 一、我的理解（四段，与最终 PLAN 同构）

```markdown
## 我的理解
- **Goal**：构建/修改什么、解决什么问题、期望效果
- **Context**：涉及文件（@路径）、文件夹、文档、错误日志
- **Constraints**：架构、标准、安全、编码规范、兼容性
- **Done when**：怎样算做完（测试通过 / 接口返回 X / bug 不复现）
```

### 二、技术选型（先定技术大方向；项目已固定则不列、直接并入理解的 Constraints）

只在**真有选择空间**时列：库/框架/架构/改法有多个可行选项、且会左右后续方案与改动量。**从 1 开始连续编号**（与下方未澄清清单共用一套连号，选型占 1..k）+ a/b/c 选项（`a` = 推荐，括号说理由），单项 ≤4。项目已固定、或代码现状只有一种合理选择的**不列**，直接把沿用的技术栈写进「我的理解」的 Constraints。例：
  `1. Web 框架  a. Gin（社区最大，推荐）  b. Echo  c. Fiber（最快但生态弱）`

### 三、未澄清清单（需求约束；不确定的不要擅自决定；紧跟选型一起输出，无歧义则整段省略）

**段首先给一句整体状态摘要**：哪些已定（从代码/用户已明确的，已并入「我的理解」）、还剩哪几项待定，让用户一眼知道全局进度。例：`状态：技术栈与缓存 key 已定，剩订单状态枚举、停机窗口 2 项待你确认。`

接着只列**真有歧义**的需求约束点，**编号接着技术选型连续往下排**（选型到 k，这里从 k+1 起），每点一条 + a/b/… 解读（`a` = 最可能/推荐，括号说依据），单项 ≤4。**每项必须先写一行「现状：」**说明当前代码/需求的实际情况，再给 a/b 选项，让用户基于现状判断。**重点必查（最容易被擅自决定的两处）**：
- **key·字段定义**：用户提到的字段名、参数、状态值、枚举、key 命名/格式，其**含义/类型/取值范围/单位**若没说清 → 列出问，**禁自行假定**。例：
  ```
  5. 「订单状态」枚举有哪些？
     现状：现有 orders 表 status 仅 待付/已付/取消三值，需求未提退款。
     a. 仅 待付/已付/取消（推荐，按现有表）  b. 另含 退款中
  ```
- **冲突**：发现 一是需求内部自相矛盾（如又要实时又要批量延迟）、二是需求与现有代码/数据/已确认约束相抵触 → **必须列出**，给「以谁为准」的 a/b 选项，**禁自行选边**。例：
  ```
  6. 需求要「不停机」但现表无在线改字段方案，冲突。
     现状：orders 表无在线 DDL 能力，改字段需锁表。
     a. 加临时双写过渡（推荐）  b. 接受一次停机窗口
  ```

> **开发风险不在本轮**：开发后高概率出问题的安全/性能/数据兼容/并发/错误处理等隐藏坑，统一放到方案确认后的 **3.5 步**独立排查确认——那时方案已定，风险才查得准。本轮别把它们混进来。

铁律：技术选型与未澄清需求约束都只列真有歧义/真有选择空间的；用户已明确、或能从代码现状推断的**不列**（已明确的并入「我的理解」），无则各自整段省略。选型问「技术选哪个」、需求约束问「需求怎么解读」，两段各自归位别混写、但共用一套连续编号。凡会影响技术选型或需求解读的未确认点，必须在对应段列全；开发风险一律留到 3.5 步，不在此轮。

### 四、方案

基于技术选型的选定项 + 未澄清清单的推荐解读（每项默认取 a）给方案：单方案写思路；多方案列 A/B/C，附对比表（改动范围/开发量/性能/可维护性/扩展性）+ 推荐理由。若技术选型或未澄清里有会左右方案走向的歧义，注明「方案基于推荐解读，若你改选会相应调整」。

方案铁律：来自代码分析不凭空凑数；多方案须有实质差异（库/架构/改法）；最多 3 个；优缺点量化（如 `改 3 文件约 45 行`），禁"性能好"这类空话。

### 批量提问（纯文本）

理解 + 技术选型 + 未澄清清单 + 方案输出完，同一条回复末尾一次提问——
> 请一次回复：1) 理解准确？（`理解OK` / `理解需修正：xxx`）2) 选型与未澄清各项（共用连号，`全部默认`用推荐 a，或按全局编号 `1a 2b 5a 6b` 逐项覆盖）3) 方案选择？（多方案 `方案A/B/C` 或提替代；单方案回 `继续`）。示例：`理解OK 1a 2b 5a 方案A`。

用户改了理解/选型/未澄清选择/方案 → 把结论并入「我的理解」的 Constraints/Done when（含选定技术栈），更新方案后重出，必要时重新对齐。

## 3.5 开发风险确认（方案确认后强制独立一轮）

**触发时机（强制）**：用户在第 3 步确认了理解 + 技术选型 + 需求澄清 + 方案之后，**必须单独再发一轮**做这件事——不得与第 3 步合并，也不得跳过直接进第 4 步草案。方案未确认前不做（风险依附具体实现，方案没定查不准）。

**怎么做**：基于**已选定的方案**，对照下面这份风险清单逐项排查本次改动。**命中**＝方案真实触及该点（不是文件里不存在的假想风险）＋ 用户没说清怎么处理 ＋ 不同处理方式有实质实现差异。命中即列，未命中维度不展示。**不因"能推断出一个安全默认"而跳过**——把安全默认作为推荐 a 摆出来让用户一次确认（这就是提前预防：与其开发完返工，不如规划时先定）。

**每条命中项必须评严重度并排序**：给每条打 `严重 / 高 / 中 / 低` 标签，输出时**从严重到低排序**（严重在最前）。判级标准：
- **严重** — 安全漏洞 / 数据丢失或损坏风险（如注入、鉴权绕过、重试重复写、迁移丢数据）
- **高** — 明显影响可靠性或性能（如资源泄漏、N+1、缺超时、错误被吞）
- **中** — 影响代码质量或可维护性（如边界未处理、错误丢上下文）
- **低** — 可选优化（如日志、命名、小幅冗余）

**风险清单（提前预防）：**
- **安全**：硬编码密钥/token、输入未校验就用（用户输入 / 外部接口返回 / URL 参数）、敏感信息泄露到日志/错误消息/响应字段、权限鉴权缺失或绕过、弱加密（MD5/SHA1 存密码）
- **性能**：循环内冗余计算、资源未释放（连接/文件句柄/监听器/定时器）、大对象拷贝、N+1 查询、缺索引大表查询 / 缺分页、goroutine 泄漏
- **数据与兼容**：新增/改字段历史数据怎么处理、接口/协议向后兼容、迁移与回滚
- **并发/时序**：共享状态无锁、重试幂等、竞态
- **错误处理**：吞异常/空 catch、错误丢上下文、失败回滚与清理
- **边界**：空值/空集合/零值/负数/超大输入
- **语言专项**（按文件后缀匹配）：Go—未检查的 error return、`net/http` 未设超时、竞态；JS/TS—`innerHTML`/`dangerouslySetInnerHTML`(XSS)、`eval`、监听器/定时器未清理；SQL—字符串拼接注入、过宽 GRANT、动态表名未白名单；Python—async 中夹同步阻塞、ORM N+1

**输出与回复格式**（每条 = `[严重度]` + 一句风险现象 + a/b 处理方式 + **末尾固定一个 `不处理/忽略` 逃生项**，`a` = 推荐的安全处理；**从严重到低排序**；3.5 是独立一轮，编号自己从 1 连号）：

逃生项放每条最后一个字母（如已有 a/b 则为 `c`，只有 a 则为 `b`），统一写「不处理/忽略（本次不动，明确接受该风险）」，让用户对低价值或越界的风险点能一键跳过。

```
开发风险确认（按严重度排序，请逐项回复怎么处理，如 `1a 2b 3c`，全用推荐回 `全部默认`）：
1. [严重] 失败重试可能重复写 → a. 仅查询类重试（推荐，避免重复写入）  b. 写请求重试 + 业务幂等 key  c. 不处理/忽略（明确接受该风险）
2. [高] 新接口入参未见校验 → a. 入口统一校验非空+格式（推荐，防脏数据）  b. 仅依赖下游兜底  c. 不处理/忽略（明确接受该风险）
3. [中] 新增 status 字段历史行为空 → a. 迁移补默认值（推荐，避免空值分支）  b. 运行时兼容 null  c. 不处理/忽略（明确接受该风险）
```

**无命中**：输出「已逐项排查安全/性能/数据兼容/并发/错误处理/边界等维度，本次改动无需额外确认的开发风险」并直接进第 4 步。

**用户回复后**：把每项选定的处理方式并入「我的理解」的 Constraints / 技术方案，并**必须在第 4 步草案 todolist 的 change details 里落地**（如"入口加校验"要成为某条 todo 的具体改动点），不得只确认不落地，然后进第 4 步。**选「不处理/忽略」的项**不落地为 todo，但在 Constraints 里记一句「已确认接受 X 风险，本次不处理」留痕，避免后续误以为漏掉。

## 4. 生成草案（先输出对话，不写文件）

**输出顺序（硬性，违反即重来）**：所有工具调用（`date`、补读代码等）必须先做完，然后在**同一条回复**里依次输出——一、草案全文（按下方模板逐字写出，含每条 todo 的 change details）→ 二、4.5 测试方案 → 三、第 5 步文本确认提问。三者全是终端文本、连续输出、中间不得再插任何工具调用；禁止只发提问不发草案，禁止用「计划已生成」之类的摘要代替全文。用户必须先在终端看到完整计划，才轮到确认是否写入/执行。

时间：`date "+%Y-%m-%d %H:%M:%S"`（在输出草案前调用）。

**章节规则**：Goal 写做啥；Context 放涉及文件 + 用户贴的代码/日志/链接（**原文保留禁止总结**），无则写「无」；Constraints 写约束，无则「无」；Done when 写可验证标准。

**3.5 风险处理必须落地**：3.5 步用户确认的每项风险处理方式，必须体现到 Constraints / 技术方案 / 对应 todo 的 change details 中，不得只确认不落地。

**change details**：修改标 `path:起始-结束行` + `(现:摘要)`（行号必 Read 确认，禁猜）；新建不标行号但列函数/类/常量名；超 30 行拆子区域。**粒度**：每条 2-5 分钟、可独立验证、一个功能单元一条。

````markdown
# 版本 N: 中文需求名（10-25 字，与目录名同步）

> 创建时间: YYYY-MM-DD HH:mm:ss
> 最后更新: YYYY-MM-DD HH:mm:ss
> 状态: 待执行

## Goal
做什么、解决什么问题、期望效果。

## Context
> 无则写「无」。
- 相关文件/文件夹：@路径
- 引用代码/数据/日志：用户原文片段（代码块包住，禁止总结）
- 外部链接/文档、业务背景/术语

## Constraints
架构、标准、安全、编码规范、兼容性。无则「无」。

## Done when
完成标准（测试通过 / 接口返回 X / bug 不复现）。

## 技术方案
选定方案及理由。

## Todolist

- [ ] 1. 任务标题

  **Files:**
  - Create: `path`
  - Modify: `path:42-58`

  ```
  change details:
  新建: path → 导出的函数/常量/类型
  修改: path:42-58 (现:摘要, 改后:目标) → 具体改动点
  ```
----------------------
- [ ] 2. ...

## 总结
共 N 条，涉及 X 文件（新建 Y，修改 Z）。逐条一句：做什么、涉及文件、关键函数、改成什么样。

## 改动前后对比
基于实际代码/数据，直观展示宏观变化（有数据贴数据、有请求贴请求响应、可用终端图示），不重复 todolist。
改动前：（现状）
改动后：（变化后）

## 变更记录
- YYYY-MM-DD HH:mm:ss 初始创建
````

## 4.5 测试方案（仅对话，不入文件）

草案后额外输出，帮用户自测，**不写进 PLAN.md**：

```markdown
## 测试方案（对话参考）
**目前情况** / **前置条件** / **操作步骤**（可直接执行的命令，敏感信息只写引用如「见 .env」）/ **预期结果**
```

来自草案推导、覆盖主要改动路径，只给人工跑一遍的指引，不涉及自动化循环。

## 5. 确认（纯文本提问，禁用提问工具）

**禁止调用 AskUserQuestion**（其弹窗会吞掉同回复中前面的草案文本）。在草案全文 + 测试方案之后、同一条回复末尾直接以文本提问：

> 以上计划是否确认？回复数字：
>   1) 确认写入 — 写 N-PLAN.md，等手动调 `/xz-exec N`
>   2) 确认写入并直接执行 — 写入后立即进入 `/xz-exec N` 流程
>   3) 手动执行 — 写 N-PLAN.md（状态置待手动执行）+ N-MANUAL.md，AI 不碰源码
>   4) 修改意见 — 说明调整点后重出

「修改意见」→ 按反馈调整后重出草案。

## 6. 写入文件

目录已存在直接写 `N-PLAN.md`；否则新建 `.xz_planning/phases/N.中文名/`（`中文名` 10-25 字，含「改动对象+动作+关键差异」，禁空格与 `/\:*?"<>|`、首字符禁用数字（与版本号小数解析冲突），禁单用「优化/重构」等泛词，如 `订单表加软删除兼容取消流程`）。按第 5 步选择分支：

**1) 确认写入** → 写 PLAN（状态 `待执行`）→ `xz-tools.py update-state` → 第 7 步。

**2) 确认写入并直接执行** → 写 PLAN（状态 `待执行`）→ `xz-tools.py update-state` → 直接按 `/xz-exec N` 完整流程接着执行，跳过第 7 步。

**3) 手动执行** → 写 PLAN 但状态设为 **`待手动执行`**（这是 xz-exec 进入「校验模式」的触发标记）→ 同目录生成 `N-MANUAL.md`（格式见下）→ **AI 绝不改源码、不勾选 todo** → `xz-tools.py update-state` → 输出：
```
已写入 N-PLAN.md（待手动执行）+ N-MANUAL.md
```

````markdown
做什么：新增重试工具 Retry()，供登录失败时调用。整个文件新建，不动其他文件。
```go
package util

import "time"

// Retry 执行 fn，失败则重试，最多 attempts 次，每次间隔 delay。
// 例: Retry(3, 2*time.Second, login) → 失败时最多试 3 次，总耗时约 0s/2s/4s 三档。
func Retry(attempts int, delay time.Duration, fn func() error) error {
	var err error
	for i := 0; i < attempts; i++ {
		// fn 成功立即返回；失败记录 err 进入下一轮
		if err = fn(); err == nil {
			return nil
		}
		time.Sleep(delay) // 每轮间隔: delay=2s → 第2次在2s后、第3次在4s后
	}
	return err // 全部失败，返回最后一次的错误
}
```
````
