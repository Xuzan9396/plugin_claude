# XZ Plan - 创建新版本计划

参数 `$ARGUMENTS`：第一个空格前为版本号 N，之后为需求描述（`2 支持多语言` → N=2）。
任一不满足 → 停止并提示 `用法: /xz-plan N 需求描述`：`$ARGUMENTS` 为空 / N 非合法版本号（正整数，或小数如 1.5） / 需求为空。

**脚本**：`xz-tools.py`（`bin/` 已在 PATH，直接调用，在当前目录操作 `.xz_planning/`）。

## 前置检查

1. 无 `.xz_planning/` → 停止，提示 `请先执行 /xz-init`。
2. `xz-tools.py parse N`：`ok:true` → 停止，提示用 `/xz-update-plan N`；否则新建（`phase` 存在则复用目录）。

---

## 1. 调研（必做，不可跳过）

用 Glob/Read 深入需求模块，识别新建/修改文件与依赖。扫描排除 `.xz_planning/` 和 `.gitignore` 项。

**测试上下文扫描（必做，结果暂存喂给第 4.5 步，本步不输出）**：读需求模块的同时顺带摸清「这个项目怎么跑测试」，供第 4.5 步写出真能执行的命令，禁止到 4.5 步凭空编命令。扫描内容：
- **已有测试文件**：Glob `**/test_*.py`、`**/*_test.py`、`**/*.test.ts`、`**/*.spec.ts`、`**/__tests__/*`、`**/*_test.go`、`**/tests/**`、`**/spec/**`
- **框架与运行命令**：找到测试文件则读 1-2 个代表性文件，识别 pytest / unittest / jest / vitest / go test / 其他，以及实际运行命令（`pytest -v`、`npm test`、`go test ./...`）和可复用的 fixtures/mock/测试数据库
- **测试配置**：`pytest.ini`、`pyproject.toml`、`setup.cfg`、`jest.config.*`、`vitest.config.*`、`Makefile`（test target）、`docker-compose.yml`（测试依赖服务）
- **服务启动方式**：入口文件、启动命令、默认端口、依赖的数据库/缓存怎么起
- **无任何测试框架**：同样记录下来，第 4.5 步走临时脚本路线（脚本落在 `.xz_planning/phases/N.xxx/tests/`）

**风险逐项排查（必做，结果暂存喂给第 3.5 步，本步不输出）**：读完代码后，对照第 3.5 步的风险清单（安全 / 性能 / 数据兼容 / 并发时序 / 错误处理 / 边界 / 语言专项）逐项过一遍本次改动，记下命中的点，留到澄清完毕后的 3.5 步逐项与用户确认处理方式。本步只排查、不提问、不输出。

## 2. 范围检查

- **多个独立子系统（无依赖）** → 停止，输出拆分建议，各走独立 `/xz-plan`。
- **Bug/排查类**（报错、异常、贴了堆栈/截图）→ 停止，提示先用 `xz-debug` 定位根因，**禁止凭猜测规划修复**。（性能/UX/重构/新增功能不算排查类。）

> ⚠️ **全程禁用 AskUserQuestion 等提问工具**：Claude Code 已知 bug——同一轮回复中提问弹窗之前的文本会被终端吞掉，用户会看不到理解/澄清/草案。所有确认一律用纯文本提问，等用户回复。

## 3. 理解 + 澄清（同一条回复批量输出，末尾一次提问；答复后有新问题继续追问）

调研后在**同一条回复**里依次输出 一、我的理解 → 二、未澄清清单，中间不插工具调用，末尾只问一次。**不单独输出方案对比段**——实施方案/技术方向选择本质也是「让用户在 a/b 里选」，直接作为未澄清清单里的一项混排。**已确认/能从代码稳定推断的关键点不单列**，直接并入「我的理解」的 约束/完成标准（不设「已澄清清单」段）。

> 未澄清清单**整段从 1 连续编号**（方案项 + 约束项混排、按高/中/低排序），用户末尾一次按编号回 `1a 2b 3a` 即可。**开发风险不在本轮**——风险依附于具体实现，必须等澄清完毕后在 **3.5 步单独一轮**确认（编号从 1 重新连号）。

### 一、我的理解（四段，与最终 PLAN 同构）

```markdown
## 我的理解
- **目标**：构建/修改什么、解决什么问题、期望效果
- **上下文**：涉及文件（@路径）、文件夹、文档、错误日志
- **约束**：架构、标准、安全、编码规范、兼容性
- **完成标准**：怎样算做完（测试通过 / 接口返回 X / bug 不复现）
```

### 二、未澄清清单（实施方案/技术方向选择 + 需求约束；按高/中/低排序；无则整段省略）

**段首先给一句整体状态摘要**：哪些已定（从代码/用户已明确的，已并入「我的理解」）、还剩哪几项待定，让用户一眼知道全局进度。例：`状态：缓存 key 已定，剩缓存存储选型、订单状态枚举、停机窗口 3 项待你确认。`

把两类「需要用户在 a/b 里定夺」的点合到这一张清单、**整段从 1 连续编号**，单项选项 ≤4：
- **实施方案/技术方向选择**：库/框架/架构/改法有多个可行方向、会左右改动范围与开发量的，列出让用户选。选项来自代码分析、不凭空凑数，各选项须有实质差异，括号内给**量化差异**（如 `改 2 文件约 20 行`），禁"性能好"这类空话；**禁止只丢方案名词**，按下方展开格式给 做法/举例/差异，做法**技术专有词与大白话并用**（术语给判断依据，大白话保证一眼看懂）。项目已固定、或只有一种合理改法的**不列**，直接写进「我的理解」的 约束。
- **需求约束**：真有歧义的约束/边界/验收解读、需求内部矛盾或与现状冲突，列出让用户定（`a` 放最可能的解读，括号说依据）。

**每项格式**：`编号. [高/中/低] 一句话问题` → 换行 `现状：当前代码/需求的实际情况` → 选项。**推荐项固定放 `a` 位、括号必须带「推荐」二字**（如 `a. xxx（推荐，理由）`），保证用户回 `全部默认` = 全选 a 即最优组合。选项分两种写法：
- **简单项**（选项字面自明，如枚举取值、要不要兼容 null）：一行并排 `a. xxx（推荐…）  b. xxx`。
- **方案类/不直观项**（实施方案/技术方向选择，或任何选项名词字面看不懂的）：**每个选项独立成块**，按「方案类选项展开格式」写——
  ```
  a. 方案名（推荐，理由 + 量化：改 X 文件约 Y 行）
     做法：技术表述说改哪里、怎么改（准确专有词：模式/库/接口/函数名）；大白话：一句说人话的效果
     举例：一个具体例子直观展示改动前后的效果/数据/调用方式
  b. 方案名（量化）
     做法：…；大白话：…
     举例：…
  差异：一两句点破 a/b 的本质取舍（选 a 得到什么/放弃什么，选 b 反之）
  ```

**优先级 + 排序（必做）**：每项打标签并**从高到低排序**——`高` = 选错会大幅改变实施方向/返工成本高（多数方案选择、核心字段定义、需求冲突）；`中` = 只影响局部实现或某分支；`低` = 边角细节。方案类多属高、自然靠前 = 先定大方向。

**重点必查（最容易被擅自决定的两处，必列不得自行定）**：
- **key·字段定义**：用户提到的字段名、参数、状态值、枚举、key 命名/格式，其**含义/类型/取值范围/单位**若没说清 → 列出问，**禁自行假定**（如「订单状态枚举有哪些？现状：现有表仅三值，需求未提退款 → a. 按现有表 b. 另含退款中」）。
- **冲突**：需求内部自相矛盾（如又要实时又要批量延迟），或需求与现有代码/数据/已确认约束相抵触 → **必须列出**，给「以谁为准」的 a/b 选项，**禁自行选边**。

完整格式示例（方案类选项按展开格式写，简单项一行并排即可）：
  ```
  1. [高] 改法选哪种？
     现状：解析逻辑散落 3 处、重复约 60 行，最小改动与结构化归一均可行。
     a. 最小改动（推荐，改 2 文件约 20 行，风险小）
        做法：在 3 处解析函数内各加新字段的分支判断，不动调用链与现有结构；大白话：哪儿缺补哪儿，不动架构。
        举例：parse_order() 里加 2 行 if 就能读到新字段 refund_at，另外 2 处同样各加 2 行。
     b. 结构化归一（抽公共模块，改 5 文件约 120 行，扩展性好）
        做法：按单一职责抽公共 parser 模块，3 处散落逻辑收敛为统一入口 parser.Parse()；大白话：把重复解析收拢成一处维护。
        举例：新建 parser.go 后，3 处原本各约 20 行的解析都变成 1 行 parser.Parse(raw)；以后加字段只改 parser.go 一处。
     差异：a 马上能用但重复代码还在、下次加字段要改 3 处；b 一次多花 120 行，以后每加一个字段只改 1 处。
  ```

铁律：只列真有歧义/真有选择空间的；用户已明确、或能从代码现状推断的**不列**（并入「我的理解」），无则整段省略。凡影响实施方向或需求解读的未确认点必须列全、打好标签、从高到低排序；开发风险一律留到 3.5 步。

### 批量提问（纯文本）

理解 + 未澄清清单输出完，同一条回复末尾一次提问——
> 请一次回复：1) 理解准确？（`理解OK` / `理解需修正：xxx`）2) 未澄清各项（含实施方案与需求约束，`全部默认`用推荐 a，或按编号 `1a 2b 3a` 逐项覆盖）。示例：`理解OK 1a 2b`。

### 澄清追问循环（答复后必做）

- 用户答复后，把已定夺项（含选定实施方向/技术栈）并入「我的理解」的 约束/完成标准；用户修正了理解 → 更新后重出「我的理解」，必要时重新对齐。
- 若答复**引出新歧义**（如选定某方向后暴露新的待定点）、答复不完整、或与已确认内容冲突 → **继续追问**：同格式再出一轮未澄清清单（编号重新从 1 连号，段首说明第几轮追问及触发原因），直到无未澄清项。
- **禁止带着未定项进 3.5 / 第 4 步**；无剩余问题时输出「澄清完毕，进入开发风险确认」并进 3.5。

## 3.5 开发风险确认（澄清完毕后强制独立一轮）

**触发时机（强制）**：第 3 步（含追问轮）全部定夺之后**单独再发一轮**——不得与第 3 步合并，不得跳过直接进第 4 步；澄清未完毕前不做（实施方向没定，风险查不准）。

**怎么做**：基于**已定夺的实施方向**对照下面的风险清单逐项排查。**命中**＝改动真实触及该点（非假想风险）＋ 用户没说清怎么处理 ＋ 不同处理方式有实质差异。命中即列，未命中维度不展示。**能推断出安全默认也不跳过**——把它作为推荐 a 摆出来让用户一次确认。

**每条命中项必须评严重度并排序**：给每条打 `严重 / 高 / 中 / 低` 标签，输出时**从严重到低排序**（严重在最前）。判级标准：
- **严重** — 安全漏洞 / 数据丢失或损坏风险（如注入、鉴权绕过、重试重复写、迁移丢数据）
- **高** — 明显影响可靠性或性能（如资源泄漏、N+1、缺超时、错误被吞）
- **中** — 影响代码质量或可维护性（如边界未处理、错误丢上下文）
- **低** — 可选优化（如日志、命名、小幅冗余）

**风险清单（提前预防）：**
- **安全**：硬编码密钥/token、输入未校验就用（用户输入 / 外部接口返回 / URL 参数）、敏感信息泄露到日志/错误消息/响应字段、权限鉴权缺失或绕过、弱加密（MD5/SHA1 存密码）
- **性能**：循环内冗余计算、资源未释放（连接/文件句柄/监听器/定时器）、大对象拷贝、N+1 查询、缺索引大表查询 / 缺分页、goroutine 泄漏
- **数据与兼容**：新增/改字段历史数据怎么处理、接口/协议向后兼容、迁移与回滚
- **并发/时序**：共享状态无锁、重试幂等、竞态
- **错误处理**：吞异常/空 catch、错误丢上下文、失败回滚与清理
- **边界**：空值/空集合/零值/负数/超大输入
- **语言专项**（按文件后缀匹配）：Go—未检查的 error return、`net/http` 未设超时、竞态；JS/TS—`innerHTML`/`dangerouslySetInnerHTML`(XSS)、`eval`、监听器/定时器未清理；SQL—字符串拼接注入、过宽 GRANT、动态表名未白名单；Python—async 中夹同步阻塞、ORM N+1

**输出与回复格式**（每条 = `[严重度]` + 一句风险现象 + a/b 处理方式 + **末尾固定一个 `不处理/忽略` 逃生项**，`a` = 推荐的安全处理；**从严重到低排序**；3.5 是独立一轮，编号自己从 1 连号）：

逃生项放每条最后一个字母（如已有 a/b 则为 `c`，只有 a 则为 `b`），统一写「不处理/忽略（本次不动，明确接受该风险）」，让用户对低价值或越界的风险点能一键跳过。

```
开发风险确认（按严重度排序，请逐项回复怎么处理，如 `1a 2b 3c`，全用推荐回 `全部默认`）：
1. [严重] 失败重试可能重复写 → a. 仅查询类重试（推荐，避免重复写入）  b. 写请求重试 + 业务幂等 key  c. 不处理/忽略（明确接受该风险）
2. [高] 新接口入参未见校验 → a. 入口统一校验非空+格式（推荐，防脏数据）  b. 仅依赖下游兜底  c. 不处理/忽略（明确接受该风险）
3. [中] 新增 status 字段历史行为空 → a. 迁移补默认值（推荐，避免空值分支）  b. 运行时兼容 null  c. 不处理/忽略（明确接受该风险）
```

**无命中**：输出「已逐项排查安全/性能/数据兼容/并发/错误处理/边界等维度，本次改动无需额外确认的开发风险」并直接进第 4 步。

**用户回复后**：把每项选定的处理方式并入「我的理解」的 约束 / 技术方案，并**必须在第 4 步草案 todolist 的 改动详情 里落地**（如"入口加校验"要成为某条 todo 的具体改动点），不得只确认不落地，然后进第 4 步。**选「不处理/忽略」的项**不落地为 todo，但在 约束 里记一句「已确认接受 X 风险，本次不处理」留痕，避免后续误以为漏掉。

## 4. 生成草案（先输出对话，不写文件）

**输出顺序（硬性，违反即重来）**：工具调用（`date`、补读代码等）全部前置做完，然后在**同一条回复**里连续输出——一、草案全文（按下方模板逐字写，含每条 todo 的 改动详情）→ 二、4.5 测试方案 → 三、第 5 步确认提问，中间不得再插工具调用；禁止只发提问不发草案，禁止用「计划已生成」之类的摘要代替全文。

时间：`date "+%Y-%m-%d %H:%M:%S"`（在输出草案前调用）。

**章节规则**：目标 写做啥；上下文 放涉及文件 + 用户贴的代码/日志/链接（**原文保留禁止总结**），无则写「无」；约束 写约束，无则「无」；完成标准 写可验证标准。

**改动详情**：修改标 `path:起始-结束行` + `(现:摘要)`（行号必 Read 确认，禁猜）；新建不标行号但列函数/类/常量名；超 30 行拆子区域。**粒度**：每条 2-5 分钟、可独立验证、一个功能单元一条。

## 4.5 自动化闭环测试方案（对话展示 + 写入文件）

测试方案是草案及最终 `N-PLAN.md` 的固定章节，也是 `/xz-exec` 第七步**闭环测试**的执行依据：草案里完整展示，确认后原样写入 PLAN 的 `## 测试方案`，不得省略或只留在对话里。内容来自草案推导 + 第 1 步的测试上下文扫描，覆盖全部改动路径，**目标是 AI 能全自动跑完并自判通过与否**，而不是给人照着点一遍。

### 三类判据（缺一类就会卡住闭环）

| 类别 | 判据 | 处理 |
|------|------|------|
| **自动化用例** | AI 能用一条命令跑出**机器可判定结果**：单测/集成测试、接口 curl + 断言、CLI 输出比对、脚本、数据库查询校验、浏览器操作（**用 `xz-cdp-cli` skill 驱动 Chrome**） | 直接跑 |
| **测试前置信息** | AI **能跑，只是缺参数**：数据库/Redis/MQ 连接串、外部 API base URL + token、测试账号、环境变量、seed 数据来源、本地依赖实例 | 本轮问清 → 写进 `tests/.env.local` → 执行时自动注入，一路跑完 |
| **人工介入项** | AI **客观做不到**，仅限：真实凭证/密钥/第三方账号、线上或预发环境、真机硬件（摄像头/麦克风/推流/移动设备）、多端多人同时操作、破坏性操作（删生产数据、发真实短信/支付）、业务方主观确认的视觉与体验判断 | 执行时停下请人做或确认 |

**判定铁律**：
- 能用 `xz-cdp-cli` 驱动浏览器完成的 UI 操作 **不算**人工项；
- 「麻烦」「要起服务」「要造测试数据」**不算**人工项——AI 自己起服务、自己造数据；
- **缺连接信息 ≠ 人工介入项**——那是「测试前置信息」：给了参数 AI 自己就能跑完，别写成"这事你来做"；
- 把能自动化的写成人工项 = 违规，必须重写。

### 四段格式


````markdown
## 改动 2 ｜ 新建 `src/util/retry.go`
做什么：新增重试工具 Retry()，供登录失败时调用。整个文件新建，不动其他文件。
```go
package util

import "time"

// Retry 执行 fn，失败则重试，最多 attempts 次，每次间隔 delay。
// 例: Retry(3, 2*time.Second, login) → 失败时最多试 3 次，总耗时约 0s/2s/4s 三档。
func Retry(attempts int, delay time.Duration, fn func() error) error {
	var err error
	for i := 0; i < attempts; i++ {
		// fn 成功立即返回；失败记录 err 进入下一轮
		if err = fn(); err == nil {
			return nil
		}
		time.Sleep(delay) // 每轮间隔: delay=2s → 第2次在2s后、第3次在4s后
	}
	return err // 全部失败，返回最后一次的错误
}
```
````
