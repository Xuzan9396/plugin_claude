# XZ Plan - 创建新版本计划

参数 `$ARGUMENTS`：第一个空格前为版本号 N，之后为需求描述（`2 支持多语言` → N=2）。
任一不满足 → 停止并提示 `用法: /xz-plan N 需求描述`：`$ARGUMENTS` 为空 / N 非正整数 / 需求为空。

**脚本**：`xz-tools.py`（`bin/` 已在 PATH，直接调用，在当前目录操作 `.xz_planning/`）。

## 前置检查

1. 无 `.xz_planning/` → 停止，提示 `请先执行 /xz-init`。
2. `xz-tools.py parse N`：`ok:true` → 停止，提示用 `/xz-update-plan N`；否则新建（`phase` 存在则复用目录）。

---

## 1. 调研（必做，不可跳过）

用 Glob/Read 深入需求模块，识别新建/修改文件与依赖。扫描排除 `.xz_planning/` 和 `.gitignore` 项。

## 2. 范围检查

- **多个独立子系统（无依赖）** → 停止，输出拆分建议，各走独立 `/xz-plan`。
- **Bug/排查类**（报错、异常、贴了堆栈/截图）→ 停止，提示先用 `xz-debug` 定位根因，**禁止凭猜测规划修复**。（性能/UX/重构/新增功能不算排查类。）

## 3. 理解对齐 + 方案（一次 AskUserQuestion 同时确认）

先输出「我的理解」（四段，与最终 PLAN 同构），紧接给方案，再合并成一次提问：

```markdown
## 我的理解
- **Goal**：构建/修改什么、解决什么问题、期望效果
- **Context**：涉及文件（@路径）、文件夹、文档、错误日志
- **Constraints**：架构、标准、安全、编码规范、兼容性
- **Done when**：怎样算做完（测试通过 / 接口返回 X / bug 不复现）

## 方案
单方案写思路；多方案列 A/B/C，附对比表（改动范围/开发量/性能/可维护性/扩展性）+ 推荐理由
```

方案铁律：来自代码分析不凭空凑数；多方案须有实质差异（库/架构/改法）；最多 3 个；优缺点量化（如 `改 3 文件约 45 行`），禁"性能好"这类空话。

**AskUserQuestion**：question "理解是否准确？选哪个方案？"，options 动态构建——多方案时每个有效方案一项（label 如 `理解OK-方案A(推荐)`）+ "需要修正理解"；单方案时 "理解准确，继续" / "需要修正理解"。选修正或 Other → 更新后重问。

## 3.3 约束澄清（无模糊约束则跳过）

用户给的**约束、规定、边界、验收标准、目标范围**若有歧义或多种解读 → 先列编号问题确认，再进选型。每个模糊点一条，给可能的解读 a/b/…（`a` = 最可能/推荐，括号说依据），单项 ≤4 个：

```markdown
1. 「兼容旧接口」指？  a. 旧接口并存不动（推荐，影响最小）  b. 旧接口转发到新实现  c. 直接替换不再兼容
2. 「不能影响性能」的标准？  a. P99 不超过现有（推荐）  b. 仅功能正确，不卡硬指标
3. 本次范围是否含「批量导入」？  a. 不含，仅单条（推荐，需求未提）  b. 含批量
```

铁律：只列真有歧义的；用户已明确、或能从代码现状推断的**不列**；无模糊点则**跳过本步**；不与 3.5 选型混在一起（这里只问「需求约束怎么解读」，不问「技术选哪个」）。

**AskUserQuestion**：每个模糊点一个 question（最多 4 个，超出分批问），options 为各解读（`a` 标推荐）+ 必要时「都不是，我来说」。用户选定或 Other → 把确认结论并入「我的理解」的 Constraints/Done when，必要时回 3 重新对齐。

## 3.5 选型澄清（无模糊选型则跳过）

列出所有真有选择空间的具体选型（项目已固定的不列），每项 `a=推荐`，括号一句话说优势，单项 ≤4 个：

```markdown
1. Web 框架  a. Gin（社区最大，推荐）  b. Echo  c. Fiber（最快但生态弱）
回复「全部确认」用默认，或指定如 `1b` 覆盖。
```

## 4. 生成草案（先输出对话，不写文件）

时间：`date "+%Y-%m-%d %H:%M:%S"`。

**章节规则**：Goal 写做啥；Context 放涉及文件 + 用户贴的代码/日志/链接（**原文保留禁止总结**），无则写「无」；Constraints 写约束，无则「无」；Done when 写可验证标准。

**change details**：修改标 `path:起始-结束行` + `(现:摘要)`（行号必 Read 确认，禁猜）；新建不标行号但列函数/类/常量名；超 30 行拆子区域。**粒度**：每条 2-5 分钟、可独立验证、一个功能单元一条。

````markdown
# 版本 N: 中文需求名（10-25 字，与目录名同步）

> 创建时间: YYYY-MM-DD HH:mm:ss
> 最后更新: YYYY-MM-DD HH:mm:ss
> 状态: 待执行

## Goal
做什么、解决什么问题、期望效果。

## Context
> 无则写「无」。
- 相关文件/文件夹：@路径
- 引用代码/数据/日志：用户原文片段（代码块包住，禁止总结）
- 外部链接/文档、业务背景/术语

## Constraints
架构、标准、安全、编码规范、兼容性。无则「无」。

## Done when
完成标准（测试通过 / 接口返回 X / bug 不复现）。

## 技术方案
选定方案及理由。

## Todolist

- [ ] 1. 任务标题

  **Files:**
  - Create: `path`
  - Modify: `path:42-58`

  ```
  change details:
  新建: path → 导出的函数/常量/类型
  修改: path:42-58 (现:摘要, 改后:目标) → 具体改动点
  ```
----------------------
- [ ] 2. ...

## 总结
共 N 条，涉及 X 文件（新建 Y，修改 Z）。逐条一句：做什么、涉及文件、关键函数、改成什么样。

## 改动前后对比
基于实际代码/数据，直观展示宏观变化（有数据贴数据、有请求贴请求响应、可用终端图示），不重复 todolist。
改动前：（现状）
改动后：（变化后）

## 变更记录
- YYYY-MM-DD HH:mm:ss 初始创建
````

## 4.5 测试方案（仅对话，不入文件）

草案后额外输出，帮用户自测，**不写进 PLAN.md**：

```markdown
## 测试方案（对话参考）
**目前情况** / **前置条件** / **操作步骤**（可直接执行的命令，敏感信息只写引用如「见 .env」）/ **预期结果**
```

来自草案推导、覆盖主要改动路径，只给人工跑一遍的指引，不涉及自动化循环。

## 5. 确认（AskUserQuestion）

question "以上计划是否确认？"，options：
- **确认写入** — 只写 N-PLAN.md，等手动调 /xz-exec
- **确认写入并直接执行** — 写入后立即进入 /xz-exec N 流程
- **手动执行** — 写 N-PLAN.md（状态置待手动执行）+ N-MANUAL.md，AI 不碰源码
- **修改意见** — 按反馈调整后重出

## 6. 写入文件

目录已存在直接写 `N-PLAN.md`；否则新建 `.xz_planning/phases/N.中文名/`（`中文名` 10-25 字，含「改动对象+动作+关键差异」，禁空格与 `/\:*?"<>|`，禁单用「优化/重构」等泛词，如 `订单表加软删除兼容取消流程`）。按第 5 步选择分支：

**① 确认写入** → 写 PLAN（状态 `待执行`）→ `xz-tools.py update-state` → 第 7 步。

**② 确认写入并直接执行** → 写 PLAN（状态 `待执行`）→ `xz-tools.py update-state` → 直接按 `/xz-exec N` 完整流程接着执行，跳过第 7 步。

**③ 手动执行** → 写 PLAN 但状态设为 **`待手动执行`**（这是 xz-exec 进入「校验模式」的触发标记）→ 同目录生成 `N-MANUAL.md`（格式见下）→ **AI 绝不改源码、不勾选 todo** → `xz-tools.py update-state` → 输出：
```
已写入 N-PLAN.md（待手动执行）+ N-MANUAL.md
按 N-MANUAL.md 手动改完后运行 /xz-exec N 校验并自动勾选。AI 不会改源码。
```

**N-MANUAL.md 模板**（每条对应一个 todo；标题说位置，「做什么」说目的+边界）：

````markdown

> 供人工照改，AI 不改源码。改完运行 `/xz-exec N` 校验勾选。编号对应 N-PLAN.md。

## 改动 2 ｜ 新建 `src/util/retry.go`
做什么：新增重试工具 Retry()，供登录失败时调用。整个文件新建，不动其他文件。
```go
package util

import "time"

// Retry 执行 fn，失败则重试，最多 attempts 次，每次间隔 delay。
// 例: Retry(3, 2*time.Second, login) → 失败时最多试 3 次，总耗时约 0s/2s/4s 三档。
func Retry(attempts int, delay time.Duration, fn func() error) error {
	var err error
	for i := 0; i < attempts; i++ {
		// fn 成功立即返回；失败记录 err 进入下一轮
		if err = fn(); err == nil {
			return nil
		}
		time.Sleep(delay) // 每轮间隔: delay=2s → 第2次在2s后、第3次在4s后
	}
	return err // 全部失败，返回最后一次的错误
}
```
````

**版面结构（让人一眼定位到块）：**
- 每个改动用大分隔线 `═══ 改动 N ═══`（含编号）起头，块与块界线分明；
- 标题：操作 + 文件 + 处数（单处则写大概位置：行号/函数名）；「做什么」一句：达成的效果 + 明确边界「仅动这几处，其他不改」；
- **一个改动涉及多处** → 拆 `### Na / Nb / Nc / Nd` 子块，每个子块标注自己的位置（行号/函数名/import 区），子块之间用小分隔线 `- - - - -` 隔开，照子块逐个改完即完成该改动；单处则不拆，直接给代码块。

每个改动点的写法：
- **改** = 找到（真实原文锚点）→ 替换为
- **增** = 新建则给整文件；已有文件插入则写「在…之后插入」＋代码块
- **删** = 删除 ＋ 贴出要删的原文
锚点取自真实 Read 内容、**禁杜撰**，位置标注要让人能一眼定位。

**代码完整性（强制）**：每个代码块必须是**最终成品代码，复制粘贴即可用**——
- 禁止任何省略：不得出现 `...`、`// 略`、`// 其余不变`、`// 完整内容见 PLAN`、`<同上>`、伪代码、自然语言占位；
- **新建** = 从第一行到最后一行的整个文件（含 package/import/注释），人不需要补任何一行；
- **改** = 「找到」贴真实原文、「替换为」贴替换后的完整代码段，两边都不得截断；
- **删** = 贴出要删的完整原文；
- **方法注释必带**：新建/替换代码中的每个函数/方法，上方必须有注释说明它是干嘛的（用途一句话，按语言惯例如 Go 的 `// FuncName 说明`），匿名函数和单行闭包除外；
- **关键逻辑详细注释 + 示例数据**：代码内的关键步骤（计算、拼接、转换、解析、分支判断）须有行内/行上注释说明在干嘛；凡涉及**数据格式、字符串拼接、计算结果**的，注释必须带示例数据直观展示前后格式，如 `// key = uid + "_" + date → "1001_20260610"`、`// 金额分转元: 1250 → "12.50"`，让人不跑代码就知道数据长什么样；
- 上面模板中的代码仅为格式示例，实际生成时一律写真实完整代码。
写完 MANUAL 后自查一遍：任何代码块含省略标记、函数/方法上方缺注释、或格式/拼接/计算处缺示例数据注释即违规，必须补全重写。

## 红线

1. **先输出后写** — 草案确认后才落盘。
2. **顶层四段缺一不可** — Goal/Context/Constraints/Done when。
3. **调研先行、方案来自代码** — 不读代码不规划，禁凭空凑数。
4. **零上下文 + 原子粒度** — 写给不懂项目的人看，每条 todo 可独立验证。
5. **change details 带行号 + 现状摘要**，新建列函数/类/常量。
6. **Context 原文保留** — 用户贴的代码/日志不得总结重写。
7. **聚焦本次边界** — 不写需求外的"顺手优化"；多子系统拆分；版本已存在导向 /xz-update-plan。
8. **手动执行不碰源码** — 路径③只写 N-PLAN.md（状态 `待手动执行`）+ N-MANUAL.md，绝不改源码、不勾选，勾选交给 /xz-exec 校验模式；MANUAL 锚点须来自真实代码。
9. **MANUAL 代码必须完整成品** — N-MANUAL.md 的每个代码块都是复制即用的最终代码：新建给整文件、改给完整替换段、删贴完整原文，函数/方法上方带用途注释，格式/拼接/计算处注释带示例数据（如 `// 1250 → "12.50"`）；出现 `...`/`略`/`其余不变`/伪代码等任何省略即违规，必须展开重写。
10. **约束模糊先澄清再规划** — 用户给的约束/规定/边界/验收/目标范围有歧义时，3.3 用编号 + a/b 解读选项确认，禁凭猜测把模糊约束写进 Constraints/Done when；能从代码现状推断的不问。
