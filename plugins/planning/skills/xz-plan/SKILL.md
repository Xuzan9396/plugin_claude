# XZ Plan - 创建新版本计划

参数 `$ARGUMENTS`：第一个空格前为版本号 N，之后为需求描述（`2 支持多语言` → N=2）。
任一不满足 → 停止并提示 `用法: /xz-plan N 需求描述`：`$ARGUMENTS` 为空 / N 非合法版本号（正整数，或小数如 1.5） / 需求为空。

**脚本**：`xz-tools.py`（`bin/` 已在 PATH，直接调用，在当前目录操作 `.xz_planning/`）。

## 前置检查

1. 无 `.xz_planning/` → 停止，提示 `请先执行 /xz-init`。
2. `xz-tools.py parse N`：`ok:true` → 停止，提示用 `/xz-update-plan N`；否则新建（`phase` 存在则复用目录）。

---

## 总纲：事实归 AI，拍板归用户

**代码、配置、文档里查得到的，一律自己查完再说；只有需要用户拿主意的才问。** 凡是写「我找过」，必须是真查过的文件，不许编。这条管全流程——调研、澄清、风险排查、测试资料，一处都不例外。

## 1. 调研（必做，不可跳过）

用 Glob/Read 深入需求模块，识别新建/修改文件与依赖。扫描排除 `.xz_planning/` 和 `.gitignore` 项。

**测试上下文扫描（必做，结果暂存喂给 4.5，本步不输出）**：顺带摸清「这个项目怎么跑测试」——已有测试文件（Glob `**/*_test.*`、`**/test_*.py`、`**/*.spec.ts`、`**/tests/**`）、框架与真实运行命令（读 1-2 个代表性测试文件确认，如 `pytest -v` / `npm test` / `go test ./...`）、测试配置（`pytest.ini`、`jest.config.*`、`Makefile`、`docker-compose.yml`）、服务怎么起（入口、端口、依赖服务）。**只摸清「怎么跑」，不定「测什么」**——用例是 `/xz-exec` 3.5 的事。项目无测试框架也记下来，4.5 走临时脚本路线。**禁止到 4.5 凭空编命令。**

**本次改动会碰到的外部依赖**（DB / 缓存 / MQ / 第三方 API / 测试账号）：**先自查**上面那些配置文件里有没有现成的连接与凭据——找得到的记下来源，找不到的攒着、3.5 步一并问。

**风险逐项排查（必做，结果暂存喂给第 3.5 步，本步不输出）**：读完代码后，对照第 3.5 步的风险清单（安全 / 性能 / 数据兼容 / 并发时序 / 错误处理 / 边界 / 语言专项）逐项过一遍本次改动，记下命中的点，留到澄清完毕后的 3.5 步逐项与用户确认处理方式。本步只排查、不提问、不输出。

## 2. 范围检查

- **多个独立子系统（无依赖）** → 停止，输出拆分建议，各走独立 `/xz-plan`。
- **Bug/排查类**（报错、异常、贴了堆栈/截图）→ 停止，提示先用 `xz-debug` 定位根因，**禁止凭猜测规划修复**。（性能/UX/重构/新增功能不算排查类。）
- **宽重构**（改列名、改共享类型、改接口签名、批量重命名）→ **不拆成多个 `/xz-plan`**，在本计划里按 expand-contract 三段排 todolist：① **expand** 新旧形式并存、一个调用方都不破坏（1 条 todo）② **migrate** 按包按目录分批迁，每批 1 条 todo，批与批之间始终能编译能跑 ③ **contract** 确认没调用方了再删旧形式（1 条 todo，排在所有 migrate 之后）。**必须在 PLAN 的 `## 技术方案` 里写明「本计划走 expand-contract 三段」**——`/xz-exec` 3.5 靠这句话给用例表加「阶段」列；不写它会把正常的中间态判成失败。

> ⚠️ **全程禁用 AskUserQuestion 等提问工具**：Claude Code 已知 bug——同一轮回复中提问弹窗之前的文本会被终端吞掉，用户会看不到理解/澄清/草案。所有确认一律用纯文本提问，等用户回复。

## 3. 理解 + 澄清（同一条回复批量输出，末尾一次提问；答复后有新问题继续追问）

### 分轮总规矩（决定什么问题放哪一轮）

**每一轮只问那些前置已经定了的问题。** 某个问题的答案得等本轮另一个问题先定下来，它就归下一轮。用户答完，重新看一遍哪些问题现在能问了，再出下一轮；没有能问的了，澄清就结束。

- **默认分两层**（最常见的情况）：实施方案 / 技术方向 / 需求约束 → 第一轮（本步）；开发风险 / 测试前置信息 → 第二轮（3.5 步）。因为要连什么、要什么账号、有什么坑，全取决于方案选哪个，方案没定就问必然问不准。
- **该合并就合并**：如果这次改动的风险和要什么测试资料，跟方案选哪个压根没关系（纯文案调整、只有一种合理改法的单点修改都算），就并进第一轮，别硬凑出一轮来。合并时在段首说一句「本次风险与方案选择无关，合并本轮」。
- **该再分就再分**：某个答复引出的新问题，如果它的答案又得等本轮别的未定项，那就放到再下一轮，别硬塞进当前这轮。
- 每轮编号都从 1 重新连号，段首注明第几轮和触发原因。**带着未定项进第 4 步一律算违规。**

调研后在**同一条回复**里依次输出 一、我的理解 → 二、未澄清清单，中间不插工具调用，末尾只问一次。**不单独输出方案对比段**——实施方案/技术方向选择本质也是「让用户在 a/b 里选」，直接作为未澄清清单里的一项混排。**已确认/能从代码稳定推断的关键点不单列**，直接并入「我的理解」的 约束/完成标准（不设「已澄清清单」段）。

> 未澄清清单**整段从 1 连续编号**（方案项 + 约束项混排、按高/中/低排序），用户末尾一次按编号回 `1a 2b 3a` 即可。**开发风险默认不在本轮**——风险依附于具体实现，方案没定查不准，按分轮总规矩落到 3.5；只有确认风险与方案选择无关时才允许合并进来。

### 一、我的理解（四段，与最终 PLAN 同构）

```markdown
## 我的理解
- **目标**：构建/修改什么、解决什么问题、期望效果
- **上下文**：涉及文件（@路径）、文件夹、文档、错误日志
- **约束**：架构、标准、安全、编码规范、兼容性
- **完成标准**：怎样算做完（测试通过 / 接口返回 X / bug 不复现）
```

### 二、未澄清清单（实施方案/技术方向选择 + 需求约束；按高/中/低排序；无则整段省略）

**段首先给一句整体状态摘要 + 一行回复提示**（排版规范与 3.5 步同构，见那一节的五段骨架，但**这一段不给总览表**——下面每项的标题行已经带了编号、优先级、一句话，再摆一张表是重复信息）：

摘要句说全局进度——哪些已定（从代码/用户已明确的，已并入「我的理解」）、还剩哪几项待定。例：`状态：缓存 key 已定，剩缓存存储选型、订单状态枚举、停机窗口 3 项待你确认。`

紧接着给一行回复提示，**把推荐组合的等价展开写出来**，用户不必自己数编号：

```
未澄清清单  →  回「全部默认」= 1a 2a 3a
```

优先级用 `🔴 高` / `🟠 中` / `🟡 低`（emoji 与文字都要，emoji 是终端里的扫读锚点），直接标在每项的标题行上。

把两类「需要用户在 a/b 里定夺」的点合到这一张清单、**整段从 1 连续编号**，单项选项 ≤4：
- **实施方案/技术方向选择**：库/框架/架构/改法有多个可行方向、会左右改动范围与开发量的，列出让用户选。选项来自代码分析、不凭空凑数，各选项须有实质差异，**`代价` 字段给量化**（如 `改 2 文件约 20 行`），禁"性能好"这类空话；**禁止只丢方案名词**，按下方展开格式给 做法/举例/代价/差异，做法**技术专有词与大白话并用**（术语给判断依据，大白话保证一眼看懂）。项目已固定、或只有一种合理改法的**不列**，直接写进「我的理解」的 约束。
- **需求约束**：真有歧义的约束/边界/验收解读、需求内部矛盾或与现状冲突，列出让用户定（`a` 放最可能的解读，说清依据）。

**每项格式**：`编号. 🔴 高 · 一句话问题`（≤25 字，整段编号从 1 连续排）→ 换行 `现状  当前代码/需求的实际情况`（带 `file:line`）→ 选项。**推荐项固定放 `a` 位、标记写在方案名之后（`✅推荐`）**，保证用户回 `全部默认` = 全选 a 即最优组合。选项分两种写法：
- **简单项**（选项字面自明，如枚举取值、要不要兼容 null）：一行并排 `a. xxx ✅推荐  b. xxx`。
- **方案类/不直观项**（实施方案/技术方向选择，或任何选项名词字面看不懂的）：**每个选项独立成块**，三字段固定顺序固定标签，**标签后补空格让所有字段值起始列对齐**——
  ```
  a. 短方案名（≤10 字）  ✅推荐
       做法  改哪里、怎么改（准确专有词：模式/库/接口/函数名）—— 技术专有词与大白话并用
       举例  一个具体例子直观展示改动前后的效果/数据/调用方式
       代价  量化：改 X 文件约 Y 行
  b. 短方案名
       做法  …
       举例  …
       代价  …
  差异  一两句点破 a/b 的本质取舍（选 a 得到什么/放弃什么，选 b 反之）
  ```

**排版硬闸**（与 3.5 步同一套，细则见那一节）：单条 ≤20 行；每个字段值 ≤2 行、禁连续 3 行以上散文块；**量化数字必须独占 `代价` 字段**、禁埋在长句里；涉及时序/数据流可加 ≤6 行终端图示但不强制。

**优先级 + 排序（必做）**：每项打标签并**从高到低排序**——`🔴 高` = 选错会大幅改变实施方向/返工成本高（多数方案选择、核心字段定义、需求冲突）；`🟠 中` = 只影响局部实现或某分支；`🟡 低` = 边角细节。方案类多属高、自然靠前 = 先定大方向。

**重点必查（最容易被擅自决定的两处，必列不得自行定）**：
- **key·字段定义**：用户提到的字段名、参数、状态值、枚举、key 命名/格式，其**含义/类型/取值范围/单位**若没说清 → 列出问，**禁自行假定**（如「订单状态枚举有哪些？`现状  现有表仅三值，需求未提退款` → a. 按现有表 ✅推荐  b. 另含退款中」）。
- **冲突**：需求内部自相矛盾（如又要实时又要批量延迟），或需求与现有代码/数据/已确认约束相抵触 → **必须列出**，给「以谁为准」的 a/b 选项，**禁自行选边**。

铁律：只列真有歧义/真有选择空间的；用户已明确、或能从代码现状推断的**不列**（并入「我的理解」），无则整段省略。凡影响实施方向或需求解读的未确认点必须列全、打好标签、从高到低排序；开发风险一律留到 3.5 步。

### 批量提问（纯文本）

理解 + 未澄清清单输出完，同一条回复末尾一次提问——
> 请一次回复：1) 理解准确？（`理解OK` / `理解需修正：xxx`）2) 未澄清各项（含实施方案与需求约束，`全部默认`用推荐 a，或按编号 `1a 2b 3a` 逐项覆盖）。示例：`理解OK 1a 2b`。

### 澄清追问循环（答复后必做）

- 用户答复后，把已定夺项（含选定实施方向/技术栈）并入「我的理解」的 约束/完成标准；用户修正了理解 → 更新后重出「我的理解」，必要时重新对齐。
- **重新算一遍这一轮能问什么**：答复引出新歧义（如选定某方向后暴露新的待定点）、答复不完整、或与已确认内容冲突 → **继续追问**，同格式再出一轮未澄清清单（编号重新从 1 连号，段首说明第几轮追问及触发原因）。新一轮**只放前置已定的问题**，答案还得等本轮别的未定项的留到再下一轮。直到没有能问的为止。
- **禁止带着未定项进 3.5 / 第 4 步**；无剩余问题时输出「澄清完毕，进入开发风险 + 测试资料确认」并进 3.5。

## 3.5 开发风险 + 测试资料确认（澄清完毕后强制独立一轮）

**触发时机**：第 3 步（含追问轮）全部定夺之后再发这一轮——**不得跳过直接进第 4 步**；澄清未完毕前也不做，方案没定风险查不准、要什么测试资料也说不准。

**唯一能合并进第 3 步的情况**：这次改动的风险和要什么测试资料，跟方案选哪个确实无关（纯文案调整、只有一种合理改法的单点修改都算）。这时按分轮总规矩并进第 3 步那一轮，段首注明「本次风险与方案选择无关，合并本轮」，编号接着第 3 步往后连排。**判不准就别合并**，按默认走独立一轮。

本轮问三件事、**编号从 1 连续排下来、一次回完**：**一、开发风险**（下方风险清单）+ **二、测试前置信息**（跑用例要用、第 1 步自查没找到的连接与凭据）+ **三、执行方式**（串行还是多 agent 并行）。前两件放在这里而不是第 3 步：要防什么坑、要连什么账号，**全取决于选定的实施方案**，方案没定就问必然问不准。第三件放这里是因为**这是用户唯一的拍板窗口**——执行方式在这儿一起定掉，第 5 步就不必再问一遍。

> **不问「打算怎么测」**：具体测哪几个点、每条用例什么命令什么断言，本 skill 一律不定、也不拿来问用户——那是 `/xz-exec` 3.5 步在动手改代码前、拿着当下真实代码现场生成的事。这里只负责把**跑测试的地基**（怎么跑、缺什么参数）问清楚。

**一、开发风险怎么做**：基于**已定夺的实施方向**对照下面的风险清单逐项排查。**命中**＝改动真实触及该点（非假想风险）＋ 用户没说清怎么处理 ＋ 不同处理方式有实质差异。命中即列，未命中维度不展示。**能推断出安全默认也不跳过**——把它作为推荐 a 摆出来让用户一次确认。

**每条命中项必须评严重度并排序**：给每条打 `🔴 严重` / `🟠 高` / `🟡 中` / `⚪ 低` 标签（emoji 与文字都要，emoji 是终端里的扫读锚点），输出时**从严重到低排序**（严重在最前）。判级标准：
- **🔴 严重** — 安全漏洞 / 数据丢失或损坏风险（如注入、鉴权绕过、重试重复写、迁移丢数据）
- **🟠 高** — 明显影响可靠性或性能（如资源泄漏、N+1、缺超时、错误被吞）
- **🟡 中** — 影响代码质量或可维护性（如边界未处理、错误丢上下文）
- **⚪ 低** — 可选优化（如日志、命名、小幅冗余）

测试前置信息项统一标 `📋 资料`、执行方式那一项标 `🚀 执行`，**都不参与严重度排序**，依次排在风险项之后。

**风险清单（提前预防）：**
- **安全**：硬编码密钥/token、输入未校验就用（用户输入 / 外部接口返回 / URL 参数）、敏感信息泄露到日志/错误消息/响应字段、权限鉴权缺失或绕过、弱加密（MD5/SHA1 存密码）
- **性能**：循环内冗余计算、资源未释放（连接/文件句柄/监听器/定时器）、大对象拷贝、N+1 查询、缺索引大表查询 / 缺分页、goroutine 泄漏
- **数据与兼容**：新增/改字段历史数据怎么处理、接口/协议向后兼容、迁移与回滚
- **并发/时序**：共享状态无锁、重试幂等、竞态
- **错误处理**：吞异常/空 catch、错误丢上下文、失败回滚与清理
- **边界**：空值/空集合/零值/负数/超大输入
- **语言专项**（按文件后缀匹配）：Go—未检查的 error return、`net/http` 未设超时、竞态；JS/TS—`innerHTML`/`dangerouslySetInnerHTML`(XSS)、`eval`、监听器/定时器未清理；SQL—字符串拼接注入、过宽 GRANT、动态表名未白名单；Python—async 中夹同步阻塞、ORM N+1

**二、测试前置信息怎么做**：基于已定夺的实施方向，推出这次改动会碰到哪些外部依赖、执行阶段跑测试要连哪些东西，列出**第 1 步自查代码没找到的**那些。每项写「要什么（干什么用）/ 我找过哪里 / 怎么给」，**编号接着开发风险往后连排**。**只问「要连什么」，不问「要测什么」**——测哪几个点是 `/xz-exec` 3.5 的事。

- **先自查再问（见总纲）** —— 第 1 步已查过 `.env`/`.env.example`/`config/*`/`docker-compose.yml`/`Makefile`及测试 fixture/`README` 本地开发章节/项目已有测试里的连接配置。**找得到的不问**，直接写进 4.5「测试环境与命令」，只写来源不抄明文。
- **起本地依赖必须作为选项让用户选** —— 凡是"我可以 docker-compose / testcontainers 起一个"的，写成该项的候选选项并**注明占用端口、跑完是否清理**，用户选中才执行，**禁止自作主张起容器**。
- **每项末尾固定给一个 `先跳过，执行时再说` 逃生项**（与开发风险的「不处理/忽略」同构）；选了跳过的在 4.5 标「待定」，执行阶段由 `/xz-exec` 7.2.1 再问一次。

**三、执行方式怎么做**：这一项**永远要问**（风险和资料都无命中也照样问），编号接在前两段之后、标 `🚀 执行`。推荐依据是第 1 步调研摸到的**模块分布** —— 注意此时 todolist 还没排（第 4 步才排），所以判断的是「改动落在哪几个模块、文件重不重叠」，不是精确的 todo 条数：

- 改动落在**2 个以上互不重叠的模块**上 → 推荐并行，并把模块列出来
- 改动**集中在同一批核心文件**上、或只有一两处小改 → 推荐串行（分组没意义，硬分只会撞车）

**推荐的那个放 `a` 位**（跟其他项一样），但**推哪个由改动形态决定，不许固定推并行**。下例是「模块分散」的情形：

```
N. 🚀 执行 · 用哪种方式实现
   现状  本次改动涉及 src/api/**、src/ui/**、Makefile 三块，文件不重叠

   a. 并行（多 agent 同时做）  ✅推荐
        做法  `/xz-worktree N` —— 自动分组，每组一个 agent 在独立 git worktree 里开发，谁先完成谁先合
        代价  约 3 组并行；patch 冲突时保留现场，需要你看一眼
        结果  快，但改动是分组合并进来的（不自动 commit）
   b. 串行（一条条做）
        做法  `/xz-exec N` —— 按 todolist 顺序逐条实现，每条改完就跑用例
        代价  条数 × 单条耗时
        结果  慢一些，但全程线性、出问题好定位
   取舍  a 快、代价是要接受分组合并；b 慢、换来过程最简单
```

**选定结果直接决定第 5 步的执行分支**——第 5 步不再问执行方式，只问「确认写入吗」。

### 输出排版：卡片式（五段骨架，缺一即违规）

两段编号从 1 连着排，每段内部各自排序；每条末尾都有逃生项，放最后一个字母（已有 a/b 则为 `c`，只有 a 则为 `b`）——风险段统一写「不处理/忽略（明确接受该风险）」、资料段写「先跳过，执行时再说」。

**为什么要卡片**：这一轮是用户唯一的拍板窗口，他要在几个 a/b 之间做选择。写成散文段落会把决策依据（改多少行、多几个状态、翻几倍）埋在句子中间，用户得逐字读完才能选。定长字段 + 段首总览表让他扫一眼就能回。

**① 段首回复行 + 总览表（必给）** —— 回复行把推荐组合的等价展开直接写出来，用户不必自己数编号：

```
开发风险 + 测试资料确认  →  回「全部默认」= 1a 2a 3a

| # | 严重度  | 一句话                    | 推荐动作          |
|---|---------|--------------------------|-------------------|
| 1 | 🔴 严重 | 失败重试可能重复写         | a 仅查询类重试     |
| 2 | 🟠 高   | 新接口入参未见校验         | a 入口统一校验     |
| 3 | 📋 资料 | 测试库 DSN 代码里找不到    | a 直接贴给我       |
```

- 「一句话」≤20 字，**只说问题是什么，不说怎么办**；「推荐动作」是 `a` 选项的 3-6 字短名，不是完整句子
- **总览表是「够用就够」的出口**：用户扫完表就能回复，下面的卡片是给想细看的人准备的

**② 卡片标题行**：`N. 🔴 严重 · 一句话问题`（≤25 字），编号与严重度和总览表逐字一致。

**③ 定长字段区** —— 每行一个字段，**标签后补空格，让所有字段值起始列对齐**。风险项：

| 字段 | 写什么 | 必需 |
|---|---|---|
| `现在` | 当前代码的行为，带 `file:line` | ✅ |
| `改后` | 这次改动让它变成什么 | ✅ |
| `出事` | 触发条件 `→` 后果，用箭头连，**禁写成句子** | ✅ |
| `但现在` | 为什么当前数据形态下其实无害 / 缓解因素 | 可选 |

测试前置信息项：

| 字段 | 写什么 | 必需 |
|---|---|---|
| `用途` | **这次改动为什么会碰到它**（不写「T4 要用」——T 编号是 `/xz-exec` 3.5 才生成的） | ✅ |
| `我找过` | 查过哪些文件（带 `file:line`）`→` 结论。必须真查过，禁编（见总纲） | ✅ |
| `我能自己搞定` | 相关但不用用户给的部分（如「HTTP 端口我自己起就行」），免得用户多操心 | 可选 |

**④ 选项块** —— 每个选项独立成块，三字段固定顺序固定标签；推荐项固定 `a` 位、标记写在方案名之后：

```
a. 短方案名（≤10 字）  ✅推荐
     做法  改哪里、怎么改 —— 技术专有词与大白话并用
     代价  量化：改 X 处约 Y 行 / +1 个状态 key / 占端口 Z、跑完清理
     结果  选它之后是什么状态
b. 短方案名
     做法  …
     代价  …
     结果  …
c. 不处理/忽略（明确接受该风险）
```

**逃生项单行写完、不展开三字段**。资料项的选项若字面自明（`直接贴给我` / `指到文件字段我自己读`）也可单行，只有「我起本地实例」这类必须写 `代价`（注明占用端口、跑完是否清理）。

**⑤ 收口行**：`取舍  a 得到什么/放弃什么；b 反之` —— 一行点破本质，≤2 行。

**排版硬闸（防止又退化成散文）**：

1. **单条卡片 ≤20 行** —— 超了说明这条该简化，或本就是两条风险硬并成一条
2. **每个字段值 ≤2 行** —— 禁止出现连续 3 行以上的散文块
3. **关键数字必须独占字段**（行数、条数、端口、倍数、时长）—— 禁止埋在长句中间，这是用户做选择的唯一依据
4. **只有 1-2 条且都是简单项时省掉总览表** —— 直接一行并排 `1. 🔴 严重 失败重试可能重复写 → a. 仅查询类重试 ✅推荐  b. 写请求重试 + 幂等 key  c. 不处理/忽略（明确接受该风险）`；为 1 条风险摆张表比不摆更累
5. **终端图示允许但不强制** —— 涉及时序、多路分支、数据流时可加 ≤6 行 ASCII 图示，位置在字段区之后、选项块之前；不要求每条都画

**前两段空了整段省略**（不写「无」占位）：只有风险 → 只发第一段；只缺资料 → 只发第二段。**但第三段（执行方式）永远要发** —— 前两段都空时，输出「已逐项排查安全/性能/数据兼容/并发/错误处理/边界等维度，本次改动无需额外确认的开发风险；测试所需连接与凭据都能从代码里读到」，然后**只问执行方式这一项**（编号从 1 开始），用户回完再进第 4 步。

**用户回复后**：
- **风险项** —— 选定的处理方式并入「我的理解」的 约束 / 技术方案，并**必须在第 4 步草案 todolist 的 改动详情 里落地**（如"入口加校验"要成为某条 todo 的具体改动点），不得只确认不落地。选「不处理/忽略」的不落地为 todo，但在 约束 里记一句「已确认接受 X 风险，本次不处理」留痕。
- **连接凭据** —— 记进 4.5 的「测试前置信息」段（只写来源与用途，明文不进 PLAN）；选「先跳过」的标「待定」。
- **执行方式** —— 记住选定的模式，**第 5 步的确认选项直接按它对应**（选并行 → 路径 2 走 `/xz-worktree N`；选串行 → 走 `/xz-exec N`）。**不写进 PLAN 文件**，它只决定本次流程走向；用户下次自己敲哪个命令仍由他定。

然后进第 4 步。

## 4. 生成草案（先输出对话，不写文件）

**输出顺序（硬性，违反即重来）**：工具调用（`date`、补读代码）全部前置做完，然后在**同一条回复**里连续输出——一、草案全文（按下方模板逐字写，含每条 todo 的 改动详情）→ 二、4.5 测试方案三段 → 三、第 5 步确认提问，中间不得再插工具调用；禁止只发提问不发草案，禁止用「计划已生成」之类的摘要代替全文。

时间：`date "+%Y-%m-%d %H:%M:%S"`（在输出草案前调用）。

**章节规则**：目标 写做啥；上下文 放涉及文件 + 用户贴的代码/日志/链接（**原文保留禁止总结**），无则写「无」；约束 写约束，无则「无」；完成标准 写可验证标准。

**改动详情**：修改标 `path:起始-结束行` + `(现:摘要)`（行号必 Read 确认，禁猜）；新建不标行号但列函数/类/常量名；超 30 行拆子区域。

**粒度：竖着切一刀，别横着片一层。** 一条 todo 就是一条从入口打通到出口的完整链路（handler → service → dao 一路走完），范围可以窄，但环节不能缺——做完就能单独跑起来看结果，能被一条机器可判的用例盖住。

- **禁止按层切**（先把 model 全改完再改 handler）——单条写不出行为断言。**纯内部逻辑的改动**（工具函数、数据处理、脚本）不套分层，判据换成「做完能跑出一个可以断言的结果」。
- 单条估着超过半小时就再拆一下，别拿时间当切分依据。**宽重构是例外**：按第 2 步 expand-contract 三段排，中间态不要求每条都能跑绿。

````markdown
# 版本 N: 中文需求名（10-25 字，与目录名同步）

> 创建时间: YYYY-MM-DD HH:mm:ss
> 最后更新: YYYY-MM-DD HH:mm:ss
> 状态: 待执行

## 目标
做什么、解决什么问题、期望效果。

## 上下文
> 无则写「无」。
- 相关文件/文件夹：@路径
- 引用代码/数据/日志：用户原文片段（代码块包住，禁止总结）
- 外部链接/文档、业务背景/术语

## 约束
架构、标准、安全、编码规范、兼容性。无则「无」。

## 完成标准
怎样算做完（测试通过 / 接口返回 X / bug 不复现）。

## 技术方案
澄清中选定的实施方向及理由。

## 任务清单

- [ ] 1. 任务标题

  **文件:**
  - 新建: `path`
  - 修改: `path:42-58`

  ```
  改动详情:
  新建: path → 导出的函数/常量/类型
  修改: path:42-58 (现:摘要, 改后:目标) → 具体改动点
  ```
----------------------
- [ ] 2. ...

## 总结
共 N 条，涉及 X 文件（新建 Y，修改 Z）。逐条一句：做什么、涉及文件、关键函数、改成什么样。

## 改动前后对比
基于实际代码/数据，直观展示宏观变化（有数据贴数据、有请求贴请求响应、可用终端图示），不重复 todolist。
改动前：（现状）
改动后：（变化后）

## 测试方案
### 测试环境与命令
### 测试前置信息
### 通过标准
> 三段的写法见下方 4.5，草案与 PLAN 里都要写成完整内容，**一段都不能少**。
> **这里不列具体用例**——测哪几个点、什么命令什么断言，由 `/xz-exec` 3.5 执行时现场生成。

## 变更记录
- YYYY-MM-DD HH:mm:ss 初始创建
````

## 4.5 测试方案三段（对话展示 + 原样写入 PLAN）

`## 测试方案` 是草案及 `N-PLAN.md` 的固定章节，**只写跑测试的地基——怎么跑、缺什么参数、怎么算过**。具体用例由 `/xz-exec` 3.5 拿当下真实代码现场生成：计划到执行之间往往隔着若干轮改动（接口签名变了、todo 拆合了），plan 阶段拍下的用例到执行时多半已过期。

```markdown
### 测试环境与命令
框架 / 运行命令 / 起服务与依赖的具体命令 —— 来自第 1 步的真实扫描，**不许编**。项目无测试框架则写明「无测试框架，用临时脚本 `.xz_planning/phases/N.xxx/tests/`」。已能从代码读到的连接参数写在这里，**只写来源不写明文**（如「DB_DSN：见 `.env`」）。

### 测试前置信息
3.5 步确认结果的回填，**不是新一轮索取**：已给的只记「要什么 + 干什么用 + 来源」，回了「先跳过」的标「待定 —— 执行时由 `/xz-exec` 再问一次」，选了「我起本地实例」的记下端口、执行时才起。无则整段写「无」。

### 通过标准
`/xz-exec` 3.5 现场生成的全部自动化用例通过 + 人工介入项逐项确认 + 无阻塞项。
```

## 5. 确认（纯文本提问，禁用提问工具）

在草案全文 + 测试方案之后、同一条回复末尾直接以文本提问：

> 以上计划是否确认？回复数字：
>   1) 确认写入 — 只写 N-PLAN.md，写完就停（之后你自己调）
>   2) 确认写入并执行 — 写入后立即按你在上一轮选的「<并行 / 串行>」模式执行
>   3) 修改意见 — 说明调整点后重出

**执行方式已在 3.5 定过，这里不再问一遍** —— 选项 2 的模式名要按 3.5 的选定结果**填实**，别留占位符。例：`2) 确认写入并执行 — 写入后立即按你选的**并行**模式跑 /xz-worktree N`。

「修改意见」→ 按反馈调整后重出草案。**本步只兜底不重复问**：测试前置信息已在 3.5 问过，用户给过的绝不再问一遍；仅当写 4.5 时新发现 3.5 没覆盖到的东西，才在确认提问后补一小段、和上面的选择一起回。

## 6. 写入文件

目录已存在直接写 `N-PLAN.md`；否则新建 `.xz_planning/phases/N.中文名/`（`中文名` 10-25 字，含「改动对象+动作+关键差异」，禁空格与 `/\:*?"<>|`、首字符禁用数字（与版本号小数解析冲突），禁单用「优化/重构」等泛词，如 `订单表加软删除兼容取消流程`）。

**两条写入路径都必须把对话中展示的完整测试方案原样写进 PLAN**，写完都要跑 `xz-tools.py update-state`。

**凭据**：明文一律不进 `N-PLAN.md`（只写来源或引用）；确实要落盘就放 `.xz_planning/phases/N.中文名/tests/.env.local`，文件头标一行「本文件含明文凭据，勿提交」，并先确认项目 `.gitignore` 覆盖得到该路径。

分支差异：

- **1) 确认写入** → 状态 `待执行` → 第 7 步。
- **2) 确认写入并执行** → 状态 `待执行` → 按 **3.5 选定的模式**接着执行，跳过第 7 步：
  - 选了**串行** → 按 `/xz-exec N` 完整流程走
  - 选了**并行** → 按 `/xz-worktree N` 完整流程走（它自己并行调研、分组、起多个 agent、边完成边合并，最后把状态置 `待闭环测试` 并提示跑 `/xz-exec N` 收尾）。**切不出互不重叠的分组时它会自己退回串行**，不用你操心。

## 7. 输出（仅路径 1）

```
计划已写入: .xz_planning/phases/N.xxx/N-PLAN.md
下一步: /xz-exec N（串行执行）/ /xz-worktree N（并行执行）/ /xz-update-plan N（改条目）
```

**末尾提醒一句 3.5 的选择**：「你在开发风险那一轮选的是**并行**，对应命令 `/xz-worktree N`」（选串行则说 `/xz-exec N`）。

**如果排完 todolist 发现与 3.5 的判断不符，必须在这里说出来** —— 3.5 判断执行方式时 todolist 还没排，依据只是模块分布；排完才看得清真实形态。对不上就补一句：「todolist 排下来发现 5 条里有 4 条都改 `src/core/model.go`，跟上一轮『模块分散』的判断不符，建议改走 `/xz-exec N` 串行」。**只提醒，不替用户改选择。**

## 红线（命中任一即违规重来）

| # | 红线 | 什么算违规 |
|---|------|-----------|
| 1 | 先输出、后确认、再落盘 | 草案全文没展示就弹确认，或确认前就写了文件 |
| 2 | 顶层四段缺一不可 | 目标 / 上下文 / 约束 / 完成标准 少任意一段 |
| 3 | 调研先行、方案来自代码 | 没读代码就出方案，或选项是凭空凑的 |
| 4 | 竖着切、别横着片 | todo 按层切（先全改 model 再改 handler），或哪条 todo 配不出行为用例 |
| 5 | 改动详情带行号 + 现状摘要 | 修改项没标 `path:起止行` 或行号靠猜；新建项没列函数/类/常量 |
| 6 | 上下文原文保留 | 用户贴的代码 / 日志被总结或改写 |
