# XZ Plan - 创建新版本计划

参数 `$ARGUMENTS`：第一个空格前为版本号 N，之后为需求描述（`2 支持多语言` → N=2）。
任一不满足 → 停止并提示 `用法: /xz-plan N 需求描述`：`$ARGUMENTS` 为空 / N 非合法版本号（正整数，或小数如 1.5） / 需求为空。

**脚本**：`xz-tools.py`（`bin/` 已在 PATH，直接调用，在当前目录操作 `.xz_planning/`）。

## 前置检查

1. 无 `.xz_planning/` → 停止，提示 `请先执行 /xz-init`。
2. `xz-tools.py parse N`：`ok:true` → 停止，提示用 `/xz-update-plan N`；否则新建（`phase` 存在则复用目录）。

---

## 1. 调研（必做，不可跳过）

用 Glob/Read 深入需求模块，识别新建/修改文件与依赖。扫描排除 `.xz_planning/` 和 `.gitignore` 项。

## 2. 范围检查

- **多个独立子系统（无依赖）** → 停止，输出拆分建议，各走独立 `/xz-plan`。
- **Bug/排查类**（报错、异常、贴了堆栈/截图）→ 停止，提示先用 `xz-debug` 定位根因，**禁止凭猜测规划修复**。（性能/UX/重构/新增功能不算排查类。）

> ⚠️ **全程禁用 AskUserQuestion 等提问工具**：Claude Code 已知 bug——同一轮回复中提问弹窗之前的文本会被终端吞掉，用户会看不到理解/方案/草案。所有确认一律用纯文本提问，等用户回复。

## 3. 理解 + 澄清 + 方案（同一条回复批量输出，末尾一次提问）

调研后在**同一条回复**里依次输出 ①我的理解 → ②已澄清清单 → ③未澄清清单 → ④方案，中间不插工具调用，末尾只问一次。**已澄清/未澄清必须和理解一起出**（不再分轮、不再后置），让用户一眼看清「AI 已经理解了哪些约束 + 哪里不敢替用户定」。

### ① 我的理解（四段，与最终 PLAN 同构）

```markdown
## 我的理解
- **Goal**：构建/修改什么、解决什么问题、期望效果
- **Context**：涉及文件（@路径）、文件夹、文档、错误日志
- **Constraints**：架构、标准、安全、编码规范、兼容性
- **Done when**：怎样算做完（测试通过 / 接口返回 X / bug 不复现）
```

### ② 已澄清清单（AI 已经理解/已确认的关键点；无则整段省略）

只列已经明确的关键约束、边界、验收、字段含义、用户已选方案或能从现有代码稳定推断的事实。每点一条编号，写成“结论 + 依据/来源”，不要放 a/b 选项，不要把普通背景凑进去。例：
- `1. 登录超时固定为 5s（依据：用户明确要求“超过 5s 返回 timeout”）。`
- `2. 缓存 key 沿用 uid_date 格式（依据：现有 CacheKey() 已统一生成 "1001_20260610"）。`

### ③ 未澄清清单（不确定的不要擅自决定；紧跟理解一起输出，无任何歧义则整段省略）

只列**真有歧义**的点，每点一条编号 + a/b/… 解读（`a` = 最可能/推荐，括号说依据），单项 ≤4。分三类、连续编号：

**A. 需求约束类**——约束/规定/边界/验收/范围怎么解读。**重点必查（最容易被擅自决定的两处）**：
- **key·字段定义**：用户提到的字段名、参数、状态值、枚举、key 命名/格式，其**含义/类型/取值范围/单位**若没说清 → 列出问，**禁自行假定**。例：
  `「订单状态」枚举有哪些？  a. 仅 待付/已付/取消（推荐，按现有表）  b. 另含 退款中`
  `缓存 key 格式？  a. uid_date（推荐，与现有命名一致）  b. date_uid`
- **冲突**：发现 ①需求内部自相矛盾（如又要实时又要批量延迟）、或 ②需求与现有代码/数据/已确认约束相抵触 → **必须列出**，给「以谁为准」的 a/b 选项，**禁自行选边**。例：
  `需求要「不停机」但现表无在线改字段方案，冲突。  a. 加临时双写过渡（推荐）  b. 接受一次停机窗口`

**B. 技术选型类**——真有选择空间的库/架构/改法（项目已固定的不列）。例：
  `Web 框架  a. Gin（社区最大，推荐）  b. Echo  c. Fiber（最快但生态弱）`

**C. 开发风险类**——开发后高概率会被 `/xz-review` 暴露、且当前需求或代码现状不足以确定处理方式的问题。调研时主动逐项排查：安全/权限、性能、数据兼容、并发/时序、错误处理、回滚/清理、边界输入、日志脱敏、资源释放、接口兼容、迁移风险。只有处理方式不确定才列；必须写清不同选项的实现影响，禁只写“注意风险”。例：
  `失败重试是否需要幂等保护？  a. 仅对查询类请求重试（推荐，避免重复写入）  b. 写请求也重试但要求业务幂等 key`
  `新增字段历史数据如何处理？  a. 迁移时补默认值（推荐，避免空值分支）  b. 运行时兼容 null`

铁律：只列真有歧义的；用户已明确、或能从代码现状推断的**不列**；无任何歧义则**整段省略**。约束类问「需求怎么解读」，选型类问「技术选哪个」，风险类问「开发后问题怎么提前规避」；三类各自归位别混写。凡会影响安全、性能、数据正确性、兼容性、错误处理或后续 review 结论的未确认点，必须在这里列全。

### ④ 方案

基于③未澄清清单的推荐解读（每项默认取 a）给方案：单方案写思路；多方案列 A/B/C，附对比表（改动范围/开发量/性能/可维护性/扩展性）+ 推荐理由。若③里有会左右方案走向的歧义，注明「方案基于推荐解读，若你改选会相应调整」。

方案铁律：来自代码分析不凭空凑数；多方案须有实质差异（库/架构/改法）；最多 3 个；优缺点量化（如 `改 3 文件约 45 行`），禁"性能好"这类空话。

### 批量提问（纯文本）

理解 + 已澄清清单 + 未澄清清单 + 方案输出完，同一条回复末尾一次提问——
> 请一次回复：1) 理解准确？（`理解OK` / `理解需修正：xxx`）2) 未澄清各项（`全部默认`用推荐 a，或 `1a 2b 3a` 逐项覆盖）3) 方案选择？（多方案 `方案A/B/C` 或提替代；单方案回 `继续`）。示例：`理解OK 1a 2b 方案A`。

用户改了理解/未澄清选择/方案 → 把结论并入「我的理解」的 Constraints/Done when，并在「已澄清清单」记录已确认结论，更新方案后重出，必要时重新对齐。

## 4. 生成草案（先输出对话，不写文件）

**输出顺序（硬性，违反即重来）**：所有工具调用（`date`、补读代码等）必须先做完，然后在**同一条回复**里依次输出——①草案全文（按下方模板逐字写出，含每条 todo 的 change details）→ ②4.5 测试方案 → ③第 5 步文本确认提问。三者全是终端文本、连续输出、中间不得再插任何工具调用；禁止只发提问不发草案，禁止用「计划已生成」之类的摘要代替全文。用户必须先在终端看到完整计划，才轮到确认是否写入/执行。

时间：`date "+%Y-%m-%d %H:%M:%S"`（在输出草案前调用）。

**章节规则**：Goal 写做啥；Context 放涉及文件 + 用户贴的代码/日志/链接（**原文保留禁止总结**），无则写「无」；Constraints 写约束，无则「无」；Done when 写可验证标准。

**change details**：修改标 `path:起始-结束行` + `(现:摘要)`（行号必 Read 确认，禁猜）；新建不标行号但列函数/类/常量名；超 30 行拆子区域。**粒度**：每条 2-5 分钟、可独立验证、一个功能单元一条。

````markdown
# 版本 N: 中文需求名（10-25 字，与目录名同步）

> 创建时间: YYYY-MM-DD HH:mm:ss
> 最后更新: YYYY-MM-DD HH:mm:ss
> 状态: 待执行

## Goal
做什么、解决什么问题、期望效果。

## Context
> 无则写「无」。
- 相关文件/文件夹：@路径
- 引用代码/数据/日志：用户原文片段（代码块包住，禁止总结）
- 外部链接/文档、业务背景/术语

## Constraints
架构、标准、安全、编码规范、兼容性。无则「无」。

## Done when
完成标准（测试通过 / 接口返回 X / bug 不复现）。

## 技术方案
选定方案及理由。

## Todolist

  - Create: `path`
  - Modify: `path:42-58`

  ```

## 总结
共 N 条，涉及 X 文件（新建 Y，修改 Z）。逐条一句：做什么、涉及文件、关键函数、改成什么样。

## 改动前后对比
基于实际代码/数据，直观展示宏观变化（有数据贴数据、有请求贴请求响应、可用终端图示），不重复 todolist。
改动前：（现状）
改动后：（变化后）

## 变更记录
````

## 6. 写入文件

目录已存在直接写 `N-PLAN.md`；否则新建 `.xz_planning/phases/N.中文名/`（`中文名` 10-25 字，含「改动对象+动作+关键差异」，禁空格与 `/\:*?"<>|`、首字符禁用数字（与版本号小数解析冲突），禁单用「优化/重构」等泛词，如 `订单表加软删除兼容取消流程`）。按第 5 步选择分支：

**① 确认写入** → 写 PLAN（状态 `待执行`）→ `xz-tools.py update-state` → 第 7 步。

````markdown
## 改动 2 ｜ 新建 `src/util/retry.go`
做什么：新增重试工具 Retry()，供登录失败时调用。整个文件新建，不动其他文件。
```go
package util

import "time"

// Retry 执行 fn，失败则重试，最多 attempts 次，每次间隔 delay。
// 例: Retry(3, 2*time.Second, login) → 失败时最多试 3 次，总耗时约 0s/2s/4s 三档。
func Retry(attempts int, delay time.Duration, fn func() error) error {
	var err error
	for i := 0; i < attempts; i++ {
		// fn 成功立即返回；失败记录 err 进入下一轮
		if err = fn(); err == nil {
			return nil
		}
		time.Sleep(delay) // 每轮间隔: delay=2s → 第2次在2s后、第3次在4s后
	}
	return err // 全部失败，返回最后一次的错误
}
```
````

**版面结构（让人一眼定位到块）：**
- 每个改动用大分隔线 `═══ 改动 N ═══`（含编号）起头，块与块界线分明；
- 标题：操作 + 文件 + 处数（单处则写大概位置：行号/函数名）；「做什么」一句：达成的效果 + 明确边界「仅动这几处，其他不改」；
- **一个改动涉及多处** → 拆 `### Na / Nb / Nc / Nd` 子块，每个子块标注自己的位置（行号/函数名/import 区），子块之间用小分隔线 `- - - - -` 隔开，照子块逐个改完即完成该改动；单处则不拆，直接给代码块。

每个改动点的写法：
- **改** = 修改已有文件一律给 `========= v计划号 真实改动标题 before|start|end ===========` 三段标识块；`before` 放真实原文锚点，`start` 和 `end` 之间放改后的最终代码。默认只给这次改动的最小必要上下文，**不要把未改的方法和整个文件一起带出**。
- **增** = 新建文件则给整文件；已有文件插入内容属于修改已有文件，必须使用 `before|start|end` 三段标识块，`before` 放插入点真实原文锚点，`start` 和 `end` 之间放插入后的最终片段
- **删** = 删除 ＋ 贴出要删的完整原文；如需帮助定位，可补一小段前后文，但不要带无关大段
锚点取自真实 Read 内容、**禁杜撰**，位置标注要让人能一眼定位。

**代码完整性（强制）**：每个代码块必须是**最终成品代码，复制粘贴即可用**——
- 禁止任何省略：不得出现 `...`、`// 略`、`// 其余不变`、`// 完整内容见 PLAN`、`<同上>`、伪代码、自然语言占位；
- **新建** = 从第一行到最后一行的整个文件（含 package/import/注释），人不需要补任何一行；
- **修改** = 代码块必须能直接替换到目标位置；`before` 是原文锚点，`start` 到 `end` 之间是改后的最终代码；
- **修改文件默认禁止整文件输出**：除非整个文件就是新建文件，否则不要把无关未改方法整段带出来；
- **删** = 贴出要删的完整原文；
- **方法注释与案例必带**：只要片段里出现函数/方法，上方必须有用途注释，并补一个直观案例说明输入/场景/结果；匿名函数和单行闭包除外；
- **关键逻辑详细注释 + 示例数据**：代码内的关键步骤（计算、拼接、转换、解析、分支判断）须有行内/行上注释说明在干嘛；凡涉及**数据格式、字符串拼接、计算结果**的，注释必须带示例数据直观展示前后格式，如 `// key = uid + "_" + date → "1001_20260610"`、`// 金额分转元: 1250 → "12.50"`，让人不跑代码就知道数据长什么样；
- 上面模板中的代码仅为格式示例，实际生成时一律写真实完整代码。
写完 MANUAL 后自查一遍：任何代码块含省略标记、修改场景带了整文件、片段内函数/方法上方缺注释或案例、修改已有文件缺 `v计划号` 标识、或格式/拼接/计算处缺示例数据注释即违规，必须补全重写。

## 红线

1. **先输出后确认后写** — 草案全文、测试方案、确认提问三者在同一条回复里按序出现（工具调用全部前置），用户看完整计划后才确认，确认后才落盘；草案未展示就弹确认 = 违规重来。
2. **顶层四段缺一不可** — Goal/Context/Constraints/Done when。
3. **调研先行、方案来自代码** — 不读代码不规划，禁凭空凑数。
4. **零上下文 + 原子粒度** — 写给不懂项目的人看，每条 todo 可独立验证。
5. **change details 带行号 + 现状摘要**，新建列函数/类/常量。
6. **Context 原文保留** — 用户贴的代码/日志不得总结重写。
7. **聚焦本次边界** — 不写需求外的"顺手优化"；多子系统拆分；版本已存在导向 /xz-update-plan。
8. **手动执行不碰源码** — 路径③只写 N-PLAN.md（状态 `待手动执行`）+ N-MANUAL.md，绝不改源码、不勾选，勾选交给 /xz-exec 校验模式；MANUAL 的锚点和改动块必须来自真实代码。
9. **MANUAL 改动块必须是最终成品** — N-MANUAL.md 的每个代码块都必须复制即用：新建文件给整文件；修改已有文件统一使用 `========= v计划号 真实改动标题 before|start|end ===========`；默认不要带未改的方法和整文件；片段里出现的函数/方法上方带用途注释和案例，格式/拼接/计算处注释带示例数据（如 `// key = uid + "_" + date → "1001_20260610"`、`// 1250 → "12.50"`）；出现 `...`/`略`/`其余不变`/伪代码等任何省略即违规，必须展开重写。
10. **约束分清已澄清/未澄清再规划** — 已明确或能从代码稳定推断的关键约束，必须放进第 3 步②已澄清清单；约束/规定/边界/验收/范围/**key·字段定义**有歧义，发现**需求内部矛盾 / 需求与现状冲突**，或存在开发后高概率被 review 暴露的安全/性能/数据/兼容/错误处理风险且处理方式未定时，必在第 3 步③未澄清清单里（紧跟理解一起输出）用编号 + a/b 解读确认，禁凭猜测把模糊约束写进 Constraints/Done when、禁自行替用户选边；能从代码现状推断的不问。
