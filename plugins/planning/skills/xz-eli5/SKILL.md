# 讲人话 —— 看人下菜碟地解释（ELI5）

参数: `$ARGUMENTS`

你的活儿是把复杂东西拆开，按听众的底子、词汇量、关心点重新讲一遍。不是把内容砍掉，是换个说法讲。

---

## 第一步：先搞清楚讲给谁听

从 `$ARGUMENTS` 里判断听众是谁，落到下面某一档。**没说是谁就默认「五岁小孩」**（经典 ELI5）。

### 按年龄

| 听众 | 怎么讲 |
|:--|:--|
| 5 岁 | 全大白话，句子短。拿积木、小汽车、小动物、糖、滑滑梯打比方。"你想想啊，你有一盒蜡笔……" |
| 10 岁 | 小学生水平，能听懂前因后果了。拿上学、班里的事、打游戏、体育课举例 |
| 15 岁 | 初高中，能接受一点抽象的东西。拿手机、抖音、微信、打游戏说事，语气可以随意点 |
| 20-30 岁 | 年轻人，说话直给别绕。拿上班、房租、点外卖、打车这些天天遇到的举例 |
| 40 岁往上 | 语气要尊重，别端着也别哄。拿买房装修、单位里的事、孩子上学打比方 |

### 按学历/学段

| 听众 | 怎么讲 |
|:--|:--|
| 小学五年级 | 词儿要简单，例子要摸得着，术语一个都别蹦。"你就把它想成……" |
| 初中 | 可以引入基本术语，但引一个解释一个。一步一步顺着讲 |
| 高中 | 能扛住中等复杂度。正规名词可以上，上了就解释清楚 |
| 大学生 | 可以用学术框架，专业术语稍微带一句背景就行。理论 + 怎么用 |
| 研究生 | 默认底子扎实，直接聊细微差别、取舍、边界情况、更深一层的影响。说话要准 |

### 按职场角色

| 听众 | 他关心啥 | 从哪个角度切 |
|:--|:--|:--|
| 经理/主管 | 影响、工期、风险、成本 | 对业务的结果、对团队的影响、需要拍哪些板 |
| 工程师 | 怎么实现的、架构、取舍 | 技术细节、性能、以后好不好维护 |
| 设计师 | 用户体验、视觉、流程 | 用户会感知到什么、交互怎么变、无障碍 |
| 总监/老板 | 战略、投入产出、竞争力 | 大盘子、市场位置、资源往哪投 |
| 同事 | 跟他手上的活儿有啥关系 | 影响他哪一块、协作时他得知道什么 |
| 产品经理 | 用户价值、优先级、范围 | 功能影响、用户故事、哪些先做哪些砍掉 |

### 按亲近关系

| 听众 | 语气 | 拿什么打比方 |
|:--|:--|:--|
| 老婆/老公/对象 | 家常，有耐心，不急 | 家里的活儿、俩人一起经历过的事、每天的日常 |
| 爸妈 | 尊重，别有优越感，别把人当外行哄 | 他们本来就用的微信、支付宝、电视遥控器，拿这些搭桥 |
| 小孩 | 活泼，多鼓励，句子短 | 游戏、动画片、学校、小动物 |
| 朋友 | 随意，可以贫两句 | 网上的梗、共同爱好、"你知道那种……吧" |

## 第二步：先把要讲的东西看明白

开口之前先确认自己是真懂了。要讲的可能是：

- **代码** — 先用 Read/Grep 把相关文件读了，搞清楚这段整体在干嘛，再动手翻译成人话
- **一个概念** — 拆成几个核心零件，看清楚每个零件干啥的
- **一条报错** — 找根因，不是照着字面念一遍
- **一份技术文档** — 挑出真正要紧的那几点，其余的先放下
- **别的** — 抓住两件事：「它是什么」和「为什么有它」

---

## 第三步：组织怎么讲

### 结构（四段走）

1. **先说「这是啥」** — 一句话点破本质
2. **打个比方** — 挂到听众本来就懂的东西上
3. **再补细节** — 按听众的档位一层一层加，不该加的坚决不加
4. **最后说「那又怎样」** — 这事儿对他个人到底意味着什么

### 用词标定

**对普通听众**（小孩、非技术岗、家里人）：

- 一个术语都别蹦。实在绕不开就当场解释掉
- 一句话说一件事
- 宁可具体别抽象 ——「服务器就跟饭馆里的服务员似的」完胜「服务器负责处理客户端请求」
- 多用「你」，讲得跟他有关系

**对技术听众**（工程师、研究生）：

- 该用术语就用，不用反倒显得你在哄他
- 挑有意思的部分聊：取舍在哪、有什么坑、当初为啥这么设计
- 往他已知的东西上挂 ——「跟哈希表差不多，区别是……」
- 别啰嗦，人家底子在那儿摆着

**对业务听众**（经理、总监）：

- 开门见山讲影响和结果
- 能量化就量化
- 实现细节不问就别讲
- 落到「所以我们应该……」这种能拍板的话上

### 语气匹配

- **5-10 岁**：像个特有意思的老师，"哎这个好玩儿，你听我说"
- **青少年**：放松点，但别硬装，别整"你们年轻人都懂的"那套
- **职场人**：自信干脆。尊重对方智商，同时把知识差补上
- **家里人**：有耐心、家常，就跟吃饭时随口聊那样

## 举几个例子

**用户说**："数据库索引讲人话说说"
**听众**：五岁（默认）
**该这么答**："你想想啊，你手上有本特别厚特别厚的书，好几千页。我要是让你找讲恐龙那一页，你可以一页一页往后翻……也可以直接看最前面的目录呀！数据库索引就是那个目录，电脑靠它一下就翻到了，不用挨着找。"

**用户说**："这个接口限流的事儿，怎么跟我领导说"
**听众**：经理
**该这么答**："这个接口有个速度上限，一分钟最多调一百次。现在高峰期已经顶到天花板了，有些用户的请求直接失败了。两条路：一是改代码少调几次，大概一两天的活儿；二是花钱升配，一个月 X 块。我建议……"

**用户说**："给大学生讲讲 React 的 useEffect"
**听众**：大学生
**该这么答**："useEffect 是 React 用来处理副作用的 —— 就是那些不属于正常渲染流程的事儿，比如调接口、订阅、直接操作 DOM。你要是见过 class 组件，可以把它理解成 componentDidMount、componentDidUpdate、componentWillUnmount 三个揉一块儿了。后面那个依赖数组决定它啥时候重新跑……"

## 几条要记住的

- **别居高临下**。讲给五岁小孩听应该是"有意思"，不是"哄傻子"；讲给领导听应该是让他心里有数，不是让他觉得你嫌他不懂技术
- **讲代码先讲「这玩意儿是干啥的」，再讲「它怎么干的」**。没人关心语法长啥样，得先知道它为啥存在
- **东西真复杂、听众真不懂技术，那就狠狠地简化**。把核心意思讲到位（哪怕只有八成准），好过一字不差但人家听睡着了
- **长度也看人下菜**。给小孩讲就短平快，给技术的人讲该展开就展开
