# XZ Discuss - 想清楚再动手

参数: `$ARGUMENTS`（第一个空格前是版本号 N，之后是讨论主题）

**这一步只回答「做什么」，不回答「怎么做」。** 架构怎么搭、改哪些文件、函数怎么写、怎么测，全是 `/xz-plan` 的活儿，本 skill 一个字都不碰。

### 参数校验

`$ARGUMENTS` 为空 / N 非合法版本号（正整数，或小数如 1.5）/ 主题为空 → **立即停止**：

> 用法: `/xz-discuss N 讨论内容`
> 示例: `/xz-discuss 1 做一个给自由职业者用的客户管理工具`

**辅助脚本**：`xz-tools.py`（插件启用时 `bin/` 自动加入 PATH，裸命令调用即可）。脚本在**当前工作目录**下操作 `.xz_planning/`。

---

## 硬闸门

**方案没经用户确认之前，不写任何代码、不改任何文件、不生成 todolist。**

「这需求太简单，不用讨论」是最危险的念头——**简单需求恰恰是没被审视的假设最容易造成返工的地方**。简单需求可以只写几句话，但必须走完「出方案 → 用户确认」。

> ⚠️ 全程禁用 AskUserQuestion 等提问工具：Claude Code 已知 bug——弹窗之前的文本会被终端吞掉，用户会看不到你刚输出的内容。一律纯文本提问，等用户回复。

---

## 第一步：前置检查

无 `.xz_planning/` → 停止，提示 `/xz-init`。

```bash
xz-tools.py parse N
```

- **N-DISCUSS.md 已存在** → 问用户覆盖还是在原基础上补充
- **N-PLAN.md 已存在** → 告知计划已存在，讨论仍可作为补充材料写入
- **都不存在** → 正常往下走

## 第二步：摸清现状

读 `.xz_planning/PROJECT.md`（存在则读）+ 用 Glob/Read 扫需求涉及的现有代码。扫描排除 `.xz_planning/` 和 `.gitignore` 里声明的目录。

**摸清楚了才能问对问题。** 这一步能从代码里读出答案的，第四步一律不许再拿去问用户。

## 第三步：范围闸门

需求横跨**多个互不依赖的子系统**（如"做个平台，有聊天、文件存储、计费、分析"）→ **立即停下**，给出拆分建议，每块各走一次 `/xz-discuss`。

**不要在拆分前深入细节。**

## 第四步：澄清（最多 5 问，一次一个）

**上限 5 个问题，一次只发一个，等用户回复再发下一个。** 用户说「够了」「直接出方案」随时提前结束。

先过一遍覆盖清单，**挑缺口最大的问，不要按顺序硬凑满 5 个**：

| 类目 | 问什么 |
|:--|:--|
| 目的 | 解决谁的什么问题，不做会怎样 |
| 边界 | 这次做到哪儿为止，什么明确不做 |
| 约束 | 必须兼容什么、不能碰什么、有没有死线 |
| 成功标准 | 怎么算做成了 |
| 现状冲突 | 需求跟现有代码/数据打架的地方以谁为准 |

已经从代码或用户原话里得到答案的类目**直接跳过**，不凑数。一个缺口都没有就跳过本步，直接进第五步。

**每问的格式**：

```
[1/5] 一句话问题
现状：从代码/需求里读到的实际情况
a. xxx（推荐，理由）
b. xxx
c. 其它（直接说）
```

推荐项**固定放 `a` 位**，用户回 `a` 或「默认」即取推荐。

## 第五步：出方案（2-3 个）

**永远给 2-3 个，不给一个。** 方案之间必须是真取舍——不同的范围、不同的路子，不是同一个东西换个说法。

**YAGNI 从严**：能砍的先砍掉，砍不掉的再论证为什么留。**A 默认是范围最小的那个。**

每个方案写清五项：

- **思路** — 一句话说清核心取舍
- **做什么** — 这个方案包含哪些
- **不做什么** — 明确砍掉哪些（这条最容易漏，但最值钱）
- **代价** — 放弃了什么、以后可能要补什么
- **体量** — 约 X 条 todo

末尾一句 `**推荐 A：** 一句话理由`。

## 第六步：出草案（先输出，不写文件）

取时间：

```bash
date "+%Y-%m-%d %H:%M:%S"
```

**在同一条回复里输出完整草案 + 第八步的确认提问**，中间不插工具调用。禁止用「草案已生成」之类的摘要代替全文。

**篇幅按复杂度伸缩**——简单需求几句话就够，复杂的每段 200-300 字，**不要为了凑格式写废话**。

````markdown
# 版本 N: 中文需求名 - 讨论

> 创建时间: YYYY-MM-DD HH:mm:ss

## 需求重述
2-3 句，比用户原话更准更清楚。提炼本质，不复述原文。

## 澄清结果
| # | 问的 | 用户定的 |
|---|------|---------|
（一个都没问就写「需求已足够清晰，未做澄清」）

## 方案对比
### A（推荐）方案名
思路 / 做什么 / 不做什么 / 代价 / 体量
### B 方案名
（同上结构）
**推荐 A：** 一句话理由

## 风险与待确认
- **已知** — 确定会遇到的
- **假设** — 我按这么理解的，可能不对
- **待确认** — 现在定不了、执行前要拍板的

## 变更记录
- YYYY-MM-DD HH:mm:ss 初始创建
````

## 第七步：自检四查

展示给用户前自己先过一遍，不合格改完再发：

1. **占位符** — 有没有 TBD / 待定 / xxx 没填
2. **自相矛盾** — 前后说法有没有打架
3. **含糊** — "优化一下""提升性能"这种没法验证的话，换成能验证的说法
4. **范围蔓延** — 有没有混进用户没要的东西

## 第八步：确认（纯文本）

草案同一条回复末尾：

> 以上讨论是否确认？回复数字：
>   1) 确认写入 — 存 N-DISCUSS.md
>   2) 确认并选方案 — 如「2 选 A」，选定方案写进文档
>   3) 修改意见 — 说调整点，我重出草案

**禁止自动写文件，必须等明确确认。** 用户给修改意见 → 按反馈调整后重出草案。

## 第九步：写入

目录已存在直接写；否则新建 `.xz_planning/phases/N.中文名/`（中文名 10-25 字，含「对象+动作+关键差异」，禁空格与 `/\:*?"<>|`，首字符禁数字——与版本号小数解析冲突）。

写入 `N-DISCUSS.md` 后刷新状态：

```bash
xz-tools.py update-state
```

## 第十步：输出

```
讨论已写入: .xz_planning/phases/N.xxx/N-DISCUSS.md
下一步: /xz-plan N 需求描述
```

> `/xz-plan` 不会自动读 N-DISCUSS.md——创建计划时把选定的方案在需求描述里说一句，或者先让 AI 读一下这个文件。

## 红线（命中任一即违规重来）

| # | 红线 | 什么算违规 |
|---|------|-----------|
| 1 | 先出方案、再确认、后落盘 | 草案没展示就写文件；没等明确确认就写 |
| 2 | 只答「做什么」 | 写了架构设计、组件划分、数据流、改哪些文件、怎么测——那全是 `/xz-plan` 的 |
| 3 | 一次一问、不超 5 个 | 一口气抛多个问题；为凑数硬问满 5 个；第二步扫代码能读到的还拿去问 |
| 4 | 至少 2 个方案、有实质差异 | 只给一个方案；两个方案是同一个东西换说法；没写「不做什么」 |
| 5 | 推荐明确且在 A 位 | 没标推荐 / 没给理由 / 推荐的不是 A |
| 6 | 假设不伪装成事实 | 猜的东西写进「已知」，没进「假设」 |
| 7 | 不生成 todolist、不碰源码 | 越界去排 todo 或改任何代码文件 |
| 8 | 范围先行 | 发现是多个独立子系统还继续往下深挖，没先建议拆分 |
