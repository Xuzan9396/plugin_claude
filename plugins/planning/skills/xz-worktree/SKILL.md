# XZ Worktree - 并行开发版本计划

执行版本号: `$ARGUMENTS`。为空或不是合法版本号（正整数，或小数如 1.5）→ **立即停止**，提示 `用法: /xz-worktree N`（示例 `/xz-worktree 1`）。

**脚本**：`xz-tools.py`（`bin/` 已在 PATH，直接调用，在当前目录操作 `.xz_planning/`）。

**本 skill 是 `/xz-exec N` 的并行版**：同一份 PLAN，exec 一条一条串着做，这里把互不重叠的 todo 分组、多个 agent 在各自的 git worktree 里同时做，再把改动合回主工作区。**闭环测试不在这里做** —— 合并完把状态置 `待闭环测试`，交回 `/xz-exec N` 跑全量闭环（与 `/xz-manual` 同一种交接方式）。

> ⚠️ **全程禁用 AskUserQuestion 等提问工具**：Claude Code 已知 bug——同一轮回复中提问弹窗之前的文本会被终端吞掉。要停下来说事一律用纯文本。

## 机制（先看懂再动手）

子 agent **只在自己的 worktree 目录里改文件，一律不碰 git**；主会话用 `xz-tools.py wt` 抓 `git diff --binary` 成 patch，按组序**串行** `git apply` 到主工作区，**不自动 commit**。成功即删 worktree，冲突或失败**保留现场**供检查。

| 命令 | 干什么 |
|---|---|
| `xz-tools.py wt create N <组名>...` | 校验主工作区干净 → 以 HEAD 为 base，逐组建 worktree（`<仓库上级>/worktree/<仓库名>/<组名>-<短ID>`），返回每组绝对路径与分支名 |
| `xz-tools.py wt capture N <组名>` | 抓该组改动成 patch（含新建、删除、二进制），返回改动文件列表 |
| `xz-tools.py wt apply N <组名>... [--preserve=g1,g2]` | 按给的组序串行集成到主工作区；`--preserve` 列的组只留现场不集成 |
| `xz-tools.py wt list N` | 看所有组的集成状态与现场路径 |
| `xz-tools.py wt clean N [<组名>]` | 手工删残留 worktree 与临时分支 |

集成状态四态：`applied`（已合并，worktree 已删）/ `conflict`（apply 失败，现场与 patch 都保留）/ `preserved`（该组开发失败，只留现场不集成）/ `no_changes`（一个文件都没改——实现类任务按失败处理）。

## 1. 读取计划

`xz-tools.py parse $ARGUMENTS` 取 `phase.plan_file`，读 `N-PLAN.md` 全文，必须同时理解：`目标` / `上下文` / `约束` / `完成标准` / `技术方案` / `任务清单`（含每条的 改动详情）/ `测试方案`。版本不存在 → 提示先跑 `/xz-plan N`。

`N-PLAN.md` 是唯一上下文来源，**禁止依赖「聊天里提过但计划里没写」的信息**。

按 PLAN 头部 `> 状态:` 判走向：

| 状态 | 走向 |
|---|---|
| **`待手动执行`** | 手动路径，本 skill 不处理 → 提示去跑 `/xz-manual N` |
| **`待闭环测试`** | 开发已完成、只剩闭环 → 提示去跑 `/xz-exec N`，别重做一遍 |
| 其他（`待执行` / `进行中`） | 继续第 2 步 |

## 2. 前置闸门（任一不过就停，不许硬上）

1. **不在 git 仓库** → 停：并行开发依赖 git worktree，建议改用 `/xz-exec N`。
2. **未完成 todo 少于 2 条** → 停：并行没意义，建议 `/xz-exec N`。
3. **主工作区不干净** → `wt create` 会拒绝并列出脏文件。**AI 不许替用户 commit / stash / checkout** —— 原样把脏文件清单转给他，说明「patch 集成依赖 base commit 对齐，工作区有未提交改动会把你的改动和 agent 的改动搅在一起」，让他自己处理完重跑。（`.xz_planning/` 不算脏，脚本已排除。）
   > **上一轮部分成功后重跑，必然撞上这一条**：已合并的组还没 commit，工作区当然是脏的。这不是脚本坏了，照样要他先 commit 或 stash 再重跑。

## 3. 并行调研（只读，摸清分组边界）

按未完成 todo 的模块归属划出 2-4 个候选方向，**在同一条回复里并行起多个只读 agent**（一个方向一个），各自摸清四件事：

- 这几条 todo **真正会改哪些文件**（要具体到路径，不是「大概在 api 层」）
- 与其他方向**有没有文件重叠**
- 跨方向的**接口契约**是什么（函数签名、请求/响应结构、表结构、常量）
- 这个方向**能不能独立跑起来验证**、用哪条命令验

调研 agent **只读不写**：可以 Read / Grep / Glob 和只读的 Bash 命令，**禁止改任何文件**。汇总它们的结论进第 4 步。

## 4. 分组（自动判定，展示但不停下等确认）

基于第 3 步的结论自己分好组，在对话里展示这张表**然后直接往下走** —— 展示是为了让用户事后能看清 AI 怎么分的，不是设一道审批（与 `/xz-exec` 3.5 展示用例表同一个口径）：

```
并行分组（3 组并行）

| 组 | todo | 只碰这些文件 | 组内验收用例 | 依赖 |
|-------|-------|----------------------|------------------------------|------|
| api   | #1,#2 | src/api/**（4 文件）  | `go test ./api/...` 全 PASS  | 无 |
| ui    | #3    | src/ui/**（2 文件）   | `npm test -- ui` 全 PASS     | 用 api 的接口契约（见下） |
| infra | #4,#5 | Makefile, docker/**  | `make build` 退出码 0        | 无 |

文件重叠检查：三组文件集合两两无交集 ✅
接口契约：POST /orders 请求体 {...}，api 组产出、ui 组按此对接
```

**分组硬规则**：

1. **组间文件集合必须两两无交集** —— 有交集的 todo 并到同一组
2. 每组必须有一条**机器可判**的组内验收用例（命令 + 退出码或输出断言），配不出用例的 todo 不许单独成组
3. 跨组依赖只能是**只读约定**（接口契约），不能是「等对方写完的代码」；真有先后依赖的**分两轮跑**（第一轮合并完再起第二轮）
4. 并行度 = 组数、**上限 4**，超了把小组并起来
5. 组名只用字母 / 数字 / 下划线 / 连字符（脚本会校验），用模块名别用 `g1 g2`

**判不出来就别硬分**（硬分的代价是 patch 冲突，比串行更慢）：

- 所有未完成 todo 都碰同一批核心文件、切不出两个无交集的组 → **不硬分**，说明原因并让用户去跑 `/xz-exec N`，本 skill 到此结束
- 只有一部分能并行 → 能并的分组并行，剩下的合成一个「串行组」，排在所有并行组**合并之后**由本 skill 顺序做（避免与并行组抢同一批文件）
- 某条 todo 的 改动详情 看不出会碰哪些文件（PLAN 写得含糊）→ 该条不参与并行，归入串行组

## 5. 建 worktree + 并行开发（流水线：谁先完成谁先合，主线程不空等）

先 `xz-tools.py wt create N api ui infra`，从返回 JSON 里取每组的 `worktree_path`（绝对路径）。然后**在同一条回复里并行起多个写 agent**，一组一个。

子 agent 在后台跑、**完成一个就通知一次**。收到任一组的完成通知，就**立刻对这一组走一遍第 6 步的收口三件事，不要等其他组** —— 这样最后一组交货时，前面几组已经合完、验完了，主线程全程没有空等。

**为什么边跑边合是安全的**（三条同时成立才成立，缺一条这套就不能用）：

- 每个 agent 只在**自己的 worktree 目录**里干活，主工作区的变化对它**透明**
- `wt apply` **不 commit**，主 HEAD 始终不动 → 还在跑的那几组 base 不会漂移
- 每个 worktree 有**独立的 git index**，主工作区 `git apply` 不跟它们抢锁

每个 agent 的任务书**七段齐全，缺一段就等于放它自由发挥**：

1. **工作目录** —— `wt create` 返回的 **`exec_cwd`**（仓库根 = 运行目录时它等于 `worktree_path`；不等时它是 worktree 里的同名子目录，别拿 `worktree_path` 顶替）。**所有改动只能在这个目录里做**，禁止改主仓库或别组的目录
2. **你负责的 todo + 适用的约束** —— 从 PLAN 逐字抄那几条的标题与 改动详情（含 `path:起止行` 和现状摘要），不要转述；**PLAN 的 `## 约束` 与 `## 技术方案` 里跟这几条相关的条目也要逐字带上** —— 那里面有 `/xz-plan` 3.5 跟用户确认过的风险处理（如「入口统一校验非空+格式」）和选定的实施方向，不带下去子 agent 根本看不到，等于把计划阶段的结论丢了
3. **你只许碰的文件清单** —— 第 4 步定的那几个路径；**需要改清单外的文件就停下来报告，不许自己扩大范围**（那说明分组错了，会跟别组撞车）
4. **接口契约** —— 跨组约定逐字给全；按契约写，**不要去猜别组会写成什么样**
5. **组内验收用例** —— 具体命令 + 判定标准。**先跑一次确认它现在跑不过**，改完再跑到通过（理由同 `/xz-exec` 第四步：一条从来没失败过的用例最后通过了，你分不清是代码真做对了还是这条用例压根没断到点子上）
6. **禁令** —— 禁止 `git commit` / `merge` / `rebase` / `push` / `checkout`，禁止动 `.xz_planning/`，禁止勾 todo。**你只改文件，patch 由主会话抓**
7. **必须的结构化返回** —— 最后一段固定这个格式：

   ```
   XZ_WORKTREE_RESULT
   status:         ok | failed
   changed_files:  逐个列出你改/建/删的文件
   commands:       跑过的命令 + 退出码（组内用例的那条必须在）
   gate:           改前跑用例=失败/通过，改后跑用例=通过/失败
   blockers:       卡在哪（没有就写「无」）
   ```

**只回一句「已完成」= 该组判失败**（走第 6 步的 `--preserve`）。缺结构化返回、`gate` 里改后仍失败、或 `changed_files` 与第 3 段的清单不符，都按失败处理——不允许凭自然语言进入合并。

## 6. 收口三件事（一组一遍，收到完成通知就做，做完回去等下一组）

1. **抓 + 合** —— `xz-tools.py wt capture N <组名>`（**失败的组也要抓**，现场要留证据），然后 `xz-tools.py wt apply N <组名>`；该组开发失败就加 `--preserve=<组名>`（只留现场不合）
2. **在主工作区跑这一组的验收用例** —— agent 在自己 worktree 里已经跑过一次，这里**再跑一次**：worktree 里通过 ≠ 跟别组的改动放在一起还通过。**这一步是流水线的核心价值** —— 跨组的代码级冲突（patch 层面不冲突、但编译或语义冲突）在这儿就能抓到，不用等到全量闭环
3. **打印一行 + 勾 todo** —— 如 `api → applied（4 文件）｜主工作区验收 ✅`；合并成功的组把它那几条 todo 勾成 `[x]`

**三种失败分开处理，别混着办**：

| 情况 | 怎么办 |
|---|---|
| **只有这一组的验收用例挂了**（项目还能编译、别组的用例还跑得动） | 记进「待闭环处理」清单，**不回滚**，继续等下一组。根因交给 `/xz-exec` 的闭环修复循环 |
| **主工作区被搞坏了**（编译不过 / 服务起不来，后面几组测了也白测） | **停下报告**：说清是哪一组的 patch 引入的，给两个出口 —— `a) 回滚这一组（git apply -R <patch 路径>）再合其余组  b) 保留现状，我自己看`。**别自己决定回滚** |
| **patch 冲突**（`conflict`） | 现场与 patch 都已保留。**不许强推** —— 不许 `git apply --3way`、不许手改 patch 重试、不许在主工作区重写一遍那组的改动。冲突说明分组判错了，把现场路径交给用户 |
| **改动全被 `.gitignore` 挡住**（`no_changes` 但带 `ignored_files`） | 不是这组没干活，是产出落在被忽略的路径上、抓不进 patch。**脚本已保留现场**（这种情况不删 worktree）——把它的 `ignored_files` 和 warning 原样转给用户，让他决定是把这些路径从 `.gitignore` 摘出来后重跑 `wt capture`，还是自己去 worktree 里取文件 |

**apply 顺序 = 完成顺序**，不再是第 4 步表里的组序。分组无交集时顺序无关紧要，但**报告里必须记实际合并顺序** —— 万一出了冲突，归因要靠它。

**主 HEAD 在开发期间变了** → 脚本会拒绝集成（base 漂移）。别自己想办法绕，把脚本的错误原样转给用户。

## 7. 落盘与状态（全部组都收口完之后做一次）

todo 的勾选已在第 6 步逐组做掉了，这一步只收总账：

- **全部组 `applied`、主工作区验收都过、且任务清单里再无 `[ ]`** → 取 `date "+%Y-%m-%d %H:%M:%S"` → 更新 `> 最后更新:` → 变更记录追加一行（含实际合并顺序，如 `- YYYY-MM-DD HH:mm:ss 并行开发完成 #1-#5（3 组，合并顺序 ui→api→infra）`）→ 状态置 **`待闭环测试`** → 删掉 `worktree/*.patch`（handoff 留着做留痕，patch 已无用、留着会随 phase 目录一起被归档）→ 跑 `xz-tools.py update-state`
  > **`待闭环测试` 的隐含契约是「所有 todo 都已勾完」** —— `/xz-exec` 读到它会**完全跳过实现**、直接跑闭环然后置 `已完成`。所以清单里只要还有一条 `[ ]`（串行组没做完、某组失败），就**绝不许置这个状态**，否则未实现的条目会被静默跳过。
- **有组 `conflict` / `preserved` / `no_changes`，或有组的主工作区验收没过** → 状态**保持 `进行中`**（已合并的组 todo 照样勾着），变更记录写清哪几组成功、哪几组留了现场、哪几组待闭环处理
- 有「串行组」→ 并行组全部收口之后，按 `/xz-exec` 第四步的做法顺序做完，再一起落盘。**串行组没做完之前状态一律保持 `进行中`**

## 8. 输出下一步

**全绿**：

> 版本 N 的 3 组已全部合并到主工作区（未 commit），合并顺序 ui→api→infra，每组合并后都在主工作区跑过验收用例、全通过。状态已置「待闭环测试」。
> 下一步: /xz-exec N —— 它会现场生成用例表并跑全量闭环测试

**有「待闭环处理」项**（合并成功、但主工作区验收没过）：首行说清全绿了几组，然后逐项写「哪一组 / 哪条用例挂了 / 报的什么错」，并说明「不回滚、根因交给 `/xz-exec N` 的闭环修复循环」。

**有失败**：逐组列出现场路径 + patch 路径 + 卡在哪，然后给三个出口：

> a) 我自己看现场处理（worktree 还在，改完可以手工 `git apply` 那份 patch）
> b) 重跑 /xz-worktree N —— 先跑 `xz-tools.py wt clean N` 收掉这一轮的现场（否则同名组会被拒），并且**先把本轮已合并的改动 commit 或 stash**（主工作区必须干净，这一步 AI 不替你做），然后重新分组只做还没勾上的 todo
> c) 转 /xz-exec N 串行做剩下的
> 现场处理完记得跑 `xz-tools.py wt clean N` 收掉残留的 worktree 与临时分支 —— **归档或删除版本之前务必清掉**，`/xz-done` 与 `/xz-del` 都有闸门拦这件事，清晚了工具就再也定位不到现场了

## 关键规则（命中任一即违规）

| # | 规则 | 什么算违规 |
|---|------|-----------|
| 1 | 分组无交集、有用例、判不准就退回串行 | 组间文件有重叠还硬分；某组配不出机器可判的验收用例；切不出无交集分组却强行分了（该转 `/xz-exec N`） |
| 2 | 子 agent 只改文件、不碰 git | 让 agent 去 commit / merge / rebase / push / checkout，或改 `.xz_planning/`、勾 todo |
| 3 | 结构化返回缺失即判失败 | 凭一句「已完成」就把某组算成功；`gate` 里改后仍失败却当成功；`changed_files` 超出文件清单还合并 |
| 4 | 主工作区必须干净、base 不许漂移 | AI 替用户 commit / stash / checkout 去凑「干净」；脚本报 base 漂移却自己想办法绕 |
| 5 | 冲突保留现场、不许强推 | 用 `--3way`、手改 patch、或在主工作区重写一遍那组改动去「解决」冲突 |
| 6 | 不自动 commit | 合并完替用户 `git commit`（改动只落到工作区，提不提交是用户的事） |
| 7 | 闭环测试归 `/xz-exec` | 在本 skill 里跑全量闭环、写 `N-TEST-REPORT.md`，或全绿后不置 `待闭环测试` 就建议 `/xz-done` |
| 8 | 已完成的不重做 | 把已经 `[x]` 的 todo 又分进某个组 |
| 9 | 不许空等子 agent | 收到某组的完成通知却压着不办，非要等所有组都返回才开始 capture / apply / 验收；或合完不在主工作区跑一遍该组验收用例就算这组过了 |
